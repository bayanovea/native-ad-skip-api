# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**native-ad-skip-api** is a hybrid Node.js + Go service for crowdsourced video ad/segment skipping. Users submit time-interval markups (intro, sponsor, self_promotion, credits). A Go CLI aggregates markups into consensus boundaries stored in `VideoCalculated`, which clients poll to skip ads. AI-first (prv, behind flags, all off by default): a second Go command detects segments from prv auto subtitles with Claude into `prv_ai_video_calculateds`, served instead of the human segments when `AI_FIRST=on`, and judges them on user signals (see AI-first segments).

### Go CLI (Calculation Engine)

Each provider has its own entry point that calls the shared `calculator` package with its table prefix (`""`, `"rt_"`, `"yt_"`).

```bash
# Build all three
go build -mod=vendor -o prv/commands/calculate ./prv/commands/
go build -mod=vendor -o rt/commands/calculate ./rt/commands/
go build -mod=vendor -o yt/commands/calculate ./yt/commands/

# Run (example for prv)
./prv/commands/calculate                # Process all videos with new markups
./prv/commands/calculate <video_id>    # Process a single video
./prv/commands/calculate --recompute-ratings   # Reset every segment rating from the votes table (see Ops)

# AI command (prv only, see AI-first segments); the binary sits next to its main.go, as calculate does
go build -mod=vendor -o prv/commands/ai/ai ./prv/commands/ai/
./prv/commands/ai/ai detect               # one cron tick (exits 0 at once unless AI_DETECT_ENABLED=on)
./prv/commands/ai/ai detect <native_id>   # manual run for one video: ignores the switch, the views / requests thresholds and the budget; synchronous; no heartbeat
./prv/commands/ai/ai judge                # one judge tick (exits 0 at once unless AI_JUDGE_ENABLED=on)
./prv/commands/ai/ai regate [--backfill]  # move AI entries between data and hidden by the current rules (see Ops)
```

- **Importer** imports a sheet (`--batch` = the sheet name, default the md file name) as batches of at most `--max-items N` (default 30): a larger sheet becomes `<sheet>-p1`, `-p2`, … of near-equal size in `position` order (`splitSheet()`: 104 → 26 × 4, not 30/30/30/14; the sheet is shuffled, so there are no video boundaries to keep), a sheet within the limit keeps its name. A re-import finds the sheet's items by `(sheet, item_code)` in whichever part they live; new items go to a new part (`-p<next>`, never into a part someone holds), which takes the first part's `reviews_needed` / `excluded` unless given; a new part name that already holds another sheet's items fails the import. It registers each batch in `prv_review_batches` with `--reviews N` (how many reviewers must finish it, default 1), `--exclude CODE[,CODE]` (registered codes that may never take it, e.g. the first reviewer of a subset sheet) and `--priority urgent|important|optional` (where it sorts on the page, default `important`; `optional` = a pass for when there is time, `urgent` is what the judge sends from prod); for an existing batch a value other than the stored one fails the import (never silently re-routes a batch), an option left out is not checked. `--assignee` is gone (fails with a hint: batches are first come). It names the md verdicts' reviewer with `--reviewer CODE` (default `bayanovea`); per batch, when the newly imported verdicts leave it unfinished for that reviewer it is locked on them (only if they may take it), when they finish it their lock is released; a re-run that imports nothing touches no lock. md verdicts of a `--reviewer` in the batch's `excluded` list, or into a batch locked by another reviewer (read `FOR UPDATE` in the import transaction, so a concurrent take waits), fail the import (exit 1, nothing written; an md whose verdicts are all skipped passes): one holder per batch. It reads `<sheet>.md` + `<sheet>.key.tsv` (written by `adskip sheet` in `native-ad-skip-eval`; blind `C<n>` sheets only, `K<n>` conflict sheets are rejected). Every item needs `Proposed as:`, an http(s) `Link:` and a `Verdict:` line. The verdict is the text on the `Verdict:` line; when that line is empty (as `adskip sheet` writes it), the first non-empty line after it must be the verdict (`Verdict: ` / `not an ad` / reason, the style of the 2026-10-12 sheets) and any other text there fails the import. The remaining lines are the comment, up to a markdown heading (`#`…`######` + space) or a `---` rule line, which ends the item. It first copies the md to `<sheet>.md.bak-YYYYMMDDHHMMSS` (suffix `-1`, `-2` instead of overwriting) and never writes the md. One transaction: items `ON CONFLICT ((COALESCE(sheet, batch)), item_code) DO NOTHING`, and an item already in the sheet must be the same stretch (`native_id`, `start`, `end`, `proposed`) or the import fails, so a regenerated sheet or a wrong `--batch` never attaches verdicts to the wrong item; md verdicts (`source='import'`) go through `recordVerdict` and only for items with no verdict yet from anyone, so re-running after more md marks adds only the new ones. An unknown verdict text fails the whole import (nothing written).
- **Split** (`split-review-batch.js <batch> [--max-items N]`, for batches imported before the limit) cuts a batch the importer's way in one transaction: the parts get its `reviews_needed` / `excluded` / `priority`, its items move with their `sheet` set (verdicts stay on them, so re-import and export by sheet name still work), its row is deleted. Refuses a locked batch (release it on the page first), one within the limit, one whose part names exist and one already split (names its parts). A reviewer with verdicts in the old batch comes back to each part under the come-back rule.
- **Export** (`export-review-verdicts.sh <sheet|batch> [reviewer]`: a sheet name exports all its parts, a part name only that part) writes the latest verdict per decided item (with a reviewer: their latest per item they decided, into `<name>.<reviewer>.verdicts.tsv`; an unregistered code exits 1) as `provider native_id category start end verdict item note` for `adskip review -file`: `sponsor`/`self_promotion` → `gold_missing` (category = the verdict), `not_ad` → `model_wrong`, `unclear` → `definition_unclear` (category = first proposed). Times with one decimal; a `gold_missing` row carries the item's effective bounds (those of the latest verdict with bounds, of the given reviewer when one is given, else the item's: an assessor's correction becomes the gold interval), the other rows the item's own (they judge the stretch the model proposed; an ai item's own are its entry's whole seconds, rounded inward from the cues, so an adopted sheet exports narrower than before: its old bounds stay in `flagged_by`, export it before adopting). Note = comment with tabs/newlines collapsed. Exits 1 (nothing written) on an unknown sheet or batch; creates `review/` if missing and writes through `<file>.tmp` + `mv`, so a failed query never leaves a truncated TSV.
- **Bounds import** (`import-verdict-bounds.js <tsv> [--dry-run]`, once for the times assessors typed into comments before the bounds fields existed; the owner-checked table is `~/Web/data/review/bounds-2026-10.tsv`, private): rows `sheet item_code reviewer start end` (`sheet` = a sheet or part name, `reviewer` `-` = the author of the item's latest verdict, times as the page reads them, `#` comments). Per row it appends a verdict copying the reviewer's latest verdict and comment plus the bounds (`source = 'import'`, `bounds_source = 'import'`; an ai item's entry moves as on the page), in one transaction with every touched batch row locked. Skips with the reason: no verdict by the reviewer, a later verdict by someone else, latest not a keep, invalid bounds (short ones are valid, as on the page), already these bounds. A malformed line, an unknown item or reviewer → exit 1, nothing written.
- **Below-threshold import** (`import-below-threshold.js [--sheet NAME] [--priority P] [--max-items N] [--min-seconds S] [--empty-only] [--dry-run]`, the DB env of the other scripts; inside the app container or with prod's `AI_MIN_SEGMENT_SECONDS` in the env, which sets the default `--min-seconds`): the AI rows' `hidden` entries with reason `confidence` (sponsor below `medium`, self_promotion below `high`; with `--min-seconds` below `AI_MIN_SEGMENT_SECONDS` also those hidden as `short`, never `review`) of rows with a run, withdrawn ones included, become **ai** items on their row (`kind = 'ai'`, `video_id`), so a verdict acts as on any ai item: a keep serves the entry (unless short), `not_ad` / `unclear` hide it on review; codes `B<n>`, bounds = the entry's, `proposed` = its category, `cues` = the run's transcript cues overlapping the bounds, `link` at start − 2 s, `flagged_by` = `detect run <id>: <category> <confidence>, <len> s, hidden: <reason>`, cut into parts the importer's way (`reviews_needed` 1, default priority `optional`). Entries shorter than `--min-seconds` (default `AI_MIN_SEGMENT_SECONDS`, `lib/ai-rules.js`) are left out: a short mention is not served at any confidence while the threshold stands, and the 2026-10-24 dry run had 82 of 161 under 5 s, mostly 1–5 s sponsor mentions from four streams; `--min-seconds 0` keeps them. A segment already in `prv_review_items` (same `native_id`, bounds ± 0.05 s, category, any sheet, or a sheet item holding it as adopt matches it; `reviewRepository.hasItemAt`) is skipped, so a later run imports only new detections; default sheet `ai-below-threshold-<YYYY-MM-DD>`, a sheet that already has items is refused (exit 1). `--empty-only` = only AI rows with empty `data`, not withdrawn (funnel stage 9). Their verdicts export like any item. `--served N [--seed S]` (no `--empty-only` / `--min-seconds`) instead sends a blind sample of what viewers get: shuffles the AI rows not withdrawn with non-empty `data` (seeded, `rng` / `shuffle` of `lib/review-sheet.js`, shared with `subset-review-sheet.js`, default seed 1), takes one random served entry per native_id until N, leaving out entries already in review and those whose bounds a verdict set (`source: review`); codes `S<n>`, `flagged_by` = `detect run <id>: <category> <confidence>, <len> s, served`, default sheet `ai-served-<YYYY-MM-DD>`, default priority `urgent`. A verdict acts as on any ai item (`not_ad` hides the entry, a keep with bounds corrects its timing).
- **Adopt** (`adopt-review-items.js <sheet> [--dry-run]`, once for `ai-below-threshold-2026-10-24`, whose `B<n>` were imported as `kind = 'sheet'` before the rows kept `hidden`; after `ai regate --backfill` and after exporting the sheet; inside the app container, `applyVerdict` reads `AI_MIN_SEGMENT_SECONDS`): a sheet item whose category matches one entry of its native_id's AI rows (`data` or `hidden`) sitting inside the item's bounds by < 1 s at each end (`entryInsideSheetItem`, `lib/review-sheet.js`: the old importer kept cue times to 0.1 s, entries are rounded inward) becomes an ai item at the entry's bounds (`reviewRepository.adoptItem`: `kind`, `video_id`, `start` / `end`, so later verdicts and the judge find the entry; the old bounds go to a `flagged_by` line `adopted: item bounds a-b`; only items of the old importer, `flagged_by` … `below the publish threshold`: a md sheet's items would fail its re-import), then its latest verdict goes through `applyVerdict` (`from` = the entry, `to` = the item's effective bounds; a `not_ad` / `unclear` after a keep with bounds hides the entry at those bounds, where a later page verdict looks); undecided items are converted only. One transaction per item under its batch row lock (`withBatchLock`, then the AI rows); no match or more than one (e.g. the entry in two AI rows of the native_id) leaves it a sheet item. Prints a line per item (`<code> <native_id> <old bounds> -> video <id> <entry> (<reason>|served) <verdict> applied|unchanged`) and `N items: M matched, A applied, U unmatched, K already ai items, O not below-threshold items, F failed` (exit 1 when any failed, e.g. bounds overlapping a served entry: that item rolls back); a re-run skips ai items.
- **Video flags export** (`export-video-flags.sh`) writes the latest value per `(native_id, flag)` of `prv_review_video_flags` as `provider native_id flag value reviewer set_at` to `review/video-flags.tsv`. Today one flag: `track_mismatch` (subtitle track ≠ player), the input for the eval repo's timing-clean slice and the drift audit.
- **Detector sync** (`scripts/sync-detector.sh <eval checkout>`): the detector lives in the eval repo (`~/Web/native-ad-skip-eval`, under `internal/`, so not importable; CI builds from this repo alone), so the product keeps a copy: the script copies `detector`, `transcript`, `vtt`, `provider`, `ytdlp` into `ai/` with the import path rewritten to `odedohbest/video-calculate/ai/…`, drops `claudecli.go` (eval-only transport) and the eval's key-file lookup (`apiKeyPath`: the key comes from `ANTHROPIC_API_KEY` only), keeps the product-owned `detector/fixture.go`, `fixture_test.go`, `apikey_test.go`, copies `prompts/<PROMPT>.md` to `ai/prompts/`, writes the eval commit to `ai/SOURCE`, warns when the eval's `anthropic-sdk-go` version differs from `go.mod` (then `go get` + `go mod tidy` + `go mod vendor`) and ends with `go build ./ai/...`. **Eval first, then sync**: never edit the copied packages or the detector prompt here; change and score them in the eval repo (its `TestProductPackagesImportOnlyEachOther` keeps the five packages free of `store` / `netguard`), commit there, then sync. A new prompt file also needs `AI_PROMPT` (default `/app/ai/prompts/v2.2.md`, not wired in compose) or a new default in `ai/pipeline/detect.go`; the prompt sha in every `prv_ai_runs` row tells which videos ran under which. `ai/prompts/judge-v1.md` is product-owned (no eval copy yet).
- **`--recompute-ratings`** (`calculator.RecomputeRatings`, `calculator/recompute.go`): for every video with a `{prefix}video_calculateds` row, in its own transaction: locks that row (`FOR UPDATE`, as the vote handler and a recalculation do), computes the ratings with the calculator's rule (see Calculation Algorithm), updates only the segment rows whose rating differs and rewrites the JSON entries' `rating` (sparse; entry order and other fields kept) only when one changed. Never touches boundaries, markups or `is_new`. 10 videos in parallel; a failing video is logged (`Recompute ratings failed: <video_id>: <err>`) and the binary exits 1 at the end. For prv it then does the same for every `prv_ai_video_calculateds` row in any state (its `data` JSON only, `hidden` has no ratings; under that row's `FOR UPDATE`; `Recompute ratings failed: AI row <video_id>: <err>`). Last line: `Recompute ratings finish: N videos processed, M segments changed, K video_calculateds rewritten` (prv: `, A prv_ai_video_calculateds rewritten`).
- **`ai regate [--backfill]`** (`ai/pipeline/regate.go`, by hand after a rule change; no heartbeat): for every `prv_ai_video_calculateds` row in any state (withdrawn too: restore serves their `data`), in its own transaction under the `video_calculateds` lock then the AI row's `FOR UPDATE` (the vote handlers' order), puts each entry of `data` ∪ `hidden` where the current rules say: a `reason: review` entry never moves; an entry whose latest ai-item verdict is a keep (at its effective bounds, whenever decided: `judge.EntryKeepsAll`, the judge's `entryKeeps` query without the `judged_at` bound) skips the confidence rule; the length rule (`AI_MIN_SEGMENT_SECONDS`) applies to all, confidence before short. Entries entering `data` get the votes' rating (`calculator.WithVoteRatings`), entries leaving it drop theirs; both arrays sorted by `start`; a row is written only when something moved; never withdraws (a row left with empty `data` serves nothing); served entries never overlap, so a hidden entry overlapping a served one (a keep moved an entry over it) stays hidden. `--backfill` first rebuilds an empty `hidden` from the row's run (object `raw_output` + transcript, the way `finish()` does): the segments that fail the current rules and overlap nothing in `data` (the detector's segments never overlap, so one that does is that entry, moved or re-categorised by a verdict; one a `not_ad` verdict removed passed the rules at the threshold it was published with, so none comes back: backfill before raising `AI_MIN_SEGMENT_SECONDS`); a run that no longer parses or validates is logged (`ai regate: run <id> not backfilled: …`) and skipped; a filled `hidden` is never rebuilt, so a second run adds nothing. Log per changed row `ai regate: video <video_id>: N served, M hidden (+in -out), K backfilled`, last line `ai regate: R rows, C changed, F failed (min S s)`; a failed row is logged (`ai regate: video <video_id> failed: …`) and the binary exits 1 at the end.

## Architecture

### Dual-Process Design

Two independent runtimes managed by Supervisor inside Docker:
- **Node.js (Express)** — HTTP API: CRUD for markups, votes, and serving calculated results
- **Go CLI** — Cron job every minute: aggregates new markups into `VideoCalculated`; plus the prv `ai` command (`ai detect` every 5 min, `ai judge` hourly, both no-ops unless switched on, see AI-first segments)

Communication is only through PostgreSQL. The Go binary reads `MarkupTimeInterval` rows where `is_new = true` and writes aggregated JSON to `VideoCalculated` plus relational rows in `{provider}_calculated_segments` (and the segment ↔ markup junction). Node reads `VideoCalculated.data` for client responses and recomputes the per-segment `rating` from the votes table (in both the JSON and the segments table) when a vote arrives or is deleted; the Go binary computes it the same way on every recalculation.

### Request Flow

```
Client → Express routes → Middleware (validate, auth) → Repository layer → PostgreSQL
                                                                ↓ (async, every minute)
                                                    Go CLI (calculate) → VideoCalculated
```

### Providers

The service supports three video platforms, each isolated in its own directory:

| Provider | Mount path | Directory |
|----------|-----------|-----------|
| prv | `/` | `prv/` |
| rt | `/rt` | `rt/` |
| yt | `/yt` | `yt/` |

Each provider directory has the same internal layout:

```
<provider>/
  commands/main.go       # Go CLI entry point (passes table prefix to calculator)
  db/index.js            # Sequelize models scoped to this provider's table prefix
  repository/            # Raw Sequelize queries
  routes/                # Express route handlers
  locales/review/        # Review page strings ru/en (prv/ only; loaded by lib/i18n.js, parity checked in test/i18n.test.js)
  service/               # Business logic (prv/ only; rt and yt reuse prv/service/user.js)
```

`rt` and `yt` share `prv/service/user.js` and `prv/routes/users.js` directly — they have no separate user service.

### Calculation Algorithm (`calculator/calculate.go`)

1. Query videos where any markup has `is_new = true`
2. For each video (up to 10 in parallel via goroutine pool), in **one transaction** (`db.Begin()`, commit at the end, rollback on any error, so a failure never leaves a video without its previous segments):
   - Read and row-lock the ids of the video's live `is_new` markups (`FOR NO KEY UPDATE SKIP LOCKED`). This runs before the interval read, so a markup committed in between is aggregated but stays new. A concurrent API write that sets `is_new = true` on a locked row waits for the commit and so survives it; a row some other transaction holds right now is skipped (no waiting, so no deadlock with the API) and stays new for the next run.
   - Read all live intervals of the video and group them by `(category_id, startRounded)` where `startRounded = start - (start % 3)` (3-second buckets)
   - **Start** = average of all starts in the group
   - **End** = median of all ends in the group
   - Row-lock the video's `video_calculateds` row (`FOR UPDATE`; the vote handler and `--recompute-ratings` take this lock first too, so the same order avoids deadlocks), then clear the previous segments (`{provider}_calculated_segment_markups` → `{provider}_calculated_segments` → `video_calculateds`)
   - Read the ratings from `{prefix}votes` (`voteRatings`), as late as possible: a segment's rating is the SUM of each user's latest vote (`DISTINCT ON (user_id, category_id, start, "end")`, `"createdAt" DESC, id DESC`) with an exact `(video_id, category_id, start, end)` match — vote bounds are floats, segment bounds ints. The Node API uses the same rule (`lib/segment-rating.js`). Votes whose bounds match no segment after a boundary shift count nowhere (`docs/backlog/votes-lost-when-segment-boundaries-shift.md`).
   - Insert the JSON array into `video_calculateds.data` (each entry: `category_id`, `start`, `end`, `rating` from the votes; `rating` is omitted when 0 — sparse representation).
   - Insert one row per segment into `{provider}_calculated_segments` (with that `rating`) and one row per contributing markup into `{provider}_calculated_segment_markups`
   - Set `is_new = false` on `{provider}markups` only for the ids read in the first step, so markups posted during the run are picked up by the next one
3. Per-video errors are returned, not panicked: the failing video is logged (`Calculate video failed: <video_id>: <err>`) and rolled back, the other videos go on, and the binary exits 1 at the end (`N of M videos failed`). Only startup failures (DB connect, listing the videos) abort the run.
4. Heartbeat: once the pool is done, `Run` upserts the provider's row in the shared `calculator_heartbeats` table (`provider` PK `prv`|`rt`|`yt`, plus `ai_detect` / `ai_judge` written by the `ai` command (see AI-first segments), `last_run_at`, `last_success_at`, `failed_videos`): `last_run_at = NOW()` always, `last_success_at` only when `failed_videos = 0` (an idle run with no videos counts as a success). Single-video mode writes it too, `--recompute-ratings` does not. A failed write is logged (`Heartbeat write failed: <err>`) and exits 1 — e.g. the table is missing because Go cron fired before Node's first `sync()` on a fresh deploy; the next minute is fine. `GET /metrics` exposes the row as the `calculator_*_timestamp_seconds` gauges (see Prometheus Metrics), the "Calculator: seconds since last success" stat panel on `grafana/dashboards/infrastructure.json` shows it (thresholds 600 s red; overrides per provider: `ai_detect` orange 600 / red 900, `ai_judge` orange 3900 / red 7200).

Cron starts each provider's binary every minute (`crontab`, offsets 0/20/40 s) under `flock -n /tmp/calculate-<provider>.lock`, so a run still going when the next minute fires makes the new one exit at once instead of overlapping. Their output (stdout and stderr) is appended to `/proc/1/fd/1`, supervisord's stdout, so it shows in `docker logs` next to the Node app's. The e2e suite covers the rollback, the mid-run markup, the skipped locked row, ratings surviving a recalculation, `--recompute-ratings` and the heartbeat (`calculator:` tests in `test/e2e.js`).

The segment rows in `{provider}_calculated_segments` are the source of truth for joins (e.g. analytics) and carry the same `rating` that lives in `video_calculateds.data`. Both are derived from the votes table: by the calculator on every recalculation, by the vote handler on every vote or vote deletion (see Routes → `votes.js`), and by `calculate --recompute-ratings` (see Ops).

### AI-first segments (prv: `ai/`, `prv/commands/ai`)

Plans with the decisions and trade-offs: `docs/plans/completed/20261022-ai-first-segments.md`, `docs/plans/completed/20261027-ai-hidden-entries.md` (every detected segment kept, `data` / `hidden`). Non-technical overview for the frontend developer and the assessors: `docs/ai-first-overview/{ru,en}.html` (shared `style.css`), published as the two claude.ai artifacts linked from the README (ru `6NZNwDcYKbLV5MUgKPwc8n`, en `SQhQy8xEPoY8XaxvKL4d6o`; each page's header links the other). **Keep it current**: a change to what this section describes at the conceptual level (what is served when, the gates, the judge's decisions, what a verdict does, the switches) updates both languages and the "updated" date in their header in the same change, then republishes both artifacts from the repo files (single file each: `style.css` inlined, the cross-language link pointing at the other artifact). Owner's rule: only segments we are sure the viewer sees correctly, even at the cost of missed ads. Every switch defaults off in code and `docker-compose.yml`; turning AI-first on is only ever the owner's env change (see Environment Variables), never a code default or a migration. Human markups keep being accepted on AI-first videos: they are the judge's strongest signal and the fallback when the AI row is withdrawn.

- **Trigger** (`prv_ai_videos`, one row per native_id): `GET /video-calculated` with `v` upserts it once the response is sent (`aiRepository.seen()` on `res.once('finish')`, 204 included; errors logged, never returned): `views_max = GREATEST(…)` from the count read out of the optional `views_text` param (the page's counter as text, `39,4 тыс просмотров` / `1.7M views`, parsed by `lib/parse-views-text.js`: first number + `тыс` / `млн` / `млрд` / `K` / `M` / `B`, thousands groups, a doubtful string → null, so a request without a readable counter never lowers or clears the max; never a 400, cut to 128 chars; the numeric `views` param is gone since 2026-10-26, now an ignored unknown param), `views_text` = the latest string sent, readable or not (a new page format shows as rows with a text and no `views_max`), `requests + 1`, `last_seen_at`; only prv video ids (`^-?\d+_\d+$`) are recorded; a user's own upload (no leading `-`, `111_222`) is recorded too but never taken by the tick, only community videos (`-111_222`) are (see `ai detect`). `status` (`seen` | `queued` | `fetching` | `detecting` | `published` | `withdrawn` | `no_track` | `timeline_unreliable` | `failed`) is moved by the detector, by a withdraw (`withdrawn`) and by a restore (`published`). The extension release that sends `views_text` is out since 2026-10-28; old versions never send it, so their videos reach the detector by `requests` alone (`docs/backlog/ai-views-from-clients.md`).
- **`ai detect`** (cron `*/5`, `flock -n /tmp/ai-detect.lock`; with `AI_DETECT_ENABLED` off a tick only expires runs older than 24 h and deletes its heartbeat row): claims up to `AI_BATCH_MAX` rows (default 5), oldest `first_seen_at` first (`FOR UPDATE SKIP LOCKED`, held for the claim only, so the read path's upsert never waits on yt-dlp), only community videos (`native_id ~ communityIDRegex` = `^-[0-9]+_[0-9]+$`, `queueRule` in `ai/pipeline/queue.go`, over every branch below, so a user upload is never claimed in any state, whatever its views / requests; `nativeIDRegex` `^-?…` stays the read path's and the manual run's): `status = 'seen' AND (views_max ≥ AI_MIN_VIEWS OR requests ≥ AI_MIN_REQUESTS)` (two independent criteria, a NULL `views_max` just fails the first; the claim sets `queued_by` once, `views` / `requests` / `both` by the row's values against that tick's thresholds, kept over retries and stale re-claims, NULL for rows claimed before 2026-10-28), a due retry (`queued`, `next_attempt_at ≤ NOW()`) or a `fetching` row untouched for 1 h (a crashed tick); at most `AI_DAILY_BUDGET_VIDEOS` `prv_ai_runs` rows in the last 24 h (rolling). Per video, after a pause of `AI_FETCH_PAUSE` ± 50 % (default 40 s → 20–60 s; none in the manual run), so prv sees the host's fetches spread out rather than as a burst at the cron minute (a ban would hit the shared prod IP; the API itself never calls prv): yt-dlp info (its `view_count` is never read: `views_max` comes from clients' `views_text` only; prv's info has none anyway, `null` on every video, 2026-10-24) → ru auto track (none: `queued` again after 6 h / 24 h / 72 h, then `no_track`; a yt-dlp error: after 6 h / 24 h, `failed` with `last_error` after 3 attempts; both count one `attempts`, so an error after two no-track tries fails the video; a yt-dlp that cannot start is the host's fault: no attempt, the row stays `fetching` and is claimed again after 1 h; so is a cron tick whose every fetch (≥ 2) failed while the info of the latest `published` video fails too (`hostFetches`; when that control fetches, the errors are the videos' and spend attempts as usual: a quiet tick of only broken videos once looped `fetching` and alerted hourly): prv refusing the host, logged `ai detect: every fetch of the tick failed (N videos)`, those N count as failed videos, so `CalculatorFailedVideos` fires within a tick instead of the rows reaching `failed` after ~30 h) → VTT collapse → **timeline gate**: last cue end − yt-dlp duration > 3 s → `timeline_unreliable`, nothing published (checked first, so a refused video gets no `videos` row) → the `videos` row by `(native_id, round(yt-dlp duration) ± 2)` (`findByNativeIdAndDuration`'s SQL); when the native_id has rows with a duration and none is within ± 2 → `timeline_unreliable` (yt-dlp sees another cut than the players), else the row without a duration or a new one; other rows off by > 2 s next to a match are logged (`ai detect: duration variants`, old split families exist). The model call is the eval's held-out configuration (`AI_MODEL`, prompt `AI_PROMPT`, effort `medium`, cue timestamps dropped): `AI_CLIENT=anthropic` submits one Batches API batch per tick (half price; `status = detecting`, then `batch_id`), polls every waiting batch once per tick and fails a video after 24 h without a result; `messages` makes one synchronous call per video; `fixture` reads `<native_id>.detect.json` (as a batch on the cron tick, synchronously in the manual run). The `prv_ai_runs` row is written before the submit (transcript, overrun, yt-dlp duration, prompt sha / version, model), so the budget counts a batch even if the tick dies before storing its id (that video expires instead of being paid for twice); a rejected submit (any error: nothing was sent, e.g. the API usage limit) deletes the run rows and queues the videos again in 1 h with `last_error` `batch submit: …`, no attempt spent; they count as failed videos of the tick. The row gets the raw output, usage and cost (`detector.Price`, × 0.5 for a batch) when the answer comes; a failed call or an invalid answer → `failed`. **Publish**: every segment is kept, bounds rounded inward to whole seconds (a span with no whole second inside is dropped), categories mapped to `markup_categories` ids by name; `data` (served) = `sponsor` with confidence ≥ `medium`, `self_promotion` only `high` (`accepted()`), and `end − start ≥ AI_MIN_SEGMENT_SECONDS` (default 5); the rest goes to `hidden` with `reason` `confidence` (below `accepted()`, checked first) or `short`; insert into `prv_ai_video_calculateds` (`published_at`), status `published`, also with empty `data` when nothing passes (done, nothing served). One log line per video (`ai detect: <native_id> <status> …`, publish: `… published: N served, M hidden of K segments`); heartbeat `ai_detect`: `failed_videos` counts only infrastructure failures (DB, API, a yt-dlp that cannot start), not a video's outcome (unavailable, no track, invalid answer, expiry: on its row), and the success needs only the tick's own steps (claim, batch listing, expiry); exit 1 on either. `ai detect <native_id>` is the manual run: ignores the switch, the views / requests thresholds, the community-only rule (takes a user upload) and the budget (claims a row not `fetching` / `detecting` without an AI row, created when missing; a `fetching` row untouched for 1 h, left by an interrupted run, is claimed again, as by the queue, so it never waits for a cron that may be off; a re-detect is refused because votes, verdicts and withdrawals refer to the row; `queued_by = 'manual'` on a first claim), calls the model synchronously, exits 1 unless the video ends `published`, and writes no heartbeat.
- **Serving** (`prv/routes/videos.js`): with `AI_FIRST=on`, the active AI row (`findAiCalculated`) on a `match` / `backfilled` lookup; otherwise, and on `mismatch` / `no_duration` (the player may be on another cut), today's `video_calculateds`. The AI row is keyed by the `videos` row of the yt-dlp duration, so a re-cut video never gets the old cut's segments. Entries have the `video_calculateds.data` shape plus `confidence` and `source: "ai"`, so the extension needs no change. The legacy `!v` branch is human only.
- **Served vs hidden** (owner, 2026-10-27): an AI row keeps every detected segment; `data` is exactly what is served, `hidden` the rest with a `reason`. Two layers, both precomputed (publish, `applyVerdict`, `ai regate`), nothing evaluated on the read path: the *truth* = the model's answer above `accepted()`'s confidence thresholds, overridden by the latest ai-item verdict (a keep pins the entry against the thresholds; `not_ad` / `unclear` → `review`, never back by a rule, only by a later keep); the *serving filter* = the length rule (`AI_MIN_SEGMENT_SECONDS`) on every entry, verdict or not. A rule change is an `ai regate` run (see Ops), never a read-time filter. Everything that reads `data` (serving, votes, `--recompute-ratings`, the judge, restore) ignores `hidden`, whose entries carry no rating; a hidden entry reaches viewers only by a rule change or a keep verdict (below-threshold items, see Ops).
- **`ai judge`** (cron at minute 30, `flock -n /tmp/ai-judge.lock`; off → deletes its heartbeat row): due = published, not withdrawn, non-empty rows already judged or published ≥ 24 h ago, skipped unless there is **new evidence** since its baseline (`signals.New`, stored as `signals.new`): the baseline is per entry: `judged_at` or, when the entry's latest ai-item verdict keeps it and came after the last judgement (`entryKeeps`; an item matches the entry at its effective bounds, see Votes / Verdicts below), that verdict (humans have the last word on what they saw); a conflicting markup belongs to no entry and takes the earliest of the entries' baselines. New evidence = rows created after the baseline: a user's latest vote on an entry that is down (per user and entry), an undo event, a conflicting human markup (dated by `GREATEST(markups."createdAt", markup_time_intervals."updatedAt")`: `PUT /markups` edits an interval in place and always touches it, on a category change every live interval of the markup (the category lives on `markups`), while `markups."updatedAt"` moves on every recalculation; an author's rating crossing 0 is not dated, such a markup becomes new evidence only with a later edit); plus re-cuts beyond the `duration_recut` that `prv_ai_videos.judge_counters` recorded (a row becomes a re-cut with a later request, which has no time of its own, and that count only grows). Likes, clicks and agreeing markups never make a video due. A time watermark, not a count comparison: totals shrink (an entry removed on review, a vote changed back) and would hide new evidence, and `POST /vote` keeps the row of a repeated identical vote, so a repeat is never new. Every judgement sets `judged_at` to the tick's start (what the signals were counted up to), so evidence created during the tick counts next time; the tick waits 1 s (`commitSettle`) before its first read, so a write whose `createdAt` (set by Node after its last lock wait, just before its commit: `POST /vote` creates the vote after the `VideoCalculated` / AI row locks, `PUT /markups` writes the intervals after the markup row lock, which can wait out a calculation) precedes the tick's start has committed and is counted now rather than read as old next time. Node, the Go binary and Postgres share the host clock. Every entry kept with nothing newer → one `ok` by `rules` ("every entry kept on review since the last judgement"), which moves `judged_at` past the verdicts. Signals (`signals.go`, restricted to the AI entries' exact `(category_id, start, end)` where the signal has bounds): `votes_up` / `votes_down` (each user's latest vote on each entry), `undo` (`prv_events_interval_undo`), `clicks`, conflicting human markups (live sponsor / self_promotion markups since publish with IoU < 0.5 to every AI entry of the category, author rating ≥ 0), `duration_variants`, `duration_recut` (a `videos` row off by > 2 s created after publish, with a request for the native_id since); views, requests and age go into `signals` only. Rules first (`rules.go`, on the new evidence): a new re-cut without a new negative → `review` by `rules` (items, the row stays served: anyone can create a `videos` row with any duration, and the row reaches only players of its own cut anyway); no new `votes_down` / `undo` / conflict → `ok` (only a first judgement, whose baseline is the start, gets here); else the LLM, which sees the totals, re-cut or not (a bogus duration never keeps a row from the judge and its withdraw; a new re-cut with new negatives still gets review items whatever the LLM says) (`llm.go`, Messages API, `AI_JUDGE_MODEL`, `ai/prompts/judge-v1.md`, schema `{decision: ok|withdraw|review, reason, segments: [{index, keep}]}`, input: entries with their transcript, counters per 1k views when known, ±60 s windows around entries and conflicting human intervals), not within `AI_JUDGE_MIN_INTERVAL` of the video's last judgement (`judged_at`, set by every judgement, a rules `ok` included; within it `judged_at` stays, so the evidence is still new afterwards). An answer that does not parse or check (one keep per entry, no `ok` with a `keep: false`) → `review` by `rules` with reason `judge_invalid: …` (fail safe toward a human); a transport error fails the video (the next tick retries). An LLM `withdraw` unpublishes (`withdrawn_by = 'judge'`) when `AI_JUDGE_AUTO_WITHDRAW` is on; `withdraw` and `review` (and `judge_invalid`) send one `kind = 'ai'` review item per served (`data`) entry (see ReviewItem), except for an entry that already has an ai item without a verdict (same bounds); the other entries still get theirs, so a withdrawn row can always be restored. Each judgement is a `prv_ai_judgements` row written under the AI row's `FOR UPDATE` (a row withdrawn meanwhile is left alone; one with an ai-item verdict decided after the tick's start, which `applyVerdict` applied under the same lock and may have removed or kept an entry the judgement saw, is left for the next tick: nothing written, `judged_at` stays, the call's cost only in the log); log `ai judge: <video_id> <decision> <by>: <reason>`; heartbeat `ai_judge` (`failed_videos` = videos that failed, e.g. an API error, retried next tick; the success needs only the due-videos query), exit 1 on either. The judge never closes a case without a human (`docs/backlog/ai-judge-autonomy-flag.md`).
- **Votes** on an AI-first video resolve the segment the way GET serves it; a vote belongs to the interval whatever source served it (owner, 2026-10-22): it rates the authors of a human interval with the same bounds and sets the rating of the AI entry and of that human segment alike, in every state of the AI row (see Routes → `votes.js`). Publish starts each entry with the rating of the votes already on its bounds (`calculator.WithVoteRatings`), read holding the `video_calculateds` row lock that the vote handlers take before the AI row, so no vote on the video commits between that read and the row becoming visible; `calculate --recompute-ratings` (prv) also rewrites every AI row's ratings. **Verdicts** on ai items are applied to the AI row (see Routes → `admin-review.js` → decide). A keep verdict may carry the segment's real **bounds** (owner, 2026-10-24: if a human looks anyway, the markup should come out right; `docs/plans/completed/20261024-assessor-timing.md`): the entry is replaced by one at those bounds with `source: "review"` (`confidence` kept, `rating` from the votes on the new bounds; votes on the old bounds are not carried over, as `docs/backlog/votes-lost-when-segment-boundaries-shift.md` accepts), and viewers get it, unless the bounds are under `AI_MIN_SEGMENT_SECONDS` (saved, the entry goes to `hidden` with reason `short`). A keep verdict serves a `hidden` entry too (its truth beats the confidence thresholds); `not_ad` / `unclear` hide the entry with reason `review`. An item's **effective bounds** = those of its latest verdict with bounds, else its own; the entry an item refers to sits there, so `applyVerdict`, `allKept` (`prv/repository/ai.js`) and the judge's `entryKeeps` go from an item to its entry by them, while everything keyed on an entry's bounds (votes, events, judge signals) needs no change. The judge request marks such entries `(bounds by review)` (`ai/judge/llm.go`, `judge-v1.md`); `/admin/video` shows a "review" badge. **Admin**: `/admin/video/:video_id` shows the AI row (status, entries, judgements) with a withdraw link (`withdrawn_by = 'admin'`, the operator's per-video switch).
- **Withdraw / restore**: `aiRepository.withdraw(video_id, by, reason)` sets `withdrawn_at/by/reason` (`data` kept for the record) and `prv_ai_videos.status = 'withdrawn'`. Only keep verdicts restore a row, and only one withdrawn by `judge` or `review`; `admin` rows stay withdrawn.

### Routes

All three providers share the same route shape; `prv/` also mounts the shared `events.js` / `users.js` and the prv-only admin pages (`admin.js`, `admin-moderation.js`, `admin-review.js`).

- **`markups.js`** — Core markup CRUD. `POST /markup` validates `data.intervals` with `lib/validate-intervals.js` (1–20 items; `start`/`end` finite numbers or numeric strings; after rounding `0 <= start < end <= 86400`; else 400) and creates the markup and all its intervals in one transaction. It rejects users with rating ≤ −2. It also silently returns 201 (no row created) when the user is hard-banned (banned_at IS NOT NULL); see Authentication. `PUT /markups` edits one interval (`new_start` / `new_end` / `new_category_id`): the resulting interval (new values merged with the stored ones) must pass the same `validateIntervals` rules, else 400 with the message as plain text; the interval update and the markup's `is_new = true` are one transaction; on prv the markup is updated first (its row lock can wait out a running calculation) and the interval rows after it, so their `"updatedAt"` dates the edit after any lock wait (the AI judge reads it): the addressed interval is written even for a category change alone, and a category change touches every live interval of the markup. Several delete endpoints have both `DELETE` and `GET` variants because Grafana can only trigger GET requests.
- **`votes.js`** — Vote submission. Each new vote runs in one transaction that first row-locks the video's `VideoCalculated` (`lockVideoCalculated` in `lib/segment-rating.js`, which re-reads once when a recalculation replaced the row meanwhile), then its AI row in any state (`lockAiCalculated`, `lib/find-ai-calculated.js`; prv only, none for most videos; this order lets an AI publish, which holds the first lock, read the votes without missing one), so votes on a video, its recalculation, an AI publish and `--recompute-ratings` serialise:
  - the segment must exist in what `GET /video-calculated` serves for the video (exact category/start/end), else 404: with `AI_FIRST=on`, an active AI row and a `duration` on the vote (the write lookup then lands within ±2 s, as GET's `match` / `backfilled`), that row's `data` (a segment only in `video_calculateds` of such a video is 404), else `video_calculateds.data`; the user's previous vote rows on the segment are replaced by the new one (the latest of them, `"createdAt" DESC, id DESC`, is the previous vote: pre-2026-10-17 data has several); the same value again keeps the row and its `createdAt` (the AI judge reads that time as when the user said it) and moves no author rating, but still recomputes the segment ratings below (a repeat repairs a drifted one). **One interval, one vote** (owner, 2026-10-22): a vote belongs to the `(category_id, start, end)` whatever source served it, so everything below happens on both paths
  - `recomputeSegmentRating` (`lib/segment-rating.js`) sets `{provider}_calculated_segments.rating` and the matching `video_calculateds.data` entry (sparse) from the votes table, with the calculator's rule (each user's latest vote, summed); `recomputeAiSegmentRating` sets the AI row's matching entry (no segment rows for AI); both run on every vote, whichever path it took (each skips what does not exist), so an AI entry and a human segment with the same bounds carry the same rating and the AI ratings stay right through a withdraw / restore or an `AI_FIRST` flip
  - the markup authors' user `rating` is adjusted by `vote - prevVote.vote` via `prv/service/user.js` `updateRatingByVote(vote, prevVote, { transaction })` (every author whose live markup has an interval with the exact `(start, end)`; ascending user id, so concurrent votes do not deadlock), an AI-path vote included
  - if the rating mutation drops a user to rating ≤ −100, `prv/service/user.js` also sets `banned_at` and writes a `prv_admin_decisions` row with `decided_by='auto'` (idempotent — only the first crossing writes; the `banned_at == null` guard short-circuits repeat crossings)
  - `GET /votes/:id/delete?verifyBearerToken=…` (Grafana link) undoes the vote: 401 on a wrong token, 404 on an unknown (or concurrently deleted) vote, else one transaction under the same locks (`VideoCalculated`, then the AI row) destroys the vote, recomputes the segment rating (table + JSON; skipped when the video has no `VideoCalculated`; also the AI row's entry in any state) and reverses the authors' change with `updateRatingByVote({ ...vote, vote: 0 }, vote, { transaction })`. The voter's own rating is never touched. `201 'Updated'`.
  - `GET /votes/user/:internal_user_id/update-rating?verifyBearerToken=…&rating=N` (Grafana link, e.g. `rating=-100` in `assessors.json`) overrides a user's rating: token first (`middleware/verify-query-token.js`, 401 whatever the params), then `rating` must be an INTEGER-range int (400), unknown user 404, else `201`. Each override is logged to stdout as `Admin rating override { internal_user_id, from, to }` (no table).
- **`videos.js`** — `GET /video-calculated` serves aggregated segments (prv: the AI row instead when AI-first applies, see AI-first segments; optional `views_text` string, the page's view counter, recorded in `prv_ai_videos` with every `v` request, see AI-first segments → Trigger); prv additionally logs duration claims and tracks legacy client versions. Uses a read-only `findVideoForRead` helper (never creates Video rows): looks up by `(native_id, duration±2)` (tolerance constant in `lib/duration-tolerance.js`), then `(native_id, null duration)` updating it, then any `native_id` match, then 204. The tolerance query is ordered by `ABS(duration - <requested>)`, then `id`, on the read path and in `findByNativeIdAndDuration` (`POST /markup`) alike, so a duration that fits both rows of an old split pair always lands on the same row (the 5 pre-2026-10-19 pairs stay split by decision: `docs/backlog/video-rows-race-and-old-split-families.md`).
- **`prv/routes/events.js`** — `POST /events` (shared by all providers). Accepts a JSON array of mixed events; supported types below. Invalid events (unknown `type`, missing fields) are logged to stdout and skipped — the rest of the batch still processes. Returns `{ data: { time_saved: { ... } } }` when the batch contains at least one `time_saved` event.

  - **`interval_click`** — fields: same as above plus `click_time` (int). Stored in `{provider}_events_interval_click`.
  - **`time_saved`** — fields: `user_id`, `prv_user_id`, `inc`. Increments `User.time_saved`; stored in `{provider}_events_time_saved`. Response mirrors the old `POST /users/time-saved` structure: `by_user_id`, `by_prv_user_id`, `by_user`.
  - **`client_failed`** — fields: `user_id`, `prv_user_id`, `video_native_id`, `reason` (string), `data` (arbitrary JSON, optional). Stored in `{provider}_events_client_failed`.

### Authentication

- **Admin routes**: `Authorization: Bearer <AUTH_TOKEN>` header (middleware `verify-bearer-token.js`)
- **Admin pages** (`/admin/video`, `/admin/moderation`, `/admin/user`, `/admin/review`): `AUTH_TOKEN` as `?verifyBearerToken=` query param, checked directly in `prv/routes/admin.js`, `admin-moderation.js` and `admin-review.js`. `admin-review.js` and the AI withdraw link also refuse every request when `AUTH_TOKEN` is unset, and its pages send no `Referer` (the token is in the URL).
- **Grafana GET links in `votes.js`** (`/votes/:id/delete`, `/votes/user/:internal_user_id/update-rating`, all providers): the same query param, checked by `middleware/verify-query-token.js` before any validator.
- **API docs** (`/api/doc`): HTTP Basic Auth — username `admin`, password `AUTH_TOKEN` env var
- Public write endpoints (markup creation, votes) are unauthenticated
- `POST /markup` silently returns 201 (no markup row created) when the user's `banned_at IS NOT NULL`, parallel to the existing `rating ≤ -2` soft gate.

**Soft Deletes:** All queries must filter `deleted_at IS NULL`. This is handled in `repository/` — always check there when writing new queries.

**Dual User ID System:** Users have both a `generated_user_id` (UUID) and an optional `prv_user_id`. The codebase is transitioning to internal DB `id` references.

**Schema bootstrap:** project has no migrations folder. New tables come from `sequelize.sync()` (run on every boot in `db.js`); new columns on existing tables are added with idempotent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statements run right after `sync()`. Example: `banned_at` on `users`. Column defaults go the same way (`ALTER TABLE … ALTER COLUMN … SET DEFAULT …`, e.g. the review tables' `created_at` / `decided_at`). The sync, the ALTERs and category seeding live in `lib/schema.js` `syncSchema()`, shared by `bootstrap()` and `scripts/sync-db.js`, so both leave the DB in the same shape — add new ALTERs there. One-offs live there too, guarded so a second boot is a no-op: `migrateBatchAssignees()` (2026-10-20) touches only rows with `prv_review_batches.assignee IS NOT NULL` and, in one transaction, sets `excluded = {bayanovea}` on `gkshi` batches (blind copies of her sheets), locks every free batch whose assignee has not finished it on that assignee (`gkshi` only once started, so untouched overlap batches go to anyone else), then sets `assignee = NULL`. The column is kept (nullable, added `IF NOT EXISTS` on a fresh DB, not in the model) because a pre-2026-10-20 image inserts it on boot, so a rollback still starts; a roll-forward re-migrates only the rows that image assigned. Dropping it: `docs/backlog/drop-review-batch-assignee.md`.

### Prometheus Metrics (`prometheus-wrapper.js`, `server.js`)

Two custom counters, the heartbeat and AI gauges and one HTTP histogram are exposed on `GET /metrics` (served by `server.js`, not by `express-prom-bundle`'s autoregister — `/metrics` is in `excludeRoutes` so it doesn't record itself).

**`video_calculated_lookup_total{outcome, provider, source}`** — outcomes of `GET /video-calculated`. `provider` is `prv` / `rt` / `yt`. `source` is the table served: `ai` (prv `match` / `backfilled` served from `prv_ai_video_calculateds`) or `human` (everything else, `not_found` / `not_calculated` and rt / yt included). `outcome` is one of:

| Outcome | Definition |
|---|---|
| `match` | Request supplied `duration`; row found by `(native_id, duration ± 2)`; `VideoCalculated` row exists. |
| `backfilled` | Request supplied `duration`; no `± 2` match; a row with `duration = NULL` existed and was just updated to the request's duration; `VideoCalculated` row exists. |
| `mismatch` | Request supplied `duration`; no `± 2` match; no `NULL` row to backfill; helper fell through to `findOne({ native_id })` and returned a row whose stored duration differs by > 2 s; `VideoCalculated` row exists. |
| `no_duration` | Request had no `duration` query param (legacy client); helper fell through directly to `findOne({ native_id })`; `VideoCalculated` row exists. |
| `not_calculated` | Helper returned a `Video` (any of the four above) but no `VideoCalculated` row was found; caller overrides the helper's outcome to `not_calculated`. |
| `not_found` | Helper returned `null` (no `Video` row matched at all). |

The first five outcomes are emitted by `lib/find-video-for-read.js`; `not_calculated` is derived in the route handler when `VideoCalculated.findOne` returns null. prv's legacy `!req.query.v` branch in `prv/routes/videos.js` does **not** emit a lookup outcome — it only increments `request_without_version_total`.

**`request_without_version_total{method, provider}`** — count of legacy client requests that omit the `v` query/body param. `method` is the route key (`GET /video-calculated`, `POST /markup`).

**`calculator_last_run_timestamp_seconds{provider}`**, **`calculator_last_success_timestamp_seconds{provider}`**, **`calculator_failed_videos{provider}`** — unix time of the Go calculator's last run / last run with no failed video, and the number of videos that failed in the last run (0 included), from `calculator_heartbeats` (one row per provider, see Calculation Algorithm step 4), read on every scrape by one shared `collect()` callback that `registerCalculatorHeartbeat(sequelize)` in `prometheus-wrapper.js` installs (called from `server.js` after `bootstrap()`, so the module stays DB-free for `test/prometheus-wrapper.test.js`). A provider without a row (or, for the success gauge, with `last_success_at` NULL) has no series; a failing query is logged once and leaves all three gauges empty for that scrape, the rest of `/metrics` is unaffected. The `CalculatorStale` alert watches the success gauge and `CalculatorFailedVideos` the failed-videos one (see Grafana → Alerting). The `ai` command's rows show up as `provider="ai_detect"` / `"ai_judge"`.

**`ai_videos{status}`**, **`ai_cost_usd{kind}`** (`detect` = SUM of `prv_ai_runs.cost_usd`, `judge` = of `prv_ai_judgements.cost_usd`), **`ai_cost_usd_24h{kind}`** (the same over rows with `created_at` in the last 24 h; the cost alert and panel read it, not `increase()` of a gauge), **`ai_judgements{decision, by}`**, **`ai_review_open`** (ai review items without a verdict, below-threshold ones included) — AI-first state from four plain queries per scrape (one refresh shared by the gauges) (`registerAiMetrics(sequelize)`, registered next to the heartbeat in `server.js`). A failing query is logged once and leaves them empty (`ai_review_open`, label-less, reads 0). **`ai_first_enabled`** (label-less, set once at registration from `AI_FIRST` as `lib/find-ai-calculated.js` read it at boot: 1 = the AI rows are served) tells the dashboard whether the "ready to serve" rows reach clients. Grafana: all of them on `ai-pipeline.json` (see AI-first segments → Dashboard); `infrastructure.json` keeps only the heartbeat stat.

**`http_request_duration_seconds_{bucket|count|sum}{method, path, status_code}`** — `express-prom-bundle` histogram with buckets `[0.05, 0.1, 0.25, 0.5, 1, 2.5]`. `path` is normalized via `normalizePath` rules in `server.js` so dynamic segments collapse (`/admin/video/12345` → `/admin/video/#video_id`, `/markups/42` → `/markups/#id`, `/admin/review/<batch>` → `/admin/review/#batch` except `/admin/review/decide` and `/admin/review/reviewers`, `…/<batch>/take|release` → `/admin/review/#batch/take|release`, `/admin/video/<id>/ai/withdraw` → `/admin/video/#video_id/ai/withdraw`, etc.). The default `url-value-parser` catches any unmapped numeric/UUID IDs as defense-in-depth.

**Storage / scrape:** Prometheus (`config/prometheus.yml`; `prometheus.dev.yml` is the dev stack's) scrapes every 30 s: `app:3022/metrics` (job `native-ad-skip-api`), `node-exporter:9100` (job `node`: host disk and memory; `pid: host`, the host's `/` read-only at `/host`) and, through `blackbox-exporter:9115` (job `blackbox`, module `http_2xx` of `config/blackbox.yml`: IPv4, 2xx, HTTPS required, 10 s timeout), `https://${API_HOST}/` and `https://${LANDING_HOST}/`, i.e. through public DNS, nginx and TLS (from the prod host itself, a hairpin to its own IP; a check from outside is still open: `docs/backlog/alerting-host-and-external-checks.md`). Neither exporter publishes a port. Prometheus stores data on the `prometheus_data` named Docker volume (mounted at `/prometheus` in the container; pinned project name `native-ad-skip-api` → stable volume `native-ad-skip-api_prometheus_data`). Retention is bounded by **both** `--storage.tsdb.retention.time=30d` and `--storage.tsdb.retention.size=2GB`; whichever hits first wins, so the volume can never exceed ~2 GB. The size cap exists because the `path` label on `http_request_duration_seconds` is effectively unbounded (unmatched/404 URLs each create their own series), which previously grew the volume to 35 GB. Prometheus does not downsample — reclaiming space means dropping whole 2 h blocks, which it does on startup and every compaction cycle.

**Grafana:** the `grafana` service in `docker-compose.yml` (the old `../native-ad-skip-grafana` repo is superseded). All services attach to the external `main-network` (precondition on the host: `docker network create main-network`). Datasources are provisioned from `grafana/provisioning/datasources/datasources.yml`: Prometheus at `http://prometheus:9090`, Postgres at `${DB_HOST}:5432` (= `host.docker.internal`). Dashboards are provisioned from `grafana/dashboards`; ad-hoc UI edits live only on the `native-ad-skip-api_grafana_data` volume. Data links that call the API's GET admin endpoints (vote/markup delete, update-rating) in `tables.json` and `assessors.json` take the token from a `verifyBearerToken` textbox variable that starts empty: type `AUTH_TOKEN` into it, or open the dashboard with `?var-verifyBearerToken=…`. Never commit a token value into a dashboard. Grafana listens on plain HTTP `:3024` (`http://${HOST_IP}:3024/`), open to the internet by a Timeweb cloud firewall rule and protected only by its login (anonymous access and sign-up disabled). Plain HTTP means the password crosses the network unencrypted, and its Postgres datasource uses the app's read-write `DB_USER`. Docker-published ports bypass host `ufw`; the **Timeweb cloud firewall** is the only filter, so to close Grafana remove the 3024 rule there (or bind it to `127.0.0.1` and use `ssh -L 3024:localhost:3024`).

**Alerting:** provisioned from the repo, folder "native-ad-skip-api", evaluation group `api` every minute, on the Prometheus datasource (`StaleMarkups` on the Postgres one). `grafana/provisioning/alerting/rules.yml` has eleven rules; `noDataState: OK` unless said otherwise (a rule removed from the file stays in Grafana and keeps firing until its uid is listed under `deleteRules` there, as `lookup-not-found-share` is since 2026-10-19):
- `CalculatorStale` — age of the last success over the provider's limit, `> 1` for 5 min: `(time() - max by (provider) (calculator_last_success_timestamp_seconds{…}))` divided by 600 for prv/rt/yt, 900 for `ai_detect`, 7200 for `ai_judge` (three selectors joined by `or`); no data at all = the calculator never ran, so `noDataState: Alerting`. A switched-off `ai` command deletes its heartbeat row, so it has no series rather than an aging one.
- `Http5xx` — `sum(increase(http_request_duration_seconds_count{status_code=~"5.."}[5m])) > 5` for 5 min.
- `ApiDown` — `up{job="native-ad-skip-api"}` below 1 for 2 min (queried unfiltered: `up == 0` is empty while healthy); no `up` series = Prometheus is not scraping the app, so `noDataState: Alerting`.
- `HttpLatencyP95` — `histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) > 1` for 5 min (the top bucket is 2.5 s, the quantile saturates there).
- `CalculatorFailedVideos` — `max by (provider) (calculator_failed_videos) > 0` for 3 min (three cron runs); the summary says to look for `Calculate video failed: <video_id>` in `docker logs` (for the `ai` providers: `ai detect:` / `ai judge:` lines). For the `ai` providers a failed video is an infrastructure failure (a video's own outcome is not counted; a detect tick whose every fetch failed counts: prv refusing the host, the summary says to set `AI_DETECT_ENABLED=off`), and one failed tick holds the gauge until the next one (5 min / 1 h): `docs/backlog/ai-detect-failed-videos-alert-window.md`.
- `AiCostDaily` — `sum(ai_cost_usd_24h) > 15` for 5 min: twice the default daily budget (`AI_DAILY_BUDGET_VIDEOS` 300 × $0.025); Grafana cannot read the env, so change the threshold with the budget. `AI_DETECT_ENABLED=off` stops the spend.
- `HostDiskLow` — `min by (mountpoint) (node_filesystem_avail_bytes / node_filesystem_size_bytes)` over `ext4|xfs|btrfs` below 0.15 for 10 min (Postgres, `docker logs` and images are not capped); no series = node-exporter not scraped, so `noDataState: Alerting`.
- `HostMemoryLow` — `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes` below 0.10 for 10 min.
- `ProbeFailed` — `min by (instance) (probe_success{job="blackbox"})` below 1 for 5 min (unfiltered, as `ApiDown`): nginx down, an expired or invalid certificate, DNS, or the app behind nginx; `ApiDown` scrapes `app:3022` directly and sees none of the first three. No series = blackbox-exporter not scraped, so `noDataState: Alerting`.
- `TlsCertExpiry` — `min by (instance) (probe_ssl_earliest_cert_expiry{job="blackbox"}) - time()` below 14 days for 1 h: certbot renews at 30 days left, so it fires only after two weeks of failed renewals (missing data is `ProbeFailed`'s).
- `StaleMarkups` — Postgres: `COUNT(*)` of `markups` with `is_new = true`, `deleted_at IS NULL` and `"updatedAt"` older than 10 min, `> 0` for 5 min (every `is_new = true` writer is a Sequelize update, which bumps `updatedAt`; prv only, rt/yt have no data).

`policies.yml` routes everything to the one contact point `telegram` (group by alertname, `group_wait 30s`, `group_interval 5m`, `repeat_interval 4h`). The contact point is **not** a file in that directory: Compose renders it from the `configs:` block of `docker-compose.yml` into `/etc/grafana/provisioning/alerting/contact-points.yml` (needs Compose 2.23.1+, prod has 2.40.3), with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` from the deploy environment — GitHub Actions secrets, never in the repo. Grafana's own `$VAR` expansion cannot be used for the chat id: Grafana 12.3.1 turns an env var that parses as a number into a YAML number and the Telegram integration requires `chatid` to be a string, so provisioning fails and Grafana refuses to start. **Missing secrets:** with both variables empty Grafana exits 1 at start (`Failed to provision alerting … could not find Bot Token in settings`) and crash-loops under `restart: unless-stopped`; `docker compose up -d` still returns 0, so the deploy job passes and `app` / `prometheus` are unaffected, but Grafana is down until the two secrets exist. Verified locally with Compose 2.40.3 and `grafana/grafana:12.3.1` on 2026-10-18.

```
YTDLP_BIN (/usr/local/bin/yt-dlp)         # the image's pinned static release, absolute because cron's PATH lacks /usr/local/bin; e2e points it to the stub
ANTHROPIC_API_KEY                         # env only (no key file); AI_CLIENT=anthropic|messages without it is a startup error (exit 1)
```

Wiring: `docker-compose.yml` passes `AI_FIRST`, `AI_DETECT_ENABLED`, `AI_JUDGE_ENABLED` (`:-off`), `AI_JUDGE_AUTO_WITHDRAW` (`:-on`), `AI_JUDGE_MODEL`, `AI_JUDGE_MIN_INTERVAL`, `AI_MIN_VIEWS`, `AI_MIN_REQUESTS`, `AI_DAILY_BUDGET_VIDEOS`, `AI_MIN_SEGMENT_SECONDS`, `ANTHROPIC_API_KEY` (empty = code default) to `app`; the deploy workflow fills them from repository variables (`vars.AI_*`) and the `ANTHROPIC_API_KEY` secret. Cron jobs see only `/app/.env`: `infrastructure/init/init_env.sh` appends every `AI_*`, `YTDLP_BIN` and `ANTHROPIC_API_KEY` of the container env there, and `prv/commands/ai/main.go` loads it (variables already set win). A new flag goes into the workflow's two lists (env and the `printf %q` exports) and `docker-compose.yml`; nothing else. The other variables above keep their code defaults on prod.

### Deployment

Prod is a single Timeweb Cloud VM in Almaty, `ala-1` (Ubuntu 24.04, `${HOST_IP}`; Novosibirsk had no capacity), migrated from Yandex Cloud in Oct 2026 — see `docs/plans/completed/20261014-timeweb-migration.md`.

- **CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`), on push to `main` or manual dispatch. A `test` job runs `make test-unit`, `go test -mod=vendor ./calculator ./ai/...` (`TestIntegration` skips when neither `TEST_DB_NAME` nor `DB_USER` is set) and `make test-e2e`; the `deploy` job `needs:` it, so a red test never deploys or pushes an image (one deploy at a time, `concurrency: deploy-prod`). The deploy job builds the image in CI (`docker/build-push-action`, GHA layer cache) and pushes it to GHCR as `ghcr.io/odedohbest/native-ad-skip-api:<commit sha>` and `:latest`, logging in with the job's `GITHUB_TOKEN` (`permissions: packages: write`). It then tars the checkout (without `.git` / `node_modules`) over SSH as `skipper-admin` to `/home/skipper-admin/tmp/codebase.tar.gz`, extracts it into a fresh `/home/skipper-admin/tmp/src/` (the previous checkout moves to `src.old/`, so files deleted from the repo do not linger; prometheus/grafana configs are bind-mounted from there), logs the host into GHCR with the same job token (expires with the job; `docker logout` on exit), and runs `docker compose -p native-ad-skip-api -f …/tmp/src/docker-compose.yml pull app` then `up -d --no-build --force-recreate --remove-orphans app prometheus grafana node-exporter blackbox-exporter` with `IMAGE_TAG=<sha>`, under `set -e` (`up` pulls the exporters' pinned Docker Hub images when missing). After a successful `up` it removes old `ghcr.io/odedohbest/native-ad-skip-api` images (and that repository's `<none>` ones): it keeps the `KEEP_IMAGES` = 5 newest by creation time plus the deployed `IMAGE_TAG`, removes the rest by `repo:tag` (never another repository, never a prune), ignores a failed `rm` (image in use) and logs two `Image cleanup:` lines. The remote script and its secrets go over stdin to `ssh … 'bash -s'` (`printf %q` exports), not on the remote command line. There is no `down` and nothing is built on the host (`--no-build`: the `app` service keeps `build: .` for local runs): the old stack keeps serving through the pull and stays up if it fails; the API is down only for the container swap. The host key is pinned in the workflow (ed25519, `StrictHostKeyChecking yes`), so a rebuilt VM needs the new key there. Secrets: `HOST_IP`, `SSH_PRIVATE_KEY`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `NODE_APP_PORT`, `AUTH_TOKEN`, `GF_ADMIN_PASSWORD`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (Grafana alerting, see Alerting; without them Grafana does not start), `ANTHROPIC_API_KEY` (the `ai` command; without it a switched-on detect or judge tick exits 1). Repository variables (not secrets): the `AI_*` switches (see Environment Variables; unset = off / code default). The image carries a pinned, sha256-checked static `yt-dlp` release (own Dockerfile stage `ytdlp`, by `TARGETARCH`) at `/usr/local/bin/yt-dlp` and the `ai` binary at `/app/prv/commands/ai/ai`. Supervisor inside the app container manages cron (Go CLI) and the Node.js app.
  - **First deploy with the `src/` layout** (2026-10-18): before it, the compose file and the bind-mounted `config/`, `grafana/` lived directly under `/home/skipper-admin/tmp/`. The stack is addressed by project name (`-p native-ad-skip-api`) and the named volumes keep their names (`native-ad-skip-api_prometheus_data`, `_grafana_data`), so the new compose path recreates the same containers with the new mount paths; the old files directly under `tmp/` (everything except `src/`, `src.old/`) can be deleted by hand after the first successful deploy.
  - **Rollback:** Actions → "Build and Run Docker Image on Timeweb" → Run workflow with `image_tag` = the previous commit sha (any sha CI has pushed; `:latest` stays at the newest build). The job skips the build and deploys that tag, tests included. By hand on the host, only for the 5 newest shas (the deploy removes older images from the local cache; no registry login needed): `IMAGE_TAG=<sha> docker compose -p native-ad-skip-api -f /home/skipper-admin/tmp/src/docker-compose.yml up -d --no-build app`. Back to a pre-AI image: delete the AI heartbeat rows it no longer writes, or `CalculatorStale` fires for them: `DELETE FROM calculator_heartbeats WHERE provider LIKE 'ai_%';` (host Postgres, app role).
  - **GHCR visibility** follows the repo: the repo is private, so the package is private and the job token is the only login the host ever uses. A manual `docker pull` on the host would need a PAT with `read:packages` (`docker login ghcr.io`), and `docker logout ghcr.io` afterwards.
- **DNS:** reg.ru, zone `${DNS_ZONE}` on reg.ru's free NS; A records `api`, `www.api`, `test-api`, `adskip`, `www.adskip` → `${HOST_IP}`, zone TTL 1h (panel minimum). `api` (this repo's vhost) and the landing `adskip` (static Vue build in `/var/www/landing`, `www` redirects to it) have vhosts and certs; the landing's vhost `/etc/nginx/sites-available/landing.conf` is not in this repo.
- **TLS / reverse proxy:** nginx on the host terminates TLS for `${API_HOST}` (Let's Encrypt, certbot webroot renewals) and proxies to `127.0.0.1:3022`. The vhost is versioned in `infrastructure/nginx/` and copied to the host by hand; its access log uses the `redacted` format (`redacted-log-format.conf` in `conf.d/`: no query string, no referer), so `?verifyBearerToken=` is not logged. `.dev` is HSTS-preloaded, so the API is HTTPS-only.
- **Postgres:** PostgreSQL 16 installed on the host via apt, not in Docker. Containers reach it at `host.docker.internal` (`extra_hosts: host-gateway`); `pg_hba` + `ufw` allow only `172.16.0.0/12` (Docker bridges) and localhost, so 5432 is never public.
- **Backups:** Timeweb VM auto-backups (daily, keep 7) plus `make pull-dump` (`scripts/pull-prod-dump.sh`), which streams a gzipped `pg_dump --no-owner` over SSH to `~/Web/dumps/adskip-prod/` on the owner's Mac (`latest.sql.gz` symlink) — run weekly. The nightly S3 job (`infrastructure/backup/pg-backup.sh`, restore drill in its README) is written but **not installed yet**: `docs/backlog/offhost-pg-backup-s3.md`.
