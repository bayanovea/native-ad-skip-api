# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**native-ad-skip-api** is a hybrid Node.js + Go service for crowdsourced video ad/segment skipping. Users submit time-interval markups (intro, sponsor, self_promotion, credits). A Go CLI aggregates markups into consensus boundaries stored in `VideoCalculated`, which clients poll to skip ads. AI-first (prv, behind flags, all off by default): a second Go command detects segments from prv auto subtitles with Claude into `prv_ai_video_calculateds`, served instead of the human segments when `AI_FIRST=on`, and judges them on user signals (see AI-first segments).

- **Importer** imports a sheet (`--batch` = the sheet name, default the md file name) as batches of at most `--max-items N` (default 30): a larger sheet becomes `<sheet>-p1`, `-p2`, … of near-equal size in `position` order (`splitSheet()`: 104 → 26 × 4, not 30/30/30/14; the sheet is shuffled, so there are no video boundaries to keep), a sheet within the limit keeps its name. A re-import finds the sheet's items by `(sheet, item_code)` in whichever part they live; new items go to a new part (`-p<next>`, never into a part someone holds), which takes the first part's `reviews_needed` / `excluded` unless given; a new part name that already holds another sheet's items fails the import. It registers each batch in `prv_review_batches` with `--reviews N` (how many reviewers must finish it, default 1) and `--exclude CODE[,CODE]` (registered codes that may never take it, e.g. the first reviewer of a subset sheet); for an existing batch a value other than the stored one fails the import (never silently re-routes a batch), an option left out is not checked. `--assignee` is gone (fails with a hint: batches are first come). It names the md verdicts' reviewer with `--reviewer CODE` (default `bayanovea`); per batch, when the newly imported verdicts leave it unfinished for that reviewer it is locked on them (only if they may take it), when they finish it their lock is released; a re-run that imports nothing touches no lock. md verdicts of a `--reviewer` in the batch's `excluded` list, or into a batch locked by another reviewer (read `FOR UPDATE` in the import transaction, so a concurrent take waits), fail the import (exit 1, nothing written; an md whose verdicts are all skipped passes): one holder per batch. It reads `<sheet>.md` + `<sheet>.key.tsv` (written by `adskip sheet` in `ad-skip-segment-eval`; blind `C<n>` sheets only, `K<n>` conflict sheets are rejected). Every item needs `Proposed as:`, an http(s) `Link:` and a `Verdict:` line. The verdict is the text on the `Verdict:` line; when that line is empty (as `adskip sheet` writes it), the first non-empty line after it must be the verdict (`Verdict: ` / `not an ad` / reason, the style of the 2026-10-12 sheets) and any other text there fails the import. The remaining lines are the comment, up to a markdown heading (`#`…`######` + space) or a `---` rule line, which ends the item. It first copies the md to `<sheet>.md.bak-YYYYMMDDHHMMSS` (suffix `-1`, `-2` instead of overwriting) and never writes the md. One transaction: items `ON CONFLICT ((COALESCE(sheet, batch)), item_code) DO NOTHING`, and an item already in the sheet must be the same stretch (`native_id`, `start`, `end`, `proposed`) or the import fails, so a regenerated sheet or a wrong `--batch` never attaches verdicts to the wrong item; md verdicts (`source='import'`) go through `recordVerdict` and only for items with no verdict yet from anyone, so re-running after more md marks adds only the new ones. An unknown verdict text fails the whole import (nothing written).
- **Split** (`split-review-batch.js <batch> [--max-items N]`, for batches imported before the limit) cuts a batch the importer's way in one transaction: the parts get its `reviews_needed` / `excluded`, its items move with their `sheet` set (verdicts stay on them, so re-import and export by sheet name still work), its row is deleted. Refuses a locked batch (release it on the page first), one within the limit, one whose part names exist and one already split (names its parts). A reviewer with verdicts in the old batch comes back to each part under the come-back rule.
- **Export** (`export-review-verdicts.sh <sheet|batch> [reviewer]`: a sheet name exports all its parts, a part name only that part) writes the latest verdict per decided item (with a reviewer: their latest per item they decided, into `<name>.<reviewer>.verdicts.tsv`; an unregistered code exits 1) as `provider native_id category start end verdict item note` for `adskip review -file`: `sponsor`/`self_promotion` → `gold_missing` (category = the verdict), `not_ad` → `model_wrong`, `unclear` → `definition_unclear` (category = first proposed). Times with one decimal, note = comment with tabs/newlines collapsed. Exits 1 (nothing written) on an unknown sheet or batch; creates `review/` if missing and writes through `<file>.tmp` + `mv`, so a failed query never leaves a truncated TSV.
- **Video flags export** (`export-video-flags.sh`) writes the latest value per `(native_id, flag)` of `prv_review_video_flags` as `provider native_id flag value reviewer set_at` to `review/video-flags.tsv`. Today one flag: `track_mismatch` (subtitle track ≠ player), the input for the eval repo's timing-clean slice and the drift audit.
- **Detector sync** (`scripts/sync-detector.sh <eval checkout>`): the detector lives in the eval repo (`~/Web/ad-skip-segment-eval`, under `internal/`, so not importable; CI builds from this repo alone), so the product keeps a copy: the script copies `detector`, `transcript`, `vtt`, `provider`, `ytdlp` into `ai/` with the import path rewritten to `odedohbest/video-calculate/ai/…`, drops `claudecli.go` (eval-only transport) and the eval's key-file lookup (`apiKeyPath`: the key comes from `ANTHROPIC_API_KEY` only), keeps the product-owned `detector/fixture.go`, `fixture_test.go`, `apikey_test.go`, copies `prompts/<PROMPT>.md` to `ai/prompts/`, writes the eval commit to `ai/SOURCE`, warns when the eval's `anthropic-sdk-go` version differs from `go.mod` (then `go get` + `go mod tidy` + `go mod vendor`) and ends with `go build ./ai/...`. **Eval first, then sync**: never edit the copied packages or the detector prompt here; change and score them in the eval repo (its `TestProductPackagesImportOnlyEachOther` keeps the five packages free of `store` / `netguard`), commit there, then sync. A new prompt file also needs `AI_PROMPT` (default `/app/ai/prompts/v2.2.md`, not wired in compose) or a new default in `ai/pipeline/detect.go`; the prompt sha in every `prv_ai_runs` row tells which videos ran under which. `ai/prompts/judge-v1.md` is product-owned (no eval copy yet).
- **`--recompute-ratings`** (`calculator.RecomputeRatings`, `calculator/recompute.go`): for every video with a `{prefix}video_calculateds` row, in its own transaction: locks that row (`FOR UPDATE`, as the vote handler and a recalculation do), computes the ratings with the calculator's rule (see Calculation Algorithm), updates only the segment rows whose rating differs and rewrites the JSON entries' `rating` (sparse; entry order and other fields kept) only when one changed. Never touches boundaries, markups or `is_new`. 10 videos in parallel; a failing video is logged (`Recompute ratings failed: <video_id>: <err>`) and the binary exits 1 at the end. For prv it then does the same for every `prv_ai_video_calculateds` row in any state (JSON only, under that row's `FOR UPDATE`; `Recompute ratings failed: AI row <video_id>: <err>`). Last line: `Recompute ratings finish: N videos processed, M segments changed, K video_calculateds rewritten` (prv: `, A prv_ai_video_calculateds rewritten`).

## Architecture

### Dual-Process Design

Two independent runtimes managed by Supervisor inside Docker:
- **Node.js (Express)** — HTTP API: CRUD for markups, votes, and serving calculated results
- **Go CLI** — Cron job every minute: aggregates new markups into `VideoCalculated`; plus the prv `ai` command (`ai detect` every 5 min, `ai judge` hourly, both no-ops unless switched on, see AI-first segments)

Communication is only through PostgreSQL. The Go binary reads `MarkupTimeInterval` rows where `is_new = true` and writes aggregated JSON to `VideoCalculated` plus relational rows in `{provider}_calculated_segments` (and the segment ↔ markup junction). Node reads `VideoCalculated.data` for client responses and recomputes the per-segment `rating` from the votes table (in both the JSON and the segments table) when a vote arrives or is deleted; the Go binary computes it the same way on every recalculation.

### Request Flow

```
Client → Express routes → Middleware (validate, auth) → Repository layer → PostgreSQL
                                                                ↓ (async, every minute)
                                                    Go CLI (calculate) → VideoCalculated
```

### Calculation Algorithm (`calculator/calculate.go`)

1. Query videos where any markup has `is_new = true`
2. For each video (up to 10 in parallel via goroutine pool), in **one transaction** (`db.Begin()`, commit at the end, rollback on any error, so a failure never leaves a video without its previous segments):
   - Read and row-lock the ids of the video's live `is_new` markups (`FOR NO KEY UPDATE SKIP LOCKED`). This runs before the interval read, so a markup committed in between is aggregated but stays new. A concurrent API write that sets `is_new = true` on a locked row waits for the commit and so survives it; a row some other transaction holds right now is skipped (no waiting, so no deadlock with the API) and stays new for the next run.
   - Read all live intervals of the video and group them by `(category_id, startRounded)` where `startRounded = start - (start % 3)` (3-second buckets)
   - **Start** = average of all starts in the group
   - **End** = median of all ends in the group
   - Row-lock the video's `video_calculateds` row (`FOR UPDATE`; the vote handler and `--recompute-ratings` take this lock first too, so the same order avoids deadlocks), then clear the previous segments (`{provider}_calculated_segment_markups` → `{provider}_calculated_segments` → `video_calculateds`)
   - Read the ratings from `{prefix}votes` (`voteRatings`), as late as possible: a segment's rating is the SUM of each user's latest vote (`DISTINCT ON (user_id, category_id, start, "end")`, `"createdAt" DESC, id DESC`) with an exact `(video_id, category_id, start, end)` match — vote bounds are floats, segment bounds ints. The Node API uses the same rule (`lib/segment-rating.js`). Votes whose bounds match no segment after a boundary shift count nowhere (`docs/backlog/votes-lost-when-segment-boundaries-shift.md`).
   - Insert the JSON array into `video_calculateds.data` (each entry: `category_id`, `start`, `end`, `rating` from the votes; `rating` is omitted when 0 — sparse representation).
   - Insert one row per segment into `{provider}_calculated_segments` (with that `rating`) and one row per contributing markup into `{provider}_calculated_segment_markups`
   - Set `is_new = false` on `{provider}markups` only for the ids read in the first step, so markups posted during the run are picked up by the next one
3. Per-video errors are returned, not panicked: the failing video is logged (`Calculate video failed: <video_id>: <err>`) and rolled back, the other videos go on, and the binary exits 1 at the end (`N of M videos failed`). Only startup failures (DB connect, listing the videos) abort the run.
4. Heartbeat: once the pool is done, `Run` upserts the provider's row in the shared `calculator_heartbeats` table (`provider` PK `prv`|`rt`|`yt`, plus `ai_detect` / `ai_judge` written by the `ai` command (see AI-first segments), `last_run_at`, `last_success_at`, `failed_videos`): `last_run_at = NOW()` always, `last_success_at` only when `failed_videos = 0` (an idle run with no videos counts as a success). Single-video mode writes it too, `--recompute-ratings` does not. A failed write is logged (`Heartbeat write failed: <err>`) and exits 1 — e.g. the table is missing because Go cron fired before Node's first `sync()` on a fresh deploy; the next minute is fine. `GET /metrics` exposes the row as the `calculator_*_timestamp_seconds` gauges (see Prometheus Metrics), the "Calculator: seconds since last success" stat panel on `grafana/dashboards/infrastructure.json` shows it (thresholds 600 s red; overrides per provider: `ai_detect` orange 600 / red 900, `ai_judge` orange 3900 / red 7200).

Cron starts each provider's binary every minute (`crontab`, offsets 0/20/40 s) under `flock -n /tmp/calculate-<provider>.lock`, so a run still going when the next minute fires makes the new one exit at once instead of overlapping. Their output (stdout and stderr) is appended to `/proc/1/fd/1`, supervisord's stdout, so it shows in `docker logs` next to the Node app's. The e2e suite covers the rollback, the mid-run markup, the skipped locked row, ratings surviving a recalculation, `--recompute-ratings` and the heartbeat (`calculator:` tests in `test/e2e.js`).

The segment rows in `{provider}_calculated_segments` are the source of truth for joins (e.g. analytics) and carry the same `rating` that lives in `video_calculateds.data`. Both are derived from the votes table: by the calculator on every recalculation, by the vote handler on every vote or vote deletion (see Routes → `votes.js`), and by `calculate --recompute-ratings` (see Ops).

### AI-first segments (prv: `ai/`, `prv/commands/ai`)

Plan with the decisions and trade-offs: `docs/plans/completed/20261022-ai-first-segments.md`. Owner's rule: only segments we are sure the viewer sees correctly, even at the cost of missed ads. Every switch defaults off in code and `docker-compose.yml`; turning AI-first on is only ever the owner's env change (see Environment Variables), never a code default or a migration. Human markups keep being accepted on AI-first videos: they are the judge's strongest signal and the fallback when the AI row is withdrawn.

- **Trigger** (`prv_ai_videos`, one row per native_id): `GET /video-calculated` with `v` upserts it once the response is sent (`aiRepository.seen()` on `res.once('finish')`, 204 included; errors logged, never returned): `views_max = GREATEST(…)` from the optional `views` param (a request without it never lowers or clears the max), `requests + 1`, `last_seen_at`; only prv video ids (`^-?\d+_\d+$`) are recorded, and the claim takes no other. `status` (`seen` | `queued` | `fetching` | `detecting` | `published` | `withdrawn` | `no_track` | `timeline_unreliable` | `failed`) is moved by the detector, by a withdraw (`withdrawn`) and by a restore (`published`). No client sends `views` yet, so every row is a fallback row (`docs/backlog/ai-views-from-clients.md`).
- **`ai detect`** (cron `*/5`, `flock -n /tmp/ai-detect.lock`; with `AI_DETECT_ENABLED` off a tick only expires runs older than 24 h and deletes its heartbeat row): claims up to `AI_BATCH_MAX` rows, oldest `first_seen_at` first (`FOR UPDATE SKIP LOCKED`, held for the claim only, so the read path's upsert never waits on yt-dlp): `status = 'seen' AND (views_max ≥ AI_MIN_VIEWS OR (views_max IS NULL AND requests ≥ AI_FALLBACK_REQUESTS))`, a due retry (`queued`, `next_attempt_at ≤ NOW()`) or a `fetching` row untouched for 1 h (a crashed tick); at most `AI_DAILY_BUDGET_VIDEOS` `prv_ai_runs` rows in the last 24 h (rolling). Per video: yt-dlp info (a fallback row's `view_count` must reach `AI_MIN_VIEWS` first and is stored in `views_max`; a missing count is logged and stored as 0, so the row waits for views from clients) → ru auto track (none: `queued` again after 6 h / 24 h / 72 h, then `no_track`; a yt-dlp error: after 6 h / 24 h, `failed` with `last_error` after 3 attempts; both count one `attempts`, so an error after two no-track tries fails the video; a yt-dlp that cannot start is the host's fault: no attempt, the row stays `fetching` and is claimed again after 1 h) → VTT collapse → **timeline gate**: last cue end − yt-dlp duration > 3 s → `timeline_unreliable`, nothing published (checked first, so a refused video gets no `videos` row) → the `videos` row by `(native_id, round(yt-dlp duration) ± 2)` (`findByNativeIdAndDuration`'s SQL); when the native_id has rows with a duration and none is within ± 2 → `timeline_unreliable` (yt-dlp sees another cut than the players), else the row without a duration or a new one; other rows off by > 2 s next to a match are logged (`ai: duration variants`, old split families exist). The model call is the eval's held-out configuration (`AI_MODEL`, prompt `AI_PROMPT`, effort `medium`, cue timestamps dropped): `AI_CLIENT=anthropic` submits one Batches API batch per tick (half price; `status = detecting`, then `batch_id`), polls every waiting batch once per tick and fails a video after 24 h without a result; `messages` makes one synchronous call per video; `fixture` reads `<native_id>.detect.json` (as a batch on the cron tick, synchronously in the manual run). The `prv_ai_runs` row is written before the submit (transcript, overrun, yt-dlp duration, prompt sha / version, model), so the budget counts a batch even if the tick dies before storing its id (that video expires instead of being paid for twice); a rejected submit deletes the run rows and counts as a failed fetch. The row gets the raw output, usage and cost (`detector.Price`, × 0.5 for a batch) when the answer comes; a failed call or an invalid answer → `failed`. **Publish**: `sponsor` with confidence ≥ `medium`, `self_promotion` only `high`, bounds rounded inward to whole seconds, then `end − start ≥ 5`; categories mapped to `markup_categories` ids by name; insert into `prv_ai_video_calculateds` (`published_at`), status `published`, also with empty `data` when nothing passes (done, nothing served). One log line per video (`ai detect: <native_id> <status> …`); heartbeat `ai_detect`: `failed_videos` counts only infrastructure failures (DB, API, a yt-dlp that cannot start), not a video's outcome (unavailable, no track, invalid answer, expiry: on its row), and the success needs only the tick's own steps (claim, batch listing, expiry); exit 1 on either. `ai detect <native_id>` is the manual run: ignores the switch, views and budget (claims a row not `fetching` / `detecting` without an AI row, created when missing; a re-detect is refused because votes, verdicts and withdrawals refer to the row), calls the model synchronously, exits 1 unless the video ends `published`, and writes no heartbeat.
- **Serving** (`prv/routes/videos.js`): with `AI_FIRST=on`, the active AI row (`findAiCalculated`) on a `match` / `backfilled` lookup; otherwise, and on `mismatch` / `no_duration` (the player may be on another cut), today's `video_calculateds`. The AI row is keyed by the `videos` row of the yt-dlp duration, so a re-cut video never gets the old cut's segments. Entries have the `video_calculateds.data` shape plus `confidence` and `source: "ai"`, so the extension needs no change. The legacy `!v` branch is human only.
- **`ai judge`** (cron at minute 30, `flock -n /tmp/ai-judge.lock`; off → deletes its heartbeat row): due = published, not withdrawn, non-empty rows already judged or published ≥ 24 h ago, skipped unless there is **new evidence** since its baseline (`signals.New`, stored as `signals.new`): the baseline is `judged_at` or, when every entry's latest ai-item verdict keeps it and came after the last judgement (`keptSince`), the latest such verdict (humans have the last word). New evidence = rows created after the baseline: a user's latest vote on an entry that is down (per user and entry), an undo event, a conflicting human markup; plus re-cuts beyond the `duration_recut` that `prv_ai_videos.judge_counters` recorded (a row becomes a re-cut with a later request, which has no time of its own, and that count only grows). Likes, clicks and agreeing markups never make a video due. A time watermark, not a count comparison: totals shrink (an entry removed on review, a vote changed back) and would hide new evidence, and `POST /vote` keeps the row of a repeated identical vote, so a repeat is never new. Every judgement sets `judged_at` to the tick's start (what the signals were counted up to), so evidence created during the tick counts next time; the tick waits 1 s (`commitSettle`) before its first read, so a write whose `createdAt` (set by Node before its commit) precedes the tick's start has committed and is counted now rather than read as old next time. Node, the Go binary and Postgres share the host clock. Kept with nothing newer → one `ok` by `rules` ("every entry kept on review since the last judgement"), which moves `judged_at` past the verdicts. Signals (`signals.go`, restricted to the AI entries' exact `(category_id, start, end)` where the signal has bounds): `votes_up` / `votes_down` (each user's latest vote on each entry), `undo` (`prv_events_interval_undo`), `clicks`, conflicting human markups (live sponsor / self_promotion markups since publish with IoU < 0.5 to every AI entry of the category, author rating ≥ 0), `duration_variants`, `duration_recut` (a `videos` row off by > 2 s created after publish, with a request for the native_id since); views, requests and age go into `signals` only. Rules first (`rules.go`, on the new evidence): a new re-cut without a new negative → `review` by `rules` (items, the row stays served: anyone can create a `videos` row with any duration, and the row reaches only players of its own cut anyway); no new `votes_down` / `undo` / conflict → `ok` (only a first judgement, whose baseline is the start, gets here); else the LLM, which sees the totals, re-cut or not (a bogus duration never keeps a row from the judge and its withdraw; a new re-cut with new negatives still gets review items whatever the LLM says) (`llm.go`, Messages API, `AI_JUDGE_MODEL`, `ai/prompts/judge-v1.md`, schema `{decision: ok|withdraw|review, reason, segments: [{index, keep}]}`, input: entries with their transcript, counters per 1k views when known, ±60 s windows around entries and conflicting human intervals), not within `AI_JUDGE_MIN_INTERVAL` of the video's last judgement (`judged_at`, set by every judgement, a rules `ok` included; within it `judged_at` stays, so the evidence is still new afterwards). An answer that does not parse or check (one keep per entry, no `ok` with a `keep: false`) → `review` by `rules` with reason `judge_invalid: …` (fail safe toward a human); a transport error fails the video (the next tick retries). An LLM `withdraw` unpublishes (`withdrawn_by = 'judge'`) when `AI_JUDGE_AUTO_WITHDRAW` is on; `withdraw` and `review` (and `judge_invalid`) send one `kind = 'ai'` review item per AI entry (see ReviewItem), except for an entry that already has an ai item without a verdict (same bounds); the other entries still get theirs, so a withdrawn row can always be restored. Each judgement is a `prv_ai_judgements` row written under the AI row's `FOR UPDATE` (a row withdrawn meanwhile is left alone); log `ai judge: <video_id> <decision> <by>: <reason>`; heartbeat `ai_judge` (`failed_videos` = videos that failed, e.g. an API error, retried next tick; the success needs only the due-videos query), exit 1 on either. The judge never closes a case without a human (`docs/backlog/ai-judge-autonomy-flag.md`).
- **Votes** on an AI-first video resolve the segment the way GET serves it; a vote belongs to the interval whatever source served it (owner, 2026-10-22): it rates the authors of a human interval with the same bounds and sets the rating of the AI entry and of that human segment alike, in every state of the AI row (see Routes → `votes.js`). Publish starts each entry with the rating of the votes already on its bounds (`calculator.WithVoteRatings`), read holding the `video_calculateds` row lock that the vote handlers take before the AI row, so no vote on the video commits between that read and the row becoming visible; `calculate --recompute-ratings` (prv) also rewrites every AI row's ratings. **Verdicts** on ai items are applied to the AI row (see Routes → `admin-review.js` → decide). **Admin**: `/admin/video/:video_id` shows the AI row (status, entries, judgements) with a withdraw link (`withdrawn_by = 'admin'`, the operator's per-video switch).
- **Withdraw / restore**: `aiRepository.withdraw(video_id, by, reason)` sets `withdrawn_at/by/reason` (`data` kept for the record) and `prv_ai_videos.status = 'withdrawn'`. Only keep verdicts restore a row, and only one withdrawn by `judge` or `review`; `duration` (timed for the old cut) and `admin` rows stay withdrawn.
- **Prompt**: the default `ai/prompts/v2.2.md` has not been re-scored on held-out (v2.1 passed the gate); that re-score is a precondition of week 1 (`AI_DETECT_ENABLED=on`), see the plan's deploy order.
- Phase 3 (audio drift: re-timing segments of videos whose subtitle track is off) is designed in the plan and waits for the timeline spike on the prod host (`docs/backlog/ai-timeline-phase-3.md`); `prv_ai_timelines` exists with no writer.

### Routes

All three providers share the same route shape; `prv/` also mounts the shared `events.js` / `users.js` and the prv-only admin pages (`admin.js`, `admin-moderation.js`, `admin-review.js`).

- **`markups.js`** — Core markup CRUD. `POST /markup` validates `data.intervals` with `lib/validate-intervals.js` (1–20 items; `start`/`end` finite numbers or numeric strings; after rounding `0 <= start < end <= 86400`; else 400) and creates the markup and all its intervals in one transaction. It rejects users with rating ≤ −2. It also silently returns 201 (no row created) when the user is hard-banned (banned_at IS NOT NULL); see Authentication. `PUT /markups` edits one interval (`new_start` / `new_end` / `new_category_id`): the resulting interval (new values merged with the stored ones) must pass the same `validateIntervals` rules, else 400 with the message as plain text; the interval update and the markup's `is_new = true` are one transaction. Several delete endpoints have both `DELETE` and `GET` variants because Grafana can only trigger GET requests.
- **`votes.js`** — Vote submission. Each new vote runs in one transaction that first row-locks the video's `VideoCalculated` (`lockVideoCalculated` in `lib/segment-rating.js`, which re-reads once when a recalculation replaced the row meanwhile), then its AI row in any state (`lockAiCalculated`, `lib/find-ai-calculated.js`; prv only, none for most videos; this order lets an AI publish, which holds the first lock, read the votes without missing one), so votes on a video, its recalculation, an AI publish and `--recompute-ratings` serialise:
  - the segment must exist in what `GET /video-calculated` serves for the video (exact category/start/end), else 404: with `AI_FIRST=on`, an active AI row and a `duration` on the vote (the write lookup then lands within ±2 s, as GET's `match` / `backfilled`), that row's `data` (a segment only in `video_calculateds` of such a video is 404), else `video_calculateds.data`; the user's previous vote row on the segment is replaced by the new one; the same value again keeps the row and its `createdAt` (the AI judge reads that time as when the user said it) and moves no author rating, but still recomputes the segment ratings below (a repeat repairs a drifted one). **One interval, one vote** (owner, 2026-10-22): a vote belongs to the `(category_id, start, end)` whatever source served it, so everything below happens on both paths
  - `recomputeSegmentRating` (`lib/segment-rating.js`) sets `{provider}_calculated_segments.rating` and the matching `video_calculateds.data` entry (sparse) from the votes table, with the calculator's rule (each user's latest vote, summed); `recomputeAiSegmentRating` sets the AI row's matching entry (no segment rows for AI); both run on every vote, whichever path it took (each skips what does not exist), so an AI entry and a human segment with the same bounds carry the same rating and the AI ratings stay right through a withdraw / restore or an `AI_FIRST` flip
  - the markup authors' user `rating` is adjusted by `vote - prevVote.vote` via `prv/service/user.js` `updateRatingByVote(vote, prevVote, { transaction })` (every author whose live markup has an interval with the exact `(start, end)`; ascending user id, so concurrent votes do not deadlock), an AI-path vote included
  - if the rating mutation drops a user to rating ≤ −100, `prv/service/user.js` also sets `banned_at` and writes a `prv_admin_decisions` row with `decided_by='auto'` (idempotent — only the first crossing writes; the `banned_at == null` guard short-circuits repeat crossings)
  - `GET /votes/:id/delete?verifyBearerToken=…` (Grafana link) undoes the vote: 401 on a wrong token, 404 on an unknown (or concurrently deleted) vote, else one transaction under the same locks (AI row, then `VideoCalculated`) destroys the vote, recomputes the segment rating (table + JSON; skipped when the video has no `VideoCalculated`; also the AI row's entry in any state) and reverses the authors' change with `updateRatingByVote({ ...vote, vote: 0 }, vote, { transaction })`. The voter's own rating is never touched. `201 'Updated'`.
  - `GET /votes/user/:internal_user_id/update-rating?verifyBearerToken=…&rating=N` (Grafana link, e.g. `rating=-100` in `assessors.json`) overrides a user's rating: token first (`middleware/verify-query-token.js`, 401 whatever the params), then `rating` must be an INTEGER-range int (400), unknown user 404, else `201`. Each override is logged to stdout as `Admin rating override { internal_user_id, from, to }` (no table).
- **`videos.js`** — `GET /video-calculated` serves aggregated segments (prv: the AI row instead when AI-first applies, see AI-first segments; optional `views` int 0…2147483647, else 400, recorded in `prv_ai_videos` with every `v` request); prv additionally logs duration claims and tracks legacy client versions. Uses a read-only `findVideoForRead` helper (never creates Video rows): looks up by `(native_id, duration±2)` (tolerance constant in `lib/duration-tolerance.js`), then `(native_id, null duration)` updating it, then any `native_id` match, then 204. The tolerance query is ordered by `ABS(duration - <requested>)`, then `id`, on the read path and in `findByNativeIdAndDuration` (`POST /markup`) alike, so a duration that fits both rows of an old split pair always lands on the same row (the 5 pre-2026-10-19 pairs stay split by decision: `docs/backlog/video-rows-race-and-old-split-families.md`).
- **`prv/routes/events.js`** — `POST /events` (shared by all providers). Accepts a JSON array of mixed events; supported types below. Invalid events (unknown `type`, missing fields) are logged to stdout and skipped — the rest of the batch still processes. Returns `{ data: { time_saved: { ... } } }` when the batch contains at least one `time_saved` event.
  - **`interval_undo`** — fields: `user_id`, `prv_user_id`, `video_native_id`, `category_id`, `start`, `end`. Stored in `{provider}_events_interval_undo`.
  - **`interval_click`** — fields: same as above plus `click_time` (int). Stored in `{provider}_events_interval_click`.
  - **`time_saved`** — fields: `user_id`, `prv_user_id`, `inc`. Increments `User.time_saved`; stored in `{provider}_events_time_saved`. Response mirrors the old `POST /users/time-saved` structure: `by_user_id`, `by_prv_user_id`, `by_user`.
  - **`client_failed`** — fields: `user_id`, `prv_user_id`, `video_native_id`, `reason` (string), `data` (arbitrary JSON, optional). Stored in `{provider}_events_client_failed`.
- **`prv/routes/users.js`** — Shared by all providers (currently empty; `POST /users/time-saved` was removed in favour of the events endpoint).
- **`prv/routes/admin.js`** — Server-rendered HTML dashboard (`/admin/video/:video_id`) for viewing and deleting markups grouped by interval, plus a read-only AI block (the `prv_ai_video_calculateds` row: status, entries, `prv_ai_judgements`); protected by `AUTH_TOKEN` query param. prv only. `GET /admin/video/:video_id/ai/withdraw?verifyBearerToken=…` (numeric `videos.id`, from a confirm button) withdraws the AI row by `admin` (`200 'Withdrawn'`, 404 when there is no published row, 400 on a non-numeric id; an unset `AUTH_TOKEN` refuses every request); no verdict ever restores it.
- **`prv/routes/admin-moderation.js`** — prv-only moderation routes, protected by `AUTH_TOKEN` query param (`?verifyBearerToken=…`).
  - `GET /admin/moderation?verifyBearerToken=…&show=all&format=json` — admin moderation page. Lists worst users + worst markups sorted by suspicion score (`3*dislikes + 1*undos` for users; `+ 3*max(0, -segment_rating)` for markups). Default view hides rows where a prior decision exists and `current_score - snapshot.score < 5` (`RESURFACE_THRESHOLD`). `?show=all` reveals all. `?format=json` returns structured data for tests/integrations.
  - `POST /admin/moderation/decide?verifyBearerToken=…` — body `{target_type:'user'|'markup', target_id, decision:'approve'|'reject'}`. Returns `204`. Side effects: `user`+`reject` sets `users.banned_at=NOW()`; `user`+`approve` clears it; `markup`+`reject` soft-deletes the markup and (if no remaining siblings) destroys `VideoCalculated` else marks siblings `is_new=true`; `markup`+`approve` records the decision only. Writes a row to `prv_admin_decisions` with snapshot and `decided_by='admin'`.
  - `GET /admin/user/:internal_id?verifyBearerToken=…` — video-less per-user view showing all markups across all videos. Param is the internal `users.id` PK, NOT `prv_user_id` (which is not unique — multiple `User` rows can share the same `prv_user_id` because the unique index is composite `(generated_user_id, prv_user_id)`).
- **`prv/routes/admin-review.js`** — prv-only assessor review page (sibling of moderation, same `?verifyBearerToken=…` auth, but an unset `AUTH_TOKEN` refuses every request). One verdict per AI-flagged segment from an imported review sheet (see Ops). Reads/writes only through `prv/repository/review.js`. **Reviewer identity**: every page needs `&reviewer=<code>` (a row of `prv_review_reviewers`); `/admin/review` without it (or with an unknown code) shows the picker, `/admin/review/:batch` without it redirects there (302; `format=json` → 400). All links and POST bodies carry the code on. **Language**: Russian by default (assessors), English switch in the toolbar; `?lang=ru|en` sets the `review_lang` cookie (1 year, path `/admin/review`, httpOnly), and `<html lang>` follows. Every visible string comes from `lib/i18n.js`; only `_html` keys may hold markup (repo-owned files), the rest is escaped; verdict values stay English identifiers in the DB and JSON, only labels are translated; client-side texts go to the inline script in `STATE.i18n`.
  - **First come, one holder** (`prv/repository/review.js`, `STATE`): batches are not assigned. The `prv_review_batches` row holds `reviews_needed`, `excluded` and the lock (`locked_by`, `locked_at`); per batch `finished` = reviewers with a verdict on every item. State for reviewer R, first match wins: `mine` (R holds it), `done` (R ∈ finished), `closed` (R ∈ `excluded`, even while someone holds it), `locked` (another holder), `available` (no holder, R not finished, `|finished| < reviews_needed`; a reviewer who gave up halfway may come back only until then, so their late verdicts never override a complete review in the default export), else `closed`. Only `mine` and `done` may decide (a finisher can still fix their verdicts). **Idle locks expire**: a lock whose holder has saved no verdict in the batch for 12 h (`LOCK_IDLE_HOURS`, counted from the later of `locked_at` and their last verdict there) is cleared by `releaseIdleLocks()`, which the list, item, take/release and decide routes and the importer run first (outside their transaction, `FOR UPDATE SKIP LOCKED`); each release is logged as `Review lock expired { batch, locked_by }`. Verdicts stay; the former holder takes it again like anyone else.
  - `GET /admin/review?reviewer=…&verifyBearerToken=…[&show=all][&format=json]` — batch list in sections In work / Available / Locked by others / Done (`closed` rows only with `show=all`), with state, total and R's decided / open per batch, most recently imported first. JSON: `{reviewer, batches}`, rows `{batch, total, decided, open, reviews_needed, finished: [codes], locked_by, locked_at, state}` (`state` ∈ `mine | available | locked | done | closed`); without a reviewer `{reviewers, reviewer: null}` (400 for an unknown code). The picker has a "create reviewer" form under the name list.
  - `POST /admin/review/reviewers?verifyBearerToken=…` — body `{name}` (form or JSON); the cleaned name (`lib/reviewer-name.js`) is the code. Taken in any letter case (compared in JS under a table lock) → `taken`, bad name → `invalid`. Form: 303 to the new reviewer's batch list, or 400 with the picker, the typed value and the reason; JSON: `201 {code}` or `400 {reason, message}`.
  - `POST /admin/review/:batch/take` / `…/release?verifyBearerToken=…` — body `{reviewer, force?: boolean}`. Take runs under the batch row lock (`withBatchLock()`), then locks the batch when it is available to R (`UPDATE … WHERE` with the availability check), so of two concurrent takes exactly one wins and a take waiting on a final decide or import sees its verdicts (taking your own batch again is a no-op). Without the row lock first, a waiting UPDATE re-checks only `locked_by`, not the verdicts its subquery read, and could lock a completed batch. Release clears the holder's own lock ("Give up"; verdicts stay), or anyone's with `force: true` (the page asks for a confirm naming the holder; covers an assessor who disappeared). `200 {batch, locked_by, locked_at}`, 400 bad input / unknown reviewer, 404 unknown batch, `409 {reason, locked_by, message}` (`reason` = R's state, `message` in the page language).
  - `GET /admin/review/:batch?reviewer=…&verifyBearerToken=…&item=C7&format=json` — item page; without `item` R's first open item by `position`, or the last item when R has decided them all; 404 on unknown batch/item. "Open" and nav `decided` / first open / save → next open count R's verdicts, so a second reviewer starts at C1. A lock banner says R's state with one button: "Take it" (`available`), "Give up" (`mine`), force "Give up" naming the holder (`locked`); verdict controls are disabled unless R may decide. The verdict buttons and comment start from R's own latest verdict (`item.own_verdict`); the "Current verdict" block, history and `flagged_by` show everyone's (a second reviewer is not blind). Shows times in player format (`m:ss` / `h:mm:ss`), the stored `link` from the sheet (already at start − 2 s, used as is; `player_link` is `null` and no link is shown when it is not http(s)), cues, a short "How to decide" rules card (payer test, woven-in calls to action are still self_promotion, unclear only when the text does not decide, track flag is separate), and a signals panel (±30 s, across all `videos` rows of the native_id: live markups with author rating, calculated segments with rating + vote counts, undo/click counts). JSON shape `{reviewer, batch (R's progress row, as in the list), can_decide, item, video_flags: {track_mismatch}, nav: {prev, next, first_open}, signals}`; nav entries are `{item_code, decided, player_link}`. `item.beyond_video_s` is the longest known duration of the native_id's `videos` rows when the item starts after it (the track is from a longer cut, the player opens at 0), else `null`; the page shows it as a yellow warning under the player link. Switching items (`j`/`k`, plain click on ◀/▶/first open, save → next item) also preloads the new item's player behind the review page by swapping tabs: the new item opens in a new tab in front, the current tab navigates to the player (a page can neither open a tab behind itself nor open one on load). Popup blocked or no link → plain navigation, no player. A successful save closes the saved item's player tab (the review tab's `window.opener`, only when cross-origin; a same-origin opener is the batch list). The browser closes only script-opened tabs, so the batch list opens a batch with `window.open`; a player in a tab the reviewer opened stays and the save flash says to close it by hand. A checkbox under the hotkeys line, "After saving, open the next item" (on by default, `adminReview.autoAdvance` = `off` in localStorage when cleared), turns the save → next item switch off: the save reloads the same item and leaves its player tab open. **Verdict** = what the text is (four buttons). **Track flag** (checkbox under the "Extra flags" label with a one-line hint that a flag never replaces the verdict, hotkey `5`): "Subtitle track ≠ video", a per-video fact in `prv_review_video_flags` (`track_mismatch`, append-only, latest wins), shown pre-checked with who set it on every item of that video; independent of the verdict (replaced the pre-2026-10-18 "Wrong text" shortcut, which saved `unclear` with a canned Russian comment; such verdicts are shown as legacy and should be re-decided). Hotkeys: `1`–`4` verdict, `5` flag, `c` comment, `Enter` / Ctrl+Enter save, `j`/`k` next/prev, `o` open player, `Esc` leave a field; letters also work by physical key on a non-Latin (e.g. Russian) layout. The letter keys are one list, `LETTER_HOTKEYS`, read by the key handler (via `STATE.letters`), the hotkeys line and the onboarding table (`hotkeyRows()`), so the help cannot drift. Saving the same verdict and comment the same reviewer already has, with the flag unchanged, is "No change" on the page; the server also never appends a duplicate verdict row for the same reviewer (so a flag-only save writes only the flag), while another reviewer saving the same verdict adds a row.
  - `POST /admin/review/decide?verifyBearerToken=…` — body `{item_id (JSON integer), verdict: 'sponsor'|'self_promotion'|'not_ad'|'unclear', comment? (string or null; trimmed, blank → null), reviewer (registered code), track_mismatch? (boolean)}`. `409 {reason, locked_by, message}` unless R holds the batch or has finished it; the check and every write below run in one transaction with the `prv_review_batches` row locked `FOR UPDATE` (`withBatchLock()`), so a release or take waits for the save. Appends a `prv_review_verdicts` row (`source='page'`) unless identical to the item's latest row by the same reviewer, and a `prv_review_video_flags` row when `track_mismatch` differs from the video's current value; on a `kind = 'ai'` item an appended verdict also goes to `aiRepository.applyVerdict(item, verdict, { transaction })` in the same transaction (lock order batch row → AI row; the judge never adds to a batch someone holds or has a verdict in, so no cycle): `not_ad` / `unclear` remove the entry with the item's `(start, end)` (the row is withdrawn by `review` when none is left), `sponsor` / `self_promotion` keep it with that category or put it back (its `rating` recomputed for the new category); a row withdrawn by `judge` / `review` is served again (`prv_ai_videos.status = 'published'`) once every entry left has a keep verdict as its latest, decided after `withdrawn_at`; idempotent. Returns `201 {item_id, item_code, verdict, track_mismatch, flagged_by, next_item, next_player_link, ai_applied}` (`ai_applied`: the AI row changed; always present, false for sheet items; `next_item` = R's next open item after this one, wrapping round, `null` when R is done); R's verdict on the last open item releases their lock (`releaseIfFinished`), so the batch moves to `done`. `400` on invalid input, unknown reviewer or unknown item.
  - **Onboarding**: a `<details>` block, closed by default, on the batch list and the item page (not on the picker): what this is, workflow (take → item by item → finishes on the last verdict; give up), verdicts, track flag, player window, −2 s start, hotkeys, comments → shared chat. Sections `ONBOARDING_SECTIONS`, keys `onb_<section>_title` / `onb_<section>_html`.
  - **Blind rule**: `flagged_by` (which detector runs flagged the segment) is stripped in the repository from every item without a verdict, so neither HTML nor JSON shows it until the item is decided. On an ai item the decided block also shows an "AI segment" badge and the judge's reason (parsed from the `judge …: <reason>` line of `flagged_by`, keys `ai_badge`, `ai_judge_reason`), so they are blind too.
- **`prv/routes/routes.js`** — Health check (`GET /`) and Prometheus metrics (`GET /metrics`).

### Authentication

- **Admin routes**: `Authorization: Bearer <AUTH_TOKEN>` header (middleware `verify-bearer-token.js`)
- **Admin pages** (`/admin/video`, `/admin/moderation`, `/admin/user`, `/admin/review`): `AUTH_TOKEN` as `?verifyBearerToken=` query param, checked directly in `prv/routes/admin.js`, `admin-moderation.js` and `admin-review.js`. `admin-review.js` and the AI withdraw link also refuse every request when `AUTH_TOKEN` is unset, and its pages send no `Referer` (the token is in the URL).
- **Grafana GET links in `votes.js`** (`/votes/:id/delete`, `/votes/user/:internal_user_id/update-rating`, all providers): the same query param, checked by `middleware/verify-query-token.js` before any validator.
- **API docs** (`/api/doc`): HTTP Basic Auth — username `admin`, password `AUTH_TOKEN` env var
- Public write endpoints (markup creation, votes) are unauthenticated
- `POST /markup` silently returns 201 (no markup row created) when the user's `banned_at IS NOT NULL`, parallel to the existing `rating ≤ -2` soft gate.

**Soft Deletes:** All queries must filter `deleted_at IS NULL`. This is handled in `repository/` — always check there when writing new queries.

**Dual User ID System:** Users have both a `generated_user_id` (UUID) and an optional `prv_user_id`. The codebase is transitioning to internal DB `id` references.

**Schema bootstrap:** project has no migrations folder. New tables come from `sequelize.sync()` (run on every boot in `db.js`); new columns on existing tables are added with idempotent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statements run right after `sync()`. Example: `banned_at` on `users`. Column defaults go the same way (`ALTER TABLE … ALTER COLUMN … SET DEFAULT …`, e.g. the review tables' `created_at` / `decided_at`). The sync, the ALTERs and category seeding live in `lib/schema.js` `syncSchema()`, shared by `bootstrap()` and `scripts/sync-db.js`, so both leave the DB in the same shape — add new ALTERs there. One-offs live there too, guarded so a second boot is a no-op: `migrateBatchAssignees()` (2026-10-20) touches only rows with `prv_review_batches.assignee IS NOT NULL` and, in one transaction, sets `excluded = {bayanovea}` on `gkshi` batches (blind copies of her sheets), locks every free batch whose assignee has not finished it on that assignee (`gkshi` only once started, so untouched overlap batches go to anyone else), then sets `assignee = NULL`. The column is kept (nullable, added `IF NOT EXISTS` on a fresh DB, not in the model) because a pre-2026-10-20 image inserts it on boot, so a rollback still starts; a roll-forward re-migrates only the rows that image assigned. Dropping it: `docs/backlog/drop-review-batch-assignee.md`.

### Prometheus Metrics (`prometheus-wrapper.js`, `server.js`)

Two custom counters, the heartbeat and AI gauges and one HTTP histogram are exposed on `GET /metrics` (served by `server.js`, not by `express-prom-bundle`'s autoregister — `/metrics` is in `excludeRoutes` so it doesn't record itself).

**`video_calculated_lookup_total{outcome, provider, source}`** — outcomes of `GET /video-calculated`. `provider` is `prv` / `rt` / `yt`. `source` is the table served: `ai` (prv `match` / `backfilled` served from `prv_ai_video_calculateds`) or `human` (everything else, `not_found` / `not_calculated` and rt / yt included). `outcome` is one of:

| Outcome | Definition |
|---|---|
| `match` | Request supplied `duration`; row found by `(native_id, duration ± 2)`; `VideoCalculated` row exists. |
| `backfilled` | Request supplied `duration`; no `± 2` match; a row with `duration = NULL` existed and was just updated to the request's duration; `VideoCalculated` row exists. |
| `mismatch` | Request supplied `duration`; no `± 2` match; no `NULL` row to backfill; helper fell through to `findOne({ native_id })` and returned a row whose stored duration differs by > 2 s; `VideoCalculated` row exists. |
| `no_duration` | Request had no `duration` query param (legacy client); helper fell through directly to `findOne({ native_id })`; `VideoCalculated` row exists. |
| `not_calculated` | Helper returned a `Video` (any of the four above) but no `VideoCalculated` row was found; caller overrides the helper's outcome to `not_calculated`. |
| `not_found` | Helper returned `null` (no `Video` row matched at all). |

The first five outcomes are emitted by `lib/find-video-for-read.js`; `not_calculated` is derived in the route handler when `VideoCalculated.findOne` returns null. prv's legacy `!req.query.v` branch in `prv/routes/videos.js` does **not** emit a lookup outcome — it only increments `request_without_version_total`.

**`request_without_version_total{method, provider}`** — count of legacy client requests that omit the `v` query/body param. `method` is the route key (`GET /video-calculated`, `POST /markup`).

**`calculator_last_run_timestamp_seconds{provider}`**, **`calculator_last_success_timestamp_seconds{provider}`**, **`calculator_failed_videos{provider}`** — unix time of the Go calculator's last run / last run with no failed video, and the number of videos that failed in the last run (0 included), from `calculator_heartbeats` (one row per provider, see Calculation Algorithm step 4), read on every scrape by one shared `collect()` callback that `registerCalculatorHeartbeat(sequelize)` in `prometheus-wrapper.js` installs (called from `server.js` after `bootstrap()`, so the module stays DB-free for `test/prometheus-wrapper.test.js`). A provider without a row (or, for the success gauge, with `last_success_at` NULL) has no series; a failing query is logged once and leaves all three gauges empty for that scrape, the rest of `/metrics` is unaffected. The `CalculatorStale` alert watches the success gauge and `CalculatorFailedVideos` the failed-videos one (see Grafana → Alerting). The `ai` command's rows show up as `provider="ai_detect"` / `"ai_judge"`.

**`ai_videos{status}`**, **`ai_cost_usd_total{kind}`** (`detect` = SUM of `prv_ai_runs.cost_usd`, `judge` = of `prv_ai_judgements.cost_usd`), **`ai_cost_usd_24h{kind}`** (the same over rows with `created_at` in the last 24 h; the cost alert and panel read it, not `increase()` of a gauge), **`ai_judgements_total{decision, by}`**, **`ai_review_open`** (ai review items without a verdict) — AI-first state from four plain queries per scrape (one refresh shared by the gauges) (`registerAiMetrics(sequelize)`, registered next to the heartbeat in `server.js`). A failing query is logged once and leaves them empty (`ai_review_open`, label-less, reads 0). Grafana: row "AI" on `infrastructure.json` (videos by status, cost over the last 24 h, judgements per hour by decision, open review items).

**`http_request_duration_seconds_{bucket|count|sum}{method, path, status_code}`** — `express-prom-bundle` histogram with buckets `[0.05, 0.1, 0.25, 0.5, 1, 2.5]`. `path` is normalized via `normalizePath` rules in `server.js` so dynamic segments collapse (`/admin/video/12345` → `/admin/video/#video_id`, `/markups/42` → `/markups/#id`, `/admin/review/<batch>` → `/admin/review/#batch` except `/admin/review/decide` and `/admin/review/reviewers`, `…/<batch>/take|release` → `/admin/review/#batch/take|release`, `/admin/video/<id>/ai/withdraw` → `/admin/video/#video_id/ai/withdraw`, etc.). The default `url-value-parser` catches any unmapped numeric/UUID IDs as defense-in-depth.

**Storage / scrape:** Prometheus scrapes `app:3022/metrics` every 30 s and stores data on the `prometheus_data` named Docker volume (mounted at `/prometheus` in the container; pinned project name `native-ad-skip-api` → stable volume `native-ad-skip-api_prometheus_data`). Retention is bounded by **both** `--storage.tsdb.retention.time=30d` and `--storage.tsdb.retention.size=2GB`; whichever hits first wins, so the volume can never exceed ~2 GB. The size cap exists because the `path` label on `http_request_duration_seconds` is effectively unbounded (unmatched/404 URLs each create their own series), which previously grew the volume to 35 GB. Prometheus does not downsample — reclaiming space means dropping whole 2 h blocks, which it does on startup and every compaction cycle.

**Grafana:** the `grafana` service in `docker-compose.yml` (the old `../native-ad-skip-grafana` repo is superseded). All services attach to the external `main-network` (precondition on the host: `docker network create main-network`). Datasources are provisioned from `grafana/provisioning/datasources/datasources.yml`: Prometheus at `http://prometheus:9090`, Postgres at `${DB_HOST}:5432` (= `host.docker.internal`). Dashboards are provisioned from `grafana/dashboards`; ad-hoc UI edits live only on the `native-ad-skip-api_grafana_data` volume. Data links that call the API's GET admin endpoints (vote/markup delete, update-rating) in `tables.json` and `assessors.json` take the token from a `verifyBearerToken` textbox variable that starts empty: type `AUTH_TOKEN` into it, or open the dashboard with `?var-verifyBearerToken=…`. Never commit a token value into a dashboard. Grafana listens on plain HTTP `:3024` (`http://${HOST_IP}:3024/`), open to the internet by a Timeweb cloud firewall rule and protected only by its login (anonymous access and sign-up disabled). Plain HTTP means the password crosses the network unencrypted, and its Postgres datasource uses the app's read-write `DB_USER`. Docker-published ports bypass host `ufw`; the **Timeweb cloud firewall** is the only filter, so to close Grafana remove the 3024 rule there (or bind it to `127.0.0.1` and use `ssh -L 3024:localhost:3024`).

**Alerting:** provisioned from the repo, folder "native-ad-skip-api", evaluation group `api` every minute, on the Prometheus datasource (`StaleMarkups` on the Postgres one). `grafana/provisioning/alerting/rules.yml` has seven rules; `noDataState: OK` unless said otherwise (a rule removed from the file stays in Grafana and keeps firing until its uid is listed under `deleteRules` there, as `lookup-not-found-share` is since 2026-10-19):
- `CalculatorStale` — age of the last success over the provider's limit, `> 1` for 5 min: `(time() - max by (provider) (calculator_last_success_timestamp_seconds{…}))` divided by 600 for prv/rt/yt, 900 for `ai_detect`, 7200 for `ai_judge` (three selectors joined by `or`); no data at all = the calculator never ran, so `noDataState: Alerting`. A switched-off `ai` command deletes its heartbeat row, so it has no series rather than an aging one.
- `Http5xx` — `sum(increase(http_request_duration_seconds_count{status_code=~"5.."}[5m])) > 5` for 5 min.
- `ApiDown` — `up{job="native-ad-skip-api"}` below 1 for 2 min (queried unfiltered: `up == 0` is empty while healthy); no `up` series = Prometheus is not scraping the app, so `noDataState: Alerting`.
- `HttpLatencyP95` — `histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) > 1` for 5 min (the top bucket is 2.5 s, the quantile saturates there).
- `CalculatorFailedVideos` — `max by (provider) (calculator_failed_videos) > 0` for 3 min (three cron runs); the summary says to look for `Calculate video failed: <video_id>` in `docker logs` (for the `ai` providers: `ai detect:` / `ai judge:` lines). For the `ai` providers a failed video is an infrastructure failure (a video's own outcome is not counted), and one failed tick holds the gauge until the next one (5 min / 1 h): `docs/backlog/ai-detect-failed-videos-alert-window.md`.
- `AiCostDaily` — `sum(ai_cost_usd_24h) > 10` for 5 min: twice the default daily budget (`AI_DAILY_BUDGET_VIDEOS` 200 × $0.025); Grafana cannot read the env, so change the threshold with the budget. `AI_DETECT_ENABLED=off` stops the spend.
- `StaleMarkups` — Postgres: `COUNT(*)` of `markups` with `is_new = true`, `deleted_at IS NULL` and `"updatedAt"` older than 10 min, `> 0` for 5 min (every `is_new = true` writer is a Sequelize update, which bumps `updatedAt`; prv only, rt/yt have no data).

`policies.yml` routes everything to the one contact point `telegram` (group by alertname, `group_wait 30s`, `group_interval 5m`, `repeat_interval 4h`). The contact point is **not** a file in that directory: Compose renders it from the `configs:` block of `docker-compose.yml` into `/etc/grafana/provisioning/alerting/contact-points.yml` (needs Compose 2.23.1+, prod has 2.40.3), with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` from the deploy environment — GitHub Actions secrets, never in the repo. Grafana's own `$VAR` expansion cannot be used for the chat id: Grafana 12.3.1 turns an env var that parses as a number into a YAML number and the Telegram integration requires `chatid` to be a string, so provisioning fails and Grafana refuses to start. **Missing secrets:** with both variables empty Grafana exits 1 at start (`Failed to provision alerting … could not find Bot Token in settings`) and crash-loops under `restart: unless-stopped`; `docker compose up -d` still returns 0, so the deploy job passes and `app` / `prometheus` are unaffected, but Grafana is down until the two secrets exist. Verified locally with Compose 2.40.3 and `grafana/grafana:12.3.1` on 2026-10-18.

Wiring: `docker-compose.yml` passes `AI_FIRST`, `AI_DETECT_ENABLED`, `AI_JUDGE_ENABLED` (`:-off`), `AI_JUDGE_AUTO_WITHDRAW` (`:-on`), `AI_JUDGE_MODEL`, `AI_JUDGE_MIN_INTERVAL`, `AI_MIN_VIEWS`, `AI_DAILY_BUDGET_VIDEOS`, `ANTHROPIC_API_KEY` (empty = code default) to `app`; the deploy workflow fills them from repository variables (`vars.AI_*`) and the `ANTHROPIC_API_KEY` secret. Cron jobs see only `/app/.env`: `infrastructure/init/init_env.sh` appends every `AI_*`, `YTDLP_BIN` and `ANTHROPIC_API_KEY` of the container env there, and `prv/commands/ai/main.go` loads it (variables already set win). A new flag goes into the workflow's two lists (env and the `printf %q` exports) and `docker-compose.yml`; nothing else. The other variables above keep their code defaults on prod.

### Deployment

Prod is a single Timeweb Cloud VM in Almaty, `ala-1` (Ubuntu 24.04, `${HOST_IP}`; Novosibirsk had no capacity), migrated from Yandex Cloud in Oct 2026 — see `docs/plans/completed/20261014-timeweb-migration.md`.

- **CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`), on push to `main` or manual dispatch. A `test` job runs `make test-unit`, `go test -mod=vendor ./calculator ./ai/...` (`TestIntegration` skips when neither `TEST_DB_NAME` nor `DB_USER` is set) and `make test-e2e`; the `deploy` job `needs:` it, so a red test never deploys or pushes an image (one deploy at a time, `concurrency: deploy-prod`). The deploy job builds the image in CI (`docker/build-push-action`, GHA layer cache) and pushes it to GHCR as `ghcr.io/odedohbest/native-ad-skip-api:<commit sha>` and `:latest`, logging in with the job's `GITHUB_TOKEN` (`permissions: packages: write`). It then tars the checkout (without `.git` / `node_modules`) over SSH as `skipper-admin` to `/home/skipper-admin/tmp/codebase.tar.gz`, extracts it into a fresh `/home/skipper-admin/tmp/src/` (the previous checkout moves to `src.old/`, so files deleted from the repo do not linger; prometheus/grafana configs are bind-mounted from there), logs the host into GHCR with the same job token (expires with the job; `docker logout` on exit), and runs `docker compose -p native-ad-skip-api -f …/tmp/src/docker-compose.yml pull app` then `up -d --no-build --force-recreate --remove-orphans app prometheus grafana` with `IMAGE_TAG=<sha>`, under `set -e`. The remote script and its secrets go over stdin to `ssh … 'bash -s'` (`printf %q` exports), not on the remote command line. There is no `down` and nothing is built on the host (`--no-build`: the `app` service keeps `build: .` for local runs): the old stack keeps serving through the pull and stays up if it fails; the API is down only for the container swap. The host key is pinned in the workflow (ed25519, `StrictHostKeyChecking yes`), so a rebuilt VM needs the new key there. Secrets: `HOST_IP`, `SSH_PRIVATE_KEY`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `NODE_APP_PORT`, `AUTH_TOKEN`, `GF_ADMIN_PASSWORD`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (Grafana alerting, see Alerting; without them Grafana does not start), `ANTHROPIC_API_KEY` (the `ai` command; without it a switched-on detect or judge tick exits 1). Repository variables (not secrets): the `AI_*` switches (see Environment Variables; unset = off / code default). The image carries a pinned, sha256-checked static `yt-dlp` release (own Dockerfile stage `ytdlp`, by `TARGETARCH`) at `/usr/local/bin/yt-dlp` and the `ai` binary at `/app/prv/commands/ai/ai`. Supervisor inside the app container manages cron (Go CLI) and the Node.js app.
  - **First deploy with the `src/` layout** (2026-10-18): before it, the compose file and the bind-mounted `config/`, `grafana/` lived directly under `/home/skipper-admin/tmp/`. The stack is addressed by project name (`-p native-ad-skip-api`) and the named volumes keep their names (`native-ad-skip-api_prometheus_data`, `_grafana_data`), so the new compose path recreates the same containers with the new mount paths; the old files directly under `tmp/` (everything except `src/`, `src.old/`) can be deleted by hand after the first successful deploy.
  - **Rollback:** Actions → "Build and Run Docker Image on Timeweb" → Run workflow with `image_tag` = the previous commit sha (any sha CI has pushed; `:latest` stays at the newest build). The job skips the build and deploys that tag, tests included. By hand on the host, as long as the image is still in the local Docker cache (no registry login needed): `IMAGE_TAG=<sha> docker compose -p native-ad-skip-api -f /home/skipper-admin/tmp/src/docker-compose.yml up -d --no-build app`. Back to a pre-AI image: delete the AI heartbeat rows it no longer writes, or `CalculatorStale` fires for them: `DELETE FROM calculator_heartbeats WHERE provider LIKE 'ai_%';` (host Postgres, app role).
  - **GHCR visibility** follows the repo: the repo is private, so the package is private and the job token is the only login the host ever uses. A manual `docker pull` on the host would need a PAT with `read:packages` (`docker login ghcr.io`), and `docker logout ghcr.io` afterwards.
- **DNS:** reg.ru, zone `${DNS_ZONE}` on reg.ru's free NS; A records `api`, `www.api`, `test-api`, `adskip`, `www.adskip` → `${HOST_IP}`, zone TTL 1h (panel minimum). `api` (this repo's vhost) and the landing `adskip` (static Vue build in `/var/www/landing`, `www` redirects to it) have vhosts and certs; the landing's vhost `/etc/nginx/sites-available/landing.conf` is not in this repo.
- **TLS / reverse proxy:** nginx on the host terminates TLS for `${API_HOST}` (Let's Encrypt, certbot webroot renewals) and proxies to `127.0.0.1:3022`. The vhost is versioned in `infrastructure/nginx/` and copied to the host by hand; its access log uses the `redacted` format (`redacted-log-format.conf` in `conf.d/`: no query string, no referer), so `?verifyBearerToken=` is not logged. `.dev` is HSTS-preloaded, so the API is HTTPS-only.
- **Postgres:** PostgreSQL 16 installed on the host via apt, not in Docker. Containers reach it at `host.docker.internal` (`extra_hosts: host-gateway`); `pg_hba` + `ufw` allow only `172.16.0.0/12` (Docker bridges) and localhost, so 5432 is never public.
- **Backups:** Timeweb VM auto-backups (daily, keep 7) plus `make pull-dump` (`scripts/pull-prod-dump.sh`), which streams a gzipped `pg_dump --no-owner` over SSH to `~/Web/dumps/adskip-prod/` on the owner's Mac (`latest.sql.gz` symlink) — run weekly. The nightly S3 job (`infrastructure/backup/pg-backup.sh`, restore drill in its README) is written but **not installed yet**: `docs/backlog/offhost-pg-backup-s3.md`.
