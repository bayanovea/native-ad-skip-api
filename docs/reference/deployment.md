# Deployment

Moved out of CLAUDE.md on 2026-11-04 (instruction-size limit); CLAUDE.md keeps a summary with the
invariants. A "see X" names a section of CLAUDE.md or of another file in `docs/reference/`.

Prod is a single Timeweb Cloud VM in Almaty, `ala-1` (Ubuntu 24.04, `${HOST_IP}`; Novosibirsk had no capacity), migrated from Yandex Cloud in Oct 2026 — see `docs/plans/completed/20261014-timeweb-migration.md`.

- **CI/CD:** GitHub Actions (`.github/workflows/deploy.yml`), on push to `main` or manual dispatch. A `test` job runs `make test-unit`, `go test -mod=vendor ./calculator ./ai/...` (`TestIntegration` skips unless `TEST_DB_NAME` is set) and `make test-e2e`; the `deploy` job `needs:` it, so a red test never deploys or pushes an image (one deploy at a time, `concurrency: deploy-prod`). The deploy job builds the image in CI (`docker/build-push-action`, GHA layer cache) and pushes it to GHCR as `ghcr.io/bayanovea/native-ad-skip-api:<commit sha>` and `:latest`, logging in with the job's `GITHUB_TOKEN` (`permissions: packages: write`). It then tars the checkout (without `.git` / `node_modules`) over SSH as `skipper-admin` to `/home/skipper-admin/tmp/codebase.tar.gz`, extracts it into a fresh `/home/skipper-admin/tmp/src/` (the previous checkout moves to `src.old/`, so files deleted from the repo do not linger; prometheus/grafana configs are bind-mounted from there), logs the host into GHCR with the same job token (expires with the job; `docker logout` on exit), renders the placeholders of the bind-mounted files (see Render below), and runs `docker compose -p "$COMPOSE_PROJECT" -f …/tmp/src/docker-compose.yml pull app` then `up -d --no-build --force-recreate --remove-orphans app prometheus grafana node-exporter blackbox-exporter` with `IMAGE_TAG=<sha>`, under `set -e` (`up` pulls the exporters' pinned Docker Hub images when missing). After a successful `up` it removes old `ghcr.io/bayanovea/native-ad-skip-api` images (and that repository's `<none>` ones): it keeps the `KEEP_IMAGES` = 5 newest by creation time plus the deployed `IMAGE_TAG`, removes the rest by `repo:tag` (never another repository, never a prune), ignores a failed `rm` (image in use) and logs two `Image cleanup:` lines. The remote script and its secrets go over stdin to `ssh … 'bash -s'` (`printf %q` exports), not on the remote command line. There is no `down` and nothing is built on the host (`--no-build`: the `app` service keeps `build: .` for local runs): the old stack keeps serving through the pull and stays up if it fails; the API is down only for the container swap. The host key is pinned (`SSH_HOST_KEY` into `known_hosts`, `StrictHostKeyChecking yes`), so a rebuilt VM needs the new key in that secret. Secrets: `HOST_IP`, `SSH_PRIVATE_KEY`, `SSH_HOST_KEY` (the host's public key line, `ssh-ed25519 AAAA…`; `ssh-keyscan -t ed25519 <ip>` on a machine that trusts it), `API_HOST`, `LANDING_HOST` (the two public host names), `PROVIDER_VIDEO_URL`, `PROVIDER_LINK_AT`, `LEGACY_PRV` (the video platform, see Environment Variables), `COMPOSE_PROJECT` (the compose stack name, see below), `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `NODE_APP_PORT`, `AUTH_TOKEN`, `GF_ADMIN_PASSWORD`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (Grafana alerting, see Alerting; without them Grafana does not start; also passed to `app` for the `ai audit` ping), `ANTHROPIC_API_KEY` (the `ai` command; without it a switched-on detect or judge tick exits 1), `OPENAI_API_KEY` (the second opinion; without it a detect tick with `AI_SECOND_ENABLED=on` exits 1). Repository variables (not secrets): the `AI_*` switches (see Environment Variables; unset = off / code default). The image carries a pinned, sha256-checked static `yt-dlp` release (own Dockerfile stage `ytdlp`, by `TARGETARCH`) at `/usr/local/bin/yt-dlp` and the `ai` binary at `/app/prv/commands/ai/ai`. Supervisor inside the app container manages cron (Go CLI) and the Node.js app.
  - **Compose project name** (`COMPOSE_PROJECT`, a secret; empty = `native-ad-skip-api`): the stack, its containers (`<project>-app-1`, `<project>-grafana-1`, …) and its named volumes (`<project>_prometheus_data`, `<project>_grafana_data`) are addressed by it (`docker compose -p "$COMPOSE_PROJECT"` in the deploy script and in every command here). Prod sets it to the name the stack was created with (the repo's old name), so the containers and the volumes are kept; an empty variable would start a second stack next to the old one and fail on the published ports. Change it only together with a rename of the volumes on the host.
  - **Render** (deploy script, after the checkout is extracted into `tmp/src/`): the repo names no host and no video platform, so `config/prometheus.yml` (the blackbox targets) and `grafana/dashboards/*.json` (admin links, platform links) carry `${API_HOST}`, `${LANDING_HOST}` and `${PROVIDER_VIDEO_URL}` placeholders, filled on the host with `sed` from the `printf %q` exports (empty value or a placeholder left = the deploy fails before `pull`). `${PROVIDER_VIDEO_URL}` is the template with `{id}`: in a data link `{id}` becomes `${__data.fields.native_id}` (Grafana's own syntax, which stays), in a SQL concatenation (`'${PROVIDER_VIDEO_URL}' || videos.native_id`, `assessors.json`) the placeholder becomes the template's prefix before `{id}`, so the template must end with `{id}` (checked). The dev stack (`docker-compose.dev.yml`, `config/prometheus.dev.yml`) has no probes and needs no render; `infrastructure/nginx/api.conf` is installed by hand through the same kind of `sed` (its README).
  - **First deploy with the `src/` layout** (2026-10-18): before it, the compose file and the bind-mounted `config/`, `grafana/` lived directly under `/home/skipper-admin/tmp/`. The stack is addressed by project name and the named volumes keep their names, so the new compose path recreates the same containers with the new mount paths; the old files directly under `tmp/` (everything except `src/`, `src.old/`) can be deleted by hand after the first successful deploy.
  - **Rollback:** Actions → "Build and Run Docker Image on Timeweb" → Run workflow with `image_tag` = the previous commit sha (any sha CI has pushed; `:latest` stays at the newest build). The job skips the build and deploys that tag, tests included. By hand on the host, only for the 5 newest shas (the deploy removes older images from the local cache; no registry login needed): `IMAGE_TAG=<sha> docker compose -p <project> -f /home/skipper-admin/tmp/src/docker-compose.yml up -d --no-build app` (`<project>` = `COMPOSE_PROJECT`). Back to a pre-AI image (or one before `ai audit`, whose crontab lacks the audit line; `prv_review_audits` stays, unread): delete the AI heartbeat rows it no longer writes, or `CalculatorStale` fires for them: `DELETE FROM calculator_heartbeats WHERE provider LIKE 'ai_%';` (host Postgres, app role). An image older than 2026-10-29 cannot start on the renamed tables (its `sync()` would create a second, empty set under the earlier names and every query would hit them): stop the app, rename the DB back with `scripts/rename-to-legacy.js <legacy>` (`<legacy>` = `LEGACY_PRV`) in a one-off container of the image that just stopped, with that container's env (no `.env` on the host, so `docker compose run` would get no DB settings), then start the old image as above (bash, as root on the host):
    ```bash
    docker stop <project>-app-1
    docker run --rm --network main-network \
      --add-host host.docker.internal:host-gateway \
      --env-file <(docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' \
        <project>-app-1) \
      "$(docker inspect -f '{{.Config.Image}}' <project>-app-1)" \
      node scripts/rename-to-legacy.js <legacy>
    ```
    Tables created after the rename get the earlier prefix too; the old image ignores them. A later deploy of a current image renames everything forward on boot (`LEGACY_PRV` set), so a roll-forward needs nothing extra.
  - **Repo transfer** (2026-10-29: `odedohbest/native-ad-skip-api` → `bayanovea/native-ad-skip-api`): images up to the transfer are `ghcr.io/odedohbest/native-ad-skip-api:<sha>`, a package of the old account that the job token cannot pull, and the deploy's image cleanup never touches them. A rollback to a pre-transfer sha is by hand on the host while that image is still in its cache: `docker tag ghcr.io/odedohbest/native-ad-skip-api:<sha> ghcr.io/bayanovea/native-ad-skip-api:<sha>`, then the `up -d --no-build app` above. Remove the old-path images by hand once rolling back that far is no longer wanted.
  - **GHCR visibility** follows the repo: the repo is private, so the package is private and the job token is the only login the host ever uses. A manual `docker pull` on the host would need a PAT with `read:packages` (`docker login ghcr.io`), and `docker logout ghcr.io` afterwards.
- **DNS:** the API host (`API_HOST`) and the landing host (`LANDING_HOST`) live in the zone `${DNS_ZONE}` on the registrar's NS, A records (with their `www.` twins and a test host) → `${HOST_IP}`, zone TTL 1h (the panel's minimum); the repo names no record. Both have vhosts and certs on the host; the landing (a static Vue build in `/var/www/landing`, `www` redirects to it) and its vhost `/etc/nginx/sites-available/landing.conf` are not in this repo.
- **TLS / reverse proxy:** nginx on the host terminates TLS for the API host (Let's Encrypt, certbot webroot renewals) and proxies to `127.0.0.1:3022`. The vhost is versioned in `infrastructure/nginx/` with `${API_HOST}` placeholders and installed by hand through `sed` (its README); its access log uses the `redacted` format (`redacted-log-format.conf` in `conf.d/`: no query string, no referer), so `?verifyBearerToken=` is not logged. The zone's TLD is HSTS-preloaded, so the API is HTTPS-only.
- **Postgres:** PostgreSQL 16 installed on the host via apt, not in Docker. Containers reach it at `host.docker.internal` (`extra_hosts: host-gateway`); `pg_hba` + `ufw` allow only `172.16.0.0/12` (Docker bridges) and localhost, so 5432 is never public.
- **Backups:** Timeweb VM auto-backups (daily, keep 7) plus `make pull-dump` (`scripts/pull-prod-dump.sh`; `PROD_HOST=user@host` and `DB_NAME` required, from the owner's shell env, no defaults in the repo), which streams a gzipped `pg_dump --no-owner` over SSH to `~/Web/dumps/native-ad-skip-prod/` (`DUMP_DIR`) on the owner's Mac (`latest.sql.gz` symlink) — run weekly. The nightly S3 job (`infrastructure/backup/pg-backup.sh`, `DB_NAME` and `BUCKET` required, restore drill in its README) is written but **not installed yet**: `docs/backlog/offhost-pg-backup-s3.md`.
