# AI-first segments (prv: `ai/`, `prv/commands/ai`)

Moved out of CLAUDE.md on 2026-11-04 (instruction-size limit); CLAUDE.md keeps a summary with the
invariants. A "see X" names a section of CLAUDE.md or of another file in `docs/reference/`.

This section is the source of truth for the AI-first flow; `openspec/specs/` holds only what OpenSpec changes put there (today the detect queue, verdict absorb, the admin review request, the second opinion and the chapter check), and `docs/plans/completed/20261104-ai-flow-audit.md` records the 2026-11-04 walk of every state against every writer. Plans with the decisions and trade-offs: `docs/plans/completed/20261022-ai-first-segments.md`, `docs/plans/completed/20261027-ai-hidden-entries.md` (every detected segment kept, `data` / `hidden`). Non-technical overview for the frontend developer and the assessors: `docs/ai-first-overview/{ru,en}.html` (shared `style.css`), published as two private claude.ai artifacts (ru `6NZNwDcYKbLV5MUgKPwc8n`, en `SQhQy8xEPoY8XaxvKL4d6o`; each page's header links the other). **Keep it current**: a change to what this section describes at the conceptual level (what is served when, the gates, the judge's decisions, what a verdict does, the switches) updates both languages and the "updated" date in their header in the same change, then republishes both artifacts from the repo files (single file each: `style.css` inlined, the cross-language link pointing at the other artifact). Owner's rule: only segments we are sure the viewer sees correctly, even at the cost of missed ads. Every switch defaults off in code and `docker-compose.yml`; turning AI-first on is only ever the owner's env change (see Environment Variables), never a code default or a migration. Human markups keep being accepted on AI-first videos: they are the judge's strongest signal and the fallback when the AI row is withdrawn.

- **Trigger** (`prv_ai_videos`, one row per native_id): `GET /video-calculated` with `v` upserts it once the response is sent (`aiRepository.seen()` on `res.once('finish')`, 204 included; errors logged, never returned): `views_max = GREATEST(…)` from the count read out of the optional `views_text` param (the page's counter as text, `39,4 тыс просмотров` / `1.7M views`, parsed by `lib/parse-views-text.js`: first number + `тыс` / `млн` / `млрд` / `K` / `M` / `B`, thousands groups, a doubtful string → null, so a request without a readable counter never lowers or clears the max; never a 400, cut to 128 chars; the numeric `views` param is gone since 2026-10-26, now an ignored unknown param), `views_text` = the latest string sent, readable or not (a new page format shows as rows with a text and no `views_max`), `requests + 1`, `last_seen_at`; only prv video ids (`^-?\d+_\d+$`) are recorded; a user's own upload (no leading `-`, `111_222`) is recorded too but never taken by the tick, only community videos (`-111_222`) are (see `ai detect`). `status` (`seen` | `queued` | `fetching` | `detecting` | `published` | `withdrawn` | `no_track` | `timeline_unreliable` | `failed`) is moved by the detector, by a withdraw (`withdrawn`) and by a restore (`published`). The extension release that sends `views_text` is out since 2026-10-28; old versions never send it, so their videos reach the detector by `requests` alone (`docs/backlog/ai-views-from-clients.md`).
- **`ai detect`** (cron `*/5`, `flock -n /tmp/ai-detect.lock`; with `AI_DETECT_ENABLED` off a tick only expires runs older than 24 h and deletes its heartbeat row): claims up to `AI_BATCH_MAX` rows (default 5), highest score first: `ln(views_max / AI_MIN_VIEWS + requests / AI_MIN_REQUESTS + 1) / (1 + days since first_seen_at)` (a NULL `views_max` counts 0; the admission terms are the value terms, so 20 requests weigh as much as `AI_MIN_VIEWS` views; age divides, so an undrained low band sinks instead of waiting its turn) × 1.5 when the channel's (the owner part of the native id) latest AI row serves an entry, × 0.5 when the channel has ≥ 2 AI rows and none serves one, × 0.3 when any `videos` row of the native id has a live `sponsor` / `self_promotion` markup (the human path serves those viewers already); ties by `first_seen_at`, `native_id`; due retries and stale `fetching` rows sort by the same score (computed in the claim's `ORDER BY`, the channel factor a CTE over `prv_ai_video_calculateds`, the markup factor an `EXISTS` on `videos (native_id)`, indexed in `lib/schema.js`). A `seen` video first requested more than 14 days ago is no longer eligible (`queueMaxAge` in `ai/pipeline/queue.go`, a code constant, no switch; a later request does not revive it; the manual run still takes it; the dashboard's queue stat and funnel apply the same cut, literal tagged `/* queue.go queueMaxAge */`). The claim (`FOR UPDATE SKIP LOCKED`, held for the claim only, so the read path's upsert never waits on yt-dlp) takes only community videos (`native_id ~ communityIDRegex` = `^-[0-9]+_[0-9]+$`, `queueRule` in `ai/pipeline/queue.go`, over every branch below, so a user upload is never claimed in any state, whatever its views / requests; `nativeIDRegex` `^-?…` stays the read path's and the manual run's): `status = 'seen' AND (views_max ≥ AI_MIN_VIEWS OR requests ≥ AI_MIN_REQUESTS)` (two independent criteria, a NULL `views_max` just fails the first; the claim sets `queued_by` once, `views` / `requests` / `both` by the row's values against that tick's thresholds, kept over retries and stale re-claims, NULL for rows claimed before 2026-10-28), a due retry (`queued`, `next_attempt_at ≤ NOW()`) or a `fetching` row untouched for 1 h (a crashed tick); at most `AI_DAILY_BUDGET_VIDEOS` `prv_ai_runs` rows in the last 24 h (rolling). Per video, after a pause of `AI_FETCH_PAUSE` ± 50 % (default 40 s → 20–60 s; none in the manual run), so prv sees the host's fetches spread out rather than as a burst at the cron minute (a ban would hit the shared prod IP; the API itself never calls prv): yt-dlp info at `PROVIDER_VIDEO_URL` with `{id}` = the native id (its `view_count` is never read: `views_max` comes from clients' `views_text` only; prv's info has none anyway, `null` on every video, 2026-10-24) → ru auto track (none: `queued` again after 6 h / 24 h / 72 h, then `no_track`; a yt-dlp error: after 6 h / 24 h, `failed` with `last_error` after 3 attempts; both count one `attempts`, so an error after two no-track tries fails the video; a yt-dlp that cannot start is the host's fault: no attempt, the row stays `fetching` and is claimed again after 1 h; so is a cron tick whose every fetch (≥ 2) failed while the info of the latest `published` video fails too (`hostFetches`; when that control fetches, the errors are the videos' and spend attempts as usual: a quiet tick of only broken videos once looped `fetching` and alerted hourly): prv refusing the host, logged `ai detect: every fetch of the tick failed (N videos)`, those N count as failed videos, so `CalculatorFailedVideos` fires within a tick instead of the rows reaching `failed` after ~30 h) → VTT collapse → **timeline gate**: last cue end − yt-dlp duration > 3 s → `timeline_unreliable`, nothing published (checked first, so a refused video gets no `videos` row) → the `videos` row by `(native_id, round(yt-dlp duration) ± 2)` (`findByNativeIdAndDuration`'s SQL); when the native_id has rows with a duration and none is within ± 2 → `timeline_unreliable` (yt-dlp sees another cut than the players), else the row without a duration or a new one; other rows off by > 2 s next to a match are logged (`ai detect: duration variants`, old split families exist). The model call is the eval's held-out configuration (`AI_MODEL`, prompt `AI_PROMPT`, effort `medium`, cue timestamps dropped); the transport is `AI_DETECT_CLIENT`, empty → `AI_CLIENT` (shared with the judge and the audit, which take Anthropic values only; the fallback keeps an env with only `AI_CLIENT=fixture` off paid APIs) → `anthropic`. `anthropic` submits one Claude Batches API batch per tick (half price; `status = detecting`, then `batch_id`), polls every waiting batch once per tick and fails a video after 24 h without a result; `openai-batch` does the same through the OpenAI Batch API (`detector.OpenAIBatch`: a JSONL file uploaded, a batch with a 24 h window, the output and error files read by `custom_id`; needs a key with the Files and Batches permissions); `messages` (Claude) and `openai` (Chat Completions) make one synchronous call per video; `fixture` reads `<native_id>.detect.json` (as a batch on the cron tick, synchronously in the manual run, which calls `anthropic` / `openai-batch` synchronously too). A model id starting with `claude-` is Anthropic's, any other OpenAI's: a model of the other vendor (`AI_MODEL` against the transport; with the switch on, `AI_SECOND_MODEL` against `AI_SECOND_CLIENT`), an unknown `AI_DETECT_CLIENT` or a missing key (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY`) is a startup error of a tick that would call the model (exit 1, nothing claimed); `fixture` takes any model. Each waiting batch is polled and read through the vendor of the model on its videos' latest run, not the current transport, and priced at that model's price × 0.5, so a swap or rollback of the variables with batches in flight publishes them unchanged; the other vendor's client is built on first use (its key missing: that batch's videos count as failed for the tick, as a poll error). An OpenAI batch failed as a whole (validation, the organization's limit on enqueued tokens, reported only when polled) is handled as a rejected submit below. The `prv_ai_runs` row is written before the submit (transcript, overrun, yt-dlp duration, prompt sha / version, model, the info's `chapters` whatever the chapter switch says), so the budget counts a batch even if the tick dies before storing its id (that video expires instead of being paid for twice); a rejected submit (any error: nothing was sent, e.g. the API usage limit) deletes the run rows and queues the videos again in 1 h with `last_error` `batch submit: …`, no attempt spent; they count as failed videos of the tick. A synchronous call (`messages`, the manual run) that returns no answer (an error with zero usage: quota, 429, 5xx) is treated the same way (`last_error` `detect call: …`); an answer that came back unusable (`max_tokens`, a refusal, a parse failure: paid for) still fails the video. The row gets the raw output, usage and cost (`detector.Price`, × 0.5 for a batch) when the answer comes; a failed batch result or an invalid answer → `failed`. **Publish**: every segment is kept, bounds rounded inward to whole seconds (a span with no whole second inside is dropped), categories mapped to `markup_categories` ids by name; `data` (served) = `sponsor` with confidence ≥ `medium`, `self_promotion` only `high` (`accepted()`), and `end − start ≥ AI_MIN_SEGMENT_SECONDS` (default 5); the rest goes to `hidden` with `reason` `confidence` (below `accepted()`, checked first), `short`, or `unconfirmed` (the second opinion below, checked last, so only a segment the rules would serve gets it); then, with `AI_CHAPTERS_ENABLED`, the chapter check (below) on the served entries; insert into `prv_ai_video_calculateds` (`published_at`), status `published`, also with empty `data` when nothing passes (done, nothing served). One log line per video (`ai detect: <native_id> <status> …`, publish: `… published: N served, M hidden of K segments`, with the second opinion `M hidden (U unconfirmed by <model>, $c)` or `(second opinion of <model> failed: served unconfirmed)`, with the chapter check `… of K segments, C on chapters, R to chapter review`); heartbeat `ai_detect`: `failed_videos` counts only infrastructure failures (DB, API, a yt-dlp that cannot start), not a video's outcome (unavailable, no track, invalid answer, expiry: on its row), and the success needs only the tick's own steps (claim, batch listing, expiry); exit 1 on either. `ai detect <native_id>` is the manual run: ignores the switch, the views / requests thresholds, the community-only rule (takes a user upload) and the budget (claims a row not `fetching` / `detecting` without an AI row, created when missing; a `fetching` row untouched for 1 h, left by an interrupted run, is claimed again, as by the queue, so it never waits for a cron that may be off; a re-detect is refused because votes, verdicts and withdrawals refer to the row; `queued_by = 'manual'` on a first claim), calls the model synchronously, exits 1 unless the video ends `published`, and writes no heartbeat.
- **Serving** (`prv/routes/videos.js`): with `AI_FIRST=on`, the active AI row (`findAiCalculated`) on a `match` / `backfilled` lookup; otherwise, and on `mismatch` / `no_duration` (the player may be on another cut), today's `video_calculateds`. The AI row is keyed by the `videos` row of the yt-dlp duration, so a re-cut video never gets the old cut's segments. Entries have the `video_calculateds.data` shape plus `confidence` and `source` (`ai`, `chapter` or `review`), so the extension needs no change. The legacy `!v` branch is human only.
- **Served vs hidden** (owner, 2026-10-27): an AI row keeps every detected segment; `data` is exactly what is served, `hidden` the rest with a `reason`. Two layers, both precomputed (publish, `applyVerdict`, `ai regate`), nothing evaluated on the read path: the *truth* = the model's answer above `accepted()`'s confidence thresholds, overridden by the latest ai-item verdict (a keep pins the entry against the thresholds; `not_ad` / `unclear` → `review`, never back by a rule, only by a later keep); the *serving filter* = the length rule (`AI_MIN_SEGMENT_SECONDS`) on every entry, verdict or not. A rule change is an `ai regate` run (see Ops), never a read-time filter. Everything that reads `data` (serving, votes, `--recompute-ratings`, the judge, restore) ignores `hidden`, whose entries carry no rating; a hidden entry reaches viewers only by a rule change or a keep verdict (below-threshold items, see Ops).
- **Second opinion** (`ai/pipeline/confirm.go`, owner 2026-10-30, change `openspec/changes/archive/2026-11-04-ai-second-detector-openai/`, spec `openspec/specs/ai-second-opinion/`; switch `AI_SECOND_ENABLED` (`off` by default), transport `AI_SECOND_CLIENT` (`openai` by default | `anthropic` | `fixture`), model `AI_SECOND_MODEL` default `gpt-6-luna` (owner, 2026-10-30: ~$0.006 per video, the $100/month budget; revisit: `docs/backlog/ai-second-model-revisit.md`; the planned pair is `claude-haiku-5-5` on `anthropic`, change `openspec/changes/ai-detector-roles-swap/`), key `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`): after the detector's answer validates, one synchronous call to the second model with the same prompt, transcript rendering and schema (`detector.OpenAI`, Chat Completions, strict JSON schema; or `detector.NewAnthropic`, Messages, which sends no `effort` to a model id containing `haiku` (Haiku 5.5 defaults to `medium`); effort `medium`), on the cron tick (after the batch result) and in the manual run, before `finish()` takes the queue row's lock. A segment that would be served stays in `data` only when a second-model segment of the same category overlaps it with IoU ≥ 0.3 (`confirmIoU`, owner 2026-10-31: "the same ad", not "the same edges"; the served bounds are the first model's), else it goes to `hidden` as `unconfirmed` and gets one ai review item (sheet `ai-second-<YYYY-MM-DD>` UTC, codes `D<n>`, priority `important`, `flagged_by` `["second <model>: not found", "entry: <category> <confidence>, <len> s"]`) while the day's sheet holds fewer than 30 (`secondReviewDaily`, owner 2026-11-05: the assessors' capacity; Haiku leaves ~0.73 entries a video unconfirmed against luna's ~0.14); past the cap the entry stays hidden with no item (logged `… N unconfirmed past the day's 30 review items`), the confirmation row still counts it, so a keep serves it and `not_ad` / `unclear` hide it as `review`, as on any ai item; `ai regate` never serves it by a rule. Second-model segments matching none of the first's become no entries: counted as `extra`. A failed second call (API error, an answer that fails `detector.Validate`) publishes exactly as without the switch, logs `ai detect: <native_id> second opinion failed: …` and is no failed video of the tick; a first answer that failed gets no second call; `AI_SECOND_ENABLED=on` with the `openai` transport and no `OPENAI_API_KEY` is a startup error (exit 1). One `prv_ai_confirmations` row per call, in the publish transaction. Rows published before the switch are not re-checked. Agreement on the gold: `adskip agree FIRST_RUN SECOND_RUN` in the eval repo (confirmed / vetoed, true ads and wrong cuts vetoed, at IoU 0.3 / 0.5 / 0.7).
- **Chapters** (`ai/pipeline/chapters.go`, owner 2026-11-02, change `openspec/changes/archive/2026-11-04-ai-chapter-bounds/`, spec `openspec/specs/ai-chapter-bounds/`; switch `AI_CHAPTERS_ENABLED` (`off` by default), edge `AI_CHAPTER_EDGE_SECONDS` (default 10, int ≥ 1)): the video's own chapters (description timecodes, which yt-dlp's info reports as `chapters` exactly when the description has them; read from the raw info JSON in product code, `ai/ytdlp` is an eval copy) are stored on every run (`prv_ai_runs.chapters`, `[]` = none, NULL = before 2026-11-02 or an info that did not parse). With the switch on, after `entries()` (confidence, length, second opinion) and before publish, by time only, no model call: a served entry that a chapter overlaps with both edges within the edge seconds is served at the chapter's bounds (inward to whole seconds, `source: "chapter"`, category and confidence kept, rating from the votes on those bounds; the title is not read: the models already called it an ad), unless they are shorter than `AI_MIN_SEGMENT_SECONDS` or overlap another served entry; of several, the smallest total edge distance. Else a chapter with one edge near, the other further and a title matching `adTitle` (`реклам|интеграц|спонсор|партн[её]р|промокод|скидк|erid|…`; it also hits news about ads, so it only decides whether an assessor looks) leaves the AI bounds and sends the entry one ai review item (sheet `ai-chapter-<YYYY-MM-DD>` UTC, codes `T<n>`, priority `important`, `flagged_by` `["chapter: «<title>» m:ss–m:ss (start N s off, end M s off)", "entry: <category> <confidence>, <len> s"]`), in the publish transaction after the AI row and the second opinion's `D` items (lock order: queue row → `video_calculateds` → batch row). A chapter never creates an entry or touches `hidden`. Why (owner): in the player check the agreeing chapters were exact 2 of 3 (visual ad parts with no words included), the third ran 16:48–25:05 for an ad ending 18:03, so a chapter alone is never trusted; on 99 prod rows (2026-10-28) the rule moves 10 entries on 5 videos and sends 3 items (time-only, without the title check, it sent 19, mostly topic chapters sharing an edge with the ad). New publications only (`docs/backlog/ai-chapters-backfill-published-rows.md`); an ad chapter no entry overlaps is counted on the dashboard (`docs/backlog/ai-ad-chapters-without-ai-entry.md`). The review page lists the run's chapters on every ai item (see Routes → `admin-review.js`).
- **`ai judge`** (cron at minute 30, `flock -n /tmp/ai-judge.lock`; off → deletes its heartbeat row): due = published, not withdrawn, non-empty rows already judged or published ≥ 24 h ago, skipped unless there is **new evidence** since its baseline (`signals.New`, stored as `signals.new`): the baseline is per entry: `judged_at` or, when the entry's latest ai-item verdict keeps it and came after the last judgement (`entryKeeps`; an item matches the entry at its effective bounds, see Votes / Verdicts below), that verdict (humans have the last word on what they saw); a conflicting markup belongs to no entry and takes the earliest of the entries' baselines. New evidence = rows created after the baseline: a user's latest vote on an entry that is down (per user and entry), an undo event, a conflicting human markup (dated by `GREATEST(markups."createdAt", markup_time_intervals."updatedAt")`: `PUT /markups` edits an interval in place and always touches it, on a category change every live interval of the markup (the category lives on `markups`), while `markups."updatedAt"` moves on every recalculation; an author's rating crossing 0 is not dated, such a markup becomes new evidence only with a later edit); plus re-cuts beyond the `duration_recut` that `prv_ai_videos.judge_counters` recorded (a row becomes a re-cut with a later request, which has no time of its own, and that count only grows). Likes, clicks and agreeing markups never make a video due. A time watermark, not a count comparison: totals shrink (an entry removed on review, a vote changed back) and would hide new evidence, and `POST /vote` keeps the row of a repeated identical vote, so a repeat is never new. Every judgement sets `judged_at` to the tick's start (what the signals were counted up to), so evidence created during the tick counts next time; the tick waits 1 s (`commitSettle`) before its first read, so a write whose `createdAt` (set by Node after its last lock wait, just before its commit: `POST /vote` creates the vote after the `VideoCalculated` / AI row locks, `PUT /markups` writes the intervals after the markup row lock, which can wait out a calculation) precedes the tick's start has committed and is counted now rather than read as old next time. Node, the Go binary and Postgres share the host clock. Every entry kept with nothing newer → one `ok` by `rules` ("every entry kept on review since the last judgement"), which moves `judged_at` past the verdicts. Signals (`signals.go`, restricted to the AI entries' exact `(category_id, start, end)` where the signal has bounds): `votes_up` / `votes_down` (each user's latest vote on each entry), `undo` (`prv_events_interval_undo`), `clicks`, conflicting human markups (live sponsor / self_promotion markups since publish with IoU < 0.5 to every served AI entry of the category, author rating ≥ 0; one on a `hidden` entry, e.g. an `unconfirmed` one, is a conflict too), `duration_variants`, `duration_recut` (a `videos` row off by > 2 s created after publish, with a request for the native_id since); views, requests and age go into `signals` only. Rules first (`rules.go`, on the new evidence): a new re-cut without a new negative → `review` by `rules` (items, the row stays served: anyone can create a `videos` row with any duration, and the row reaches only players of its own cut anyway); no new `votes_down` / `undo` / conflict → `ok` (only a first judgement, whose baseline is the start, gets here); else the LLM, which sees the totals, re-cut or not (a bogus duration never keeps a row from the judge and its withdraw; a new re-cut with new negatives still gets review items whatever the LLM says) (`llm.go`, Messages API, `AI_JUDGE_MODEL`, `ai/prompts/judge-v1.md`, schema `{decision: ok|withdraw|review, reason, segments: [{index, keep}]}`, input: entries with their transcript, counters per 1k views when known, ±60 s windows around entries and conflicting human intervals), not within `AI_JUDGE_MIN_INTERVAL` of the video's last judgement (`judged_at`, set by every judgement, a rules `ok` included; within it `judged_at` stays, so the evidence is still new afterwards). An answer that does not parse or check (one keep per entry, no `ok` with a `keep: false`) → `review` by `rules` with reason `judge_invalid: …` (fail safe toward a human); a transport error fails the video (the next tick retries). An LLM `withdraw` unpublishes (`withdrawn_by = 'judge'`) when `AI_JUDGE_AUTO_WITHDRAW` is on; `withdraw` and `review` (and `judge_invalid`) send one `kind = 'ai'` review item per served (`data`) entry (see ReviewItem), except for an entry that already has an ai item without a verdict (same bounds); the other entries still get theirs, so a withdrawn row can always be restored. Each judgement is a `prv_ai_judgements` row written under the AI row's `FOR UPDATE` (a row withdrawn meanwhile is left alone; one with an ai-item verdict decided after the tick's start, which `applyVerdict` applied under the same lock and may have removed or kept an entry the judgement saw, is left for the next tick: nothing written, `judged_at` stays, the call's cost only in the log); log `ai judge: <video_id> <decision> <by>: <reason>`; heartbeat `ai_judge` (`failed_videos` = videos that failed, e.g. an API error, retried next tick; the success needs only the due-videos query), exit 1 on either. The judge never closes a case without a human (`docs/backlog/ai-judge-autonomy-flag.md`).
- **Votes** on an AI-first video resolve the segment the way GET serves it; a vote belongs to the interval whatever source served it (owner, 2026-10-22): it rates the authors of a human interval with the same bounds and sets the rating of the AI entry and of that human segment alike, in every state of the AI row (see Routes → `votes.js`). Publish starts each entry with the rating of the votes already on its bounds (`calculator.WithVoteRatings`), read holding the `video_calculateds` row lock that the vote handlers take before the AI row, so no vote on the video commits between that read and the row becoming visible; `calculate --recompute-ratings` (prv) also rewrites every AI row's ratings. **Verdicts** on ai items are applied to the AI row (see Routes → `admin-review.js` → decide). A keep verdict may carry the segment's real **bounds** (owner, 2026-10-24: if a human looks anyway, the markup should come out right; `docs/plans/completed/20261024-assessor-timing.md`): the entry is replaced by one at those bounds with `source: "review"` (`confidence` kept, `rating` from the votes on the new bounds; votes on the old bounds are not carried over, as `docs/backlog/votes-lost-when-segment-boundaries-shift.md` accepts), and viewers get it, unless the bounds are under `AI_MIN_SEGMENT_SECONDS` (saved, the entry goes to `hidden` with reason `short`). A keep verdict serves a `hidden` entry too (its truth beats the confidence thresholds); `not_ad` / `unclear` hide the entry with reason `review`. An item's **effective bounds** = those of its latest verdict with bounds, else its own; the entry an item refers to sits there, so `applyVerdict`, `allKept` (`prv/repository/ai.js`) and the judge's `entryKeeps` go from an item to its entry by them, while everything keyed on an entry's bounds (votes, events, judge signals) needs no change. A keep whose bounds cover other served entries of the same category entirely **absorbs** them (owner, 2026-10-29: the detector splits one ad into pieces; `applyVerdict` drops the covered entries, the merged entry gets `source: "review"` and the votes on the new bounds; the absorbed entries' votes count nowhere and their items are history: their effective bounds find no entry inside a served one, so a later verdict on them is a no-op (`applyVerdict` returns unchanged, no 400) and `allKept` / `entryKeeps` need only the merging item); a partial overlap or a covered entry of another category stays `bounds_overlap`; the review page warns "covers N" before the save (`item.ai_entries` = the row's other served entries; `STATE.ai_entries`; `warn_bounds_absorb`) and the decide response carries `absorbed`. The judge request marks such entries `(bounds by review)` (`ai/judge/llm.go`, `judge-v1.md`); `/admin/video` shows a "review" badge (a "chapter" one for `source: "chapter"`). **Admin**: `/admin/video/:video_id` shows the AI row (status, entries, judgements) with a withdraw link (`withdrawn_by = 'admin'`, the operator's per-video switch).
- **Withdraw / restore**: `aiRepository.withdraw(video_id, by, reason)` sets `withdrawn_at/by/reason` (`data` kept for the record) and `prv_ai_videos.status = 'withdrawn'`. Only a verdict restores a row, and only one withdrawn by `judge` or `review`, once every entry left in `data` has a keep as its latest verdict decided after the withdraw (so a `not_ad` that hides the last undecided entry restores it too); `admin` rows stay withdrawn.
