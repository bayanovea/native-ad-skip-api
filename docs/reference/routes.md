# Routes

Moved out of CLAUDE.md on 2026-11-04 (instruction-size limit); CLAUDE.md keeps a summary with the
invariants. A "see X" names a section of CLAUDE.md or of another file in `docs/reference/`.

All three providers share one set of route modules: `rt/routes/index.js` and `yt/routes/index.js` call `prv/routes/provider-router.js` (`createProviderRouter(models, provider)`), which mounts `prv/routes/{markups,videos,votes,users,events}.js` with the provider's own models and the prv repositories (`prv/repository/{markup,markup-time-interval,video}.js`); `markups.js` and `videos.js`, the two that emit metrics, also get `provider: 'rt' | 'yt'` (the metric label; default `prv`). Whatever needs a prv-only model is skipped when the provider's `models` lack it: the AI row lock and lookup (`models.AiVideoCalculated`), the AI queue (`aiRepository` not passed, so `views_text` is ignored), the ban gate (no `banned_at` on rt/yt users) and the auto-ban (no `moderationRepository`). `prv/` also mounts the prv-only admin pages (`admin.js`, `admin-moderation.js`, `admin-review.js`). With `LEGACY_PRV` set, `lib/legacy-field.js` (`legacyField()`, mounted in `server.js` before the three routers, read once at boot) copies `<legacy>_user_id` to `prv_user_id` in `req.query` and `req.body` (an object, or each object of the `POST /events` array) when `prv_user_id` is absent, so the extension's old field name passes the validators and the routes as `prv_user_id`; unset = a pass-through.

- **`markups.js`** — Core markup CRUD. `POST /markup` validates `data.intervals` with `lib/validate-intervals.js` (1–20 items; `start`/`end` finite numbers or numeric strings; after rounding `0 <= start < end <= 86400`; else 400) and creates the markup and all its intervals in one transaction. It rejects users with rating ≤ −2. It also silently returns 201 (no row created) when the user is hard-banned (banned_at IS NOT NULL); see Authentication. `PUT /markups` edits one interval (`new_start` / `new_end` / `new_category_id`): the resulting interval (new values merged with the stored ones) must pass the same `validateIntervals` rules, else 400 with the message as plain text; the interval update and the markup's `is_new = true` are one transaction; the markup is updated first (its row lock can wait out a running calculation) and the interval rows after it, so their `"updatedAt"` dates the edit after any lock wait (the AI judge reads it): the addressed interval is written even for a category change alone, and a category change touches every live interval of the markup. Several delete endpoints have both `DELETE` and `GET` variants because Grafana can only trigger GET requests.
- **`votes.js`** — Vote submission. Each new vote runs in one transaction that first row-locks the video's `VideoCalculated` (`lockVideoCalculated` in `lib/segment-rating.js`, which re-reads once when a recalculation replaced the row meanwhile), then its AI row in any state (`lockAiCalculated`, `lib/find-ai-calculated.js`; prv only (skipped on rt/yt), none for most videos; this order lets an AI publish, which holds the first lock, read the votes without missing one), so votes on a video, its recalculation, an AI publish and `--recompute-ratings` serialise:
  - the segment must exist in what `GET /video-calculated` serves for the video (exact category/start/end), else 404: with `AI_FIRST=on`, an active AI row and a `duration` on the vote (the write lookup then lands within ±2 s, as GET's `match` / `backfilled`), that row's `data` (a segment only in `video_calculateds` of such a video is 404), else `video_calculateds.data`; the user's previous vote rows on the segment are replaced by the new one (the latest of them, `"createdAt" DESC, id DESC`, is the previous vote: pre-2026-10-17 data has several); the same value again keeps the row and its `createdAt` (the AI judge reads that time as when the user said it) and moves no author rating, but still recomputes the segment ratings below (a repeat repairs a drifted one). **One interval, one vote** (owner, 2026-10-22): a vote belongs to the `(category_id, start, end)` whatever source served it, so everything below happens on both paths
  - `recomputeSegmentRating` (`lib/segment-rating.js`) sets `{provider}_calculated_segments.rating` and the matching `video_calculateds.data` entry (sparse) from the votes table, with the calculator's rule (each user's latest vote, summed); `recomputeAiSegmentRating` sets the AI row's matching entry (no segment rows for AI); both run on every vote, whichever path it took (each skips what does not exist), so an AI entry and a human segment with the same bounds carry the same rating and the AI ratings stay right through a withdraw / restore or an `AI_FIRST` flip
  - the markup authors' user `rating` is adjusted by `vote - prevVote.vote` via `prv/service/user.js` `updateRatingByVote(vote, prevVote, { transaction })` (every author whose live markup has an interval with the exact `(start, end)`; ascending user id, so concurrent votes do not deadlock), an AI-path vote included
  - if the rating mutation drops a user to rating ≤ −100, `prv/service/user.js` also sets `banned_at` and writes a `prv_admin_decisions` row with `decided_by='auto'` (idempotent — only the first crossing writes; the `banned_at == null` guard short-circuits repeat crossings)
  - `GET /votes/:id/delete?verifyBearerToken=…` (Grafana link) undoes the vote: 401 on a wrong token, 404 on an unknown (or concurrently deleted) vote, else one transaction under the same locks (`VideoCalculated`, then the AI row) destroys the vote, recomputes the segment rating (table + JSON; skipped when the video has no `VideoCalculated`; also the AI row's entry in any state) and reverses the authors' change with `updateRatingByVote({ ...vote, vote: 0 }, vote, { transaction })`. The voter's own rating is never touched. `201 'Updated'`.
  - `GET /votes/user/:internal_user_id/update-rating?verifyBearerToken=…&rating=N` (Grafana link, e.g. `rating=-100` in `assessors.json`) overrides a user's rating: token first (`middleware/verify-query-token.js`, 401 whatever the params), then `rating` must be an INTEGER-range int (400), unknown user 404, else `201`. Each override is logged to stdout as `Admin rating override { internal_user_id, from, to }` (no table).
- **`videos.js`** — `GET /video-calculated` serves aggregated segments (prv: the AI row instead when AI-first applies, see AI-first segments; optional `views_text` string, the page's view counter, recorded in `prv_ai_videos` with every `v` request, see AI-first segments → Trigger); a request without `v` is counted in `request_without_version_total` under its provider; on prv (`legacyUnversioned: true` from `prv/routes/index.js`, old prv clients) it reads `'-' + video_id` first, then `video_id`, with no lookup outcome, as `POST /markup` without `v` prepends `-`; on rt/yt (their clients always send `v`) both take the normal path. Uses a read-only `findVideoForRead` helper (never creates Video rows): looks up by `(native_id, duration±2)` (tolerance constant in `lib/duration-tolerance.js`), then `(native_id, null duration)` updating it, then any `native_id` match, then 204. The tolerance query is ordered by `ABS(duration - <requested>)`, then `id`, on the read path and in `findByNativeIdAndDuration` (`POST /markup`) alike, so a duration that fits both rows of an old split pair always lands on the same row (the 5 pre-2026-10-19 pairs stay split by decision: `docs/backlog/video-rows-race-and-old-split-families.md`).
- **`prv/routes/events.js`** — `POST /events` (shared by all providers). Accepts a JSON array of mixed events; supported types below. Invalid events (unknown `type`, missing fields) are logged to stdout and skipped — the rest of the batch still processes. Returns `{ data: { time_saved: { ... } } }` when the batch contains at least one `time_saved` event (with `LEGACY_PRV` set, `by_<legacy>_user_id` next to `by_prv_user_id`, the same value, for old clients).
  - **`interval_undo`** — fields: `user_id`, `prv_user_id`, `video_native_id`, `category_id`, `start`, `end`. Stored in `{provider}_events_interval_undo`.
  - **`interval_click`** — fields: same as above plus `click_time` (int). Stored in `{provider}_events_interval_click`.
  - **`time_saved`** — fields: `user_id`, `prv_user_id`, `inc`. Increments `User.time_saved`; stored in `{provider}_events_time_saved`. Response mirrors the old `POST /users/time-saved` structure: `by_user_id`, `by_prv_user_id`, `by_user`.
  - **`client_failed`** — fields: `user_id`, `prv_user_id`, `video_native_id`, `reason` (string), `data` (arbitrary JSON, optional). Stored in `{provider}_events_client_failed`.
- **`prv/routes/users.js`** — Shared by all providers (currently empty; `POST /users/time-saved` was removed in favour of the events endpoint).
- **`prv/routes/admin.js`** — Server-rendered HTML dashboard (`/admin/video/:video_id`) for viewing and deleting markups grouped by interval, plus an AI block (the `prv_ai_video_calculateds` row: status, served entries (a "review" / "chapter" badge when an assessor / a chapter set the bounds), `hidden` entries greyed in their own table with the reason, `prv_ai_judgements`; every entry's Review column shows its open ai item as `<batch> <code>` or a "Send to review" confirm button); protected by `AUTH_TOKEN` query param. prv only. `GET /admin/video/:video_id/ai/withdraw?verifyBearerToken=…` (numeric `videos.id`, from a confirm button) withdraws the AI row by `admin` (`200 'Withdrawn'`, 404 when there is no published row, 400 on a non-numeric id; an unset `AUTH_TOKEN` refuses every request); no verdict ever restores it. `GET /admin/video/:video_id/ai/review?verifyBearerToken=…&start=<int>&end=<int>` (same auth and 400 rules) is the operator's way to get an item on any entry he saw (`aiRepository.sendToReview`): one `kind = 'ai'` item on the entry at those bounds (served or hidden, the row in any state) in today's sheet `ai-admin-<YYYY-MM-DD>` (UTC), code `M<position>`, `proposed` = the entry's category, `cues` = the run's cues over the bounds, link at start − 2 s, `flagged_by` `["admin: sent to review", "entry: <category> <confidence>, <len> s, served|hidden: <reason>"]`, placed by `reviewRepository.openPart` (the JS twin of `ai/review` `Batch`, which the Go producers use: the sheet's newest part nobody holds or has a verdict in with room within 30, else `<sheet>`, `-p2`, … registered `urgent`, one review; lock order AI row → batch row, the judge's) — `201 'Sent to review: <batch> <code>'`, `409 'Already in review: <batch> <code>'` when the entry has an item without a verdict (the judge's rule, `openAiItems`), `404 'No AI entry at these bounds'`. The owner then takes the batch on `/admin/review` and a keep with wider bounds merges the pieces (see Votes / Verdicts → absorb).
- **`prv/routes/admin-moderation.js`** — prv-only moderation routes, protected by `AUTH_TOKEN` query param (`?verifyBearerToken=…`).
  - `GET /admin/moderation?verifyBearerToken=…&show=all&format=json` — admin moderation page. Lists worst users + worst markups sorted by suspicion score (`3*dislikes + 1*undos` for users; `+ 3*max(0, -segment_rating)` for markups). Default view hides rows where a prior decision exists and `current_score - snapshot.score < 5` (`RESURFACE_THRESHOLD`). `?show=all` reveals all. `?format=json` returns structured data for tests/integrations.
  - `POST /admin/moderation/decide?verifyBearerToken=…` — body `{target_type:'user'|'markup', target_id, decision:'approve'|'reject'}`. Returns `204`. Side effects: `user`+`reject` sets `users.banned_at=NOW()`; `user`+`approve` clears it; `markup`+`reject` soft-deletes the markup and (if no remaining siblings) destroys `VideoCalculated` else marks siblings `is_new=true`; `markup`+`approve` records the decision only. Writes a row to `prv_admin_decisions` with snapshot and `decided_by='admin'`.
  - `GET /admin/user/:internal_id?verifyBearerToken=…` — video-less per-user view showing all markups across all videos. Param is the internal `users.id` PK, NOT `prv_user_id` (which is not unique — multiple `User` rows can share the same `prv_user_id` because the unique index is composite `(generated_user_id, prv_user_id)`).
- **`prv/routes/admin-review.js`** — prv-only assessor review page (sibling of moderation, same `?verifyBearerToken=…` auth, but an unset `AUTH_TOKEN` refuses every request). One verdict per AI-flagged segment from an imported review sheet (see Ops). Reads/writes only through `prv/repository/review.js`. **Reviewer identity**: every page needs `&reviewer=<code>` (a row of `prv_review_reviewers`); `/admin/review` without it (or with an unknown code) shows the picker, `/admin/review/:batch` without it redirects there (302; `format=json` → 400). All links and POST bodies carry the code on. **Language**: Russian by default (assessors), English switch in the toolbar; `?lang=ru|en` sets the `review_lang` cookie (1 year, path `/admin/review`, httpOnly), and `<html lang>` follows. Every visible string comes from `lib/i18n.js`; only `_html` keys may hold markup (repo-owned files), the rest is escaped; verdict values stay English identifiers in the DB and JSON, only labels are translated; client-side texts go to the inline script in `STATE.i18n`.
  - **First come, one holder** (`prv/repository/review.js`, `STATE`): batches are not assigned. The `prv_review_batches` row holds `reviews_needed`, `excluded` and the lock (`locked_by`, `locked_at`); per batch `finished` = reviewers with a verdict on every item. State for reviewer R, first match wins: `mine` (R holds it), `done` (R ∈ finished), `closed` (R ∈ `excluded`, even while someone holds it), `locked` (another holder), `available` (no holder, R not finished, `|finished| < reviews_needed`; a reviewer who gave up halfway may come back only until then, so their late verdicts never override a complete review in the default export), else `closed`. Only `mine` and `done` may decide (a finisher can still fix their verdicts). **Idle locks expire**: a lock whose holder has saved no verdict in the batch for 12 h (`LOCK_IDLE_HOURS`, counted from the later of `locked_at` and their last verdict there) is cleared by `releaseIdleLocks()`, which the list, item, take/release and decide routes and the importer run first (outside their transaction, `FOR UPDATE SKIP LOCKED`); each release is logged as `Review lock expired { batch, locked_by }`. Verdicts stay; the former holder takes it again like anyone else.
  - `GET /admin/review?reviewer=…&verifyBearerToken=…[&show=all][&format=json]` — batch list in sections In work / Available / Locked by others / Done (`closed` rows only with `show=all`), with state, priority label (Urgent / Important / Optional), total and R's decided / open per batch; within a section `urgent` first, then `important`, then `optional` (each run of one priority under a divider row `priority-group-<p>` and with a coloured left edge, `groupByPriority()`), most recently imported first within a priority. JSON: `{reviewer, batches}`, rows `{batch, total, decided, open, reviews_needed, priority, finished: [codes], locked_by, locked_at, state}` (`state` ∈ `mine | available | locked | done | closed`); without a reviewer `{reviewers, reviewer: null}` (400 for an unknown code). The picker has a "create reviewer" form under the name list.
  - **Owner's audit block** (`renderAudits`): with `reviewer=bayanovea` (`OWNER_REVIEWER`) the batch list shows "Выводы аудита" / "Audit findings" above the sections, and its JSON gets `audits`: `reviewRepository.ownerAudits()` = per batch its latest `prv_review_audits` row, when not hidden and holding a new `owner` / `backlog` finding (only those findings shown: severity badge, item codes, text; summary and `llm_error`). Any other reviewer gets neither. `POST /admin/review/audits/:id/hide?verifyBearerToken=…` — body `{reviewer}` (the block's form or JSON): 403 unless the reviewer is `bayanovea`, 404 for an unknown id, else `hideAudit()` sets `hidden_at` / `hidden_by` (a second hide keeps the first, 200); form → 303 to the list, JSON → `200 {id, hidden: true}`. Strings `audit_*` in `prv/locales/review/{ru,en}.json`. See Ops → Audit.
  - `POST /admin/review/reviewers?verifyBearerToken=…` — body `{name}` (form or JSON); the cleaned name (`lib/reviewer-name.js`) is the code. Taken in any letter case (compared in JS under a table lock) → `taken`, bad name → `invalid`. Form: 303 to the new reviewer's batch list, or 400 with the picker, the typed value and the reason; JSON: `201 {code}` or `400 {reason, message}`.
  - `POST /admin/review/:batch/take` / `…/release?verifyBearerToken=…` — body `{reviewer, force?: boolean}`. Take runs under the batch row lock (`withBatchLock()`), then locks the batch when it is available to R (`UPDATE … WHERE` with the availability check), so of two concurrent takes exactly one wins and a take waiting on a final decide or import sees its verdicts (taking your own batch again is a no-op). Without the row lock first, a waiting UPDATE re-checks only `locked_by`, not the verdicts its subquery read, and could lock a completed batch. Release clears the holder's own lock ("Give up"; verdicts stay), or anyone's with `force: true` (the page asks for a confirm naming the holder; covers an assessor who disappeared). `200 {batch, locked_by, locked_at}`, 400 bad input / unknown reviewer, 404 unknown batch, `409 {reason, locked_by, message}` (`reason` = R's state, `message` in the page language).
  - `GET /admin/review/:batch?reviewer=…&verifyBearerToken=…&item=C7&format=json` — item page; without `item` R's first open item by `position`, or the last item when R has decided them all; 404 on unknown batch/item. "Open" and nav `decided` / first open / save → next open count R's verdicts, so a second reviewer starts at C1. A lock banner says R's state with one button: "Take it" (`available`), "Give up" (`mine`), force "Give up" naming the holder (`locked`); verdict controls are disabled unless R may decide. The verdict buttons and comment start from R's own latest verdict (`item.own_verdict`); the "Current verdict" block, history and `flagged_by` show everyone's (a second reviewer is not blind). Shows times in player format (`m:ss` / `h:mm:ss`), the item's bounds and, when the effective bounds differ, "→ corrected a – b (reviewer)", the stored `link` from the sheet (already at start − 2 s, used as is; `player_link` is `null` and no link is shown when it is not http(s)), cues (an ai item with an AI row: the **transcript window** instead, `?context=N` seconds on each side of its own and effective bounds, int 0…600, default 60, else 400, with a "+60 s" link: cue lines with their time, words as spans with their time when the run stored them, else a notice that a selection snaps to whole lines; the flagged stretch and the corrected one highlighted; above it the run's chapters overlapping the window, «title» and times, each with a button that fills the bounds inputs with the chapter's, rounded inward, source `chapter`; shown before a verdict: the author's public timecodes, not detector output), a short "How to decide" rules card (payer test, woven-in calls to action are still self_promotion, unclear only when the text does not decide, track flag is separate, the boundary rule: the lead-in is part of the ad, the return to the topic is not, "link in the description" is part of the ad), and a signals panel (±30 s, across all `videos` rows of the native_id: live markups with author rating, calculated segments with rating + vote counts, undo/click counts). JSON shape `{reviewer, batch (R's progress row, as in the list), can_decide, item, video_flags: {track_mismatch}, nav: {prev, next, first_open}, signals, transcript, context, min_segment_seconds}` (`min_segment_seconds` = `AI_MIN_SEGMENT_SECONDS`, also in the page's `STATE`; `transcript` = `{from, to, has_words, cues: [{start, end, text, words?: [{t, text}]}], chapters: [{start, end, title}]}` from `prv_ai_runs.transcript` / `.chapters` via the AI row's `run_id`, null for sheet items; history entries carry `bounds: {start, end, source} | null`; `item.effective_bounds` = `{start, end, reviewer, source}` (reviewer / source null for the item's own), `item.own_bounds` = R's latest verdict's bounds); nav entries are `{item_code, decided, player_link}`. `item.beyond_video_s` is the longest known duration of the native_id's `videos` rows when the item starts after it (the track is from a longer cut, the player opens at 0), else `null`; the page shows it as a yellow warning under the player link. Switching items (`j`/`k`, plain click on ◀/▶/first open, save → next item) also preloads the new item's player behind the review page by swapping tabs: the new item opens in a new tab in front, the current tab navigates to the player (a page can neither open a tab behind itself nor open one on load). Popup blocked or no link → plain navigation, no player. A successful save closes the saved item's player tab (the review tab's `window.opener`, only when cross-origin; a same-origin opener is the batch list). The browser closes only script-opened tabs, so the batch list opens a batch with `window.open`; a player in a tab the reviewer opened stays and the save flash says to close it by hand. A checkbox under the hotkeys line, "After saving, open the next item" (on by default, `adminReview.autoAdvance` = `off` in localStorage when cleared), turns the save → next item switch off: the save reloads the same item and leaves its player tab open. **Verdict** = what the text is (four buttons). **Bounds** (optional, two inputs under the verdict buttons, hint: only when the timing is visibly off and a viewer would notice; pre-filled from `own_bounds`; disabled and cleared on `not_ad` / `unclear`): a selection over the transcript fills them (`selectionchange`: floor of the first selected word's time, ceil of the last one's end = the next word's time or the cue's end; source `cue`), typing `m:ss` / `h:mm:ss` / seconds sets source `typed`; the page checks them with the server's `parsePlayerTime` / `validateVerdictBounds` (`lib/review-sheet.js`, inlined into the script); bounds shorter than `STATE.min_segment_seconds` save with a warning (`warn_bounds_short`, live under the inputs and in the save flash: saved, not served while the threshold stands), a clear button empties both. **Track flag** (checkbox under the "Extra flags" label with a one-line hint that a flag never replaces the verdict, hotkey `5`): "Subtitle track ≠ video", a per-video fact in `prv_review_video_flags` (`track_mismatch`, append-only, latest wins), shown pre-checked with who set it on every item of that video; independent of the verdict (replaced the pre-2026-10-18 "Wrong text" shortcut, which saved `unclear` with a canned Russian comment; such verdicts are shown as legacy and should be re-decided). Hotkeys: `1`–`4` verdict, `5` flag, `c` comment, `t` start-time input, `Enter` / Ctrl+Enter save, `j`/`k` next/prev, `o` open player, `Esc` leave a field; letters also work by physical key on a non-Latin (e.g. Russian) layout. The letter keys are one list, `LETTER_HOTKEYS`, read by the key handler (via `STATE.letters`), the hotkeys line and the onboarding table (`hotkeyRows()`), so the help cannot drift. Saving the same verdict, comment and bounds the same reviewer already has, with the flag unchanged, is "No change" on the page; the server also never appends a duplicate verdict row for the same reviewer (so a flag-only save writes only the flag), while another reviewer saving the same verdict adds a row.
  - `POST /admin/review/decide?verifyBearerToken=…` — body `{item_id (JSON integer), verdict: 'sponsor'|'self_promotion'|'not_ad'|'unclear', comment? (string or null; trimmed, blank → null), reviewer (registered code), track_mismatch? (boolean), bounds? ({start, end, source: 'cue'|'typed'|'chapter'} or null; times ints or `m:ss` / `h:mm:ss` strings; keep verdicts only; whole seconds, `0 ≤ start < end ≤ 86400`; shorter than `AI_MIN_SEGMENT_SECONDS` is saved, the entry then hidden)}`. `409 {reason, locked_by, message}` unless R holds the batch or has finished it; the check and every write below run in one transaction with the `prv_review_batches` row locked `FOR UPDATE` (`withBatchLock()`), so a release or take waits for the save. Appends a `prv_review_verdicts` row (`source='page'`, with the bounds) unless identical (verdict, comment, bounds) to the item's latest row by the same reviewer, and a `prv_review_video_flags` row when `track_mismatch` differs from the video's current value; on a `kind = 'ai'` item an appended verdict also goes to `aiRepository.applyVerdict(item, verdict, { from, to, transaction })` in the same transaction (lock order batch row → AI row; the judge never adds to a batch someone holds or has a verdict in, so no cycle), `from` = the item's effective bounds before this verdict (`effectiveBounds()`, read under the batch lock, as the item itself: the adopt script changes it under that lock), `to` = the verdict's bounds or `from`; the entry at `from` is looked up in `data` and `hidden`: `not_ad` / `unclear` move it to `hidden` with `reason: 'review'` at `to` (the row is withdrawn by `review` when that empties `data`), `sponsor` / `self_promotion` keep it with that category at `to` or put it back (moved → `source: 'review'`; a hidden entry at exactly `to` gives way, items find entries by bounds), in `data` (its `rating` recomputed for the new category and bounds; bounds overlapping another `data` entry → 400, nothing written) or, under `AI_MIN_SEGMENT_SECONDS` (`lib/ai-rules.js`), in `hidden` with `reason: 'short'` (a keep never withdraws: a row whose last served entry went short serves nothing); both arrays sorted by `start`; a row withdrawn by `judge` / `review` is served again (`prv_ai_videos.status = 'published'`) once every `data` entry has a keep verdict as its latest, decided after `withdrawn_at`; idempotent. Returns `201 {item_id, item_code, verdict, bounds, effective_bounds, track_mismatch, flagged_by, next_item, next_player_link, ai_applied}` (`bounds` of the item's latest verdict) (`ai_applied`: the AI row changed, either array; always present, false for sheet items; `next_item` = R's next open item after this one, wrapping round, `null` when R is done); R's verdict on the last open item releases their lock (`releaseIfFinished`), so the batch moves to `done`. `400` on invalid input, unknown reviewer or unknown item; the bounds errors (`ReviewInputError` with a `code`) are in the page language (`error_bounds_*`).
  - **Onboarding**: a `<details>` block, closed by default, on the batch list and the item page (not on the picker): what this is, workflow (take → item by item → finishes on the last verdict; give up), verdicts, track flag, player window, −2 s start, hotkeys, comments → shared chat. Sections `ONBOARDING_SECTIONS`, keys `onb_<section>_title` / `onb_<section>_html`.
  - **Blind rule**: `flagged_by` (which detector runs flagged the segment) is stripped in the repository from every item without a verdict, so neither HTML nor JSON shows it until the item is decided. On an ai item the decided block also shows an "AI segment" badge and the judge's reason (parsed from the `judge …: <reason>` line of `flagged_by`, keys `ai_badge`, `ai_judge_reason`), so they are blind too.
- **`prv/routes/routes.js`** — Health check (`GET /`) and Prometheus metrics (`GET /metrics`).
