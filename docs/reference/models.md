# Database Models

| Model | Notes |
|-------|-------|
| `Markup` | User-submitted segment; soft-deleted via `deleted_at` |
| `MarkupTimeInterval` | start/end times belonging to a Markup; also soft-deleted |
| `MarkupCategory` | Enum: intro, sponsor, self_promotion, credits |
| `Video` | Video reference with optional duration |
| `VideoCalculated` | Aggregated JSON array per video (1:1 with Video). Each entry: `category_id`, `start`, `end`; `rating` present only when non-zero. The old `meta` column was dropped on 2026-10-18 (`lib/schema.js`) |
| `CalculatedSegment` | One row per aggregated segment — table `{provider}_calculated_segments`; carries `rating`, derived from the votes table (calculator, vote handler, `--recompute-ratings`) |
| `CalculatedSegmentMarkup` | Junction linking a `CalculatedSegment` to each contributing `Markup` — table `{provider}_calculated_segment_markups` |
| `Vote` | User vote on a calculated segment (-1, 0, +1), keyed by `(video_id, category_id, start, end)`: one interval, one vote, whether an AI entry or a human segment served it |
| `User` | Internal user mapped to prv user ID; tracks `rating`, `time_saved`, and `banned_at` (hard ban — set by admin via /admin/moderation/decide or automatically when rating ≤ -100; gates POST /markup independently of the soft `rating ≤ -2` check) |
| `AdminDecision` | Append-only log of admin moderation decisions — table `prv_admin_decisions` (prv only — no rt_ / yt_ analogue exists; moderation is prv-scoped per plan). Fields `target_type` ('user'\|'markup'), `target_id`, `decision` ('approve'\|'reject'), `signals_snapshot` (JSONB), `decided_at`, `decided_by` ('admin'\|'auto'). Latest row per target acts as a watermark for the re-surface threshold on /admin/moderation. All writes go through `moderationRepository.recordDecision()` — both the admin POST endpoint and the auto-ban hook share this single entrypoint to keep `signals_snapshot` consistent. |
| `DurationLog` | Tracks claimed video durations for anomaly detection |
| `CalculatorHeartbeat` | Defined in `db.js` (shared, no provider prefix) — table `calculator_heartbeats`, one row per `provider` written by the Go calculator at the end of every run (see Calculation Algorithm step 4), read by `GET /metrics`. Node never writes it. The `ai` command writes rows `ai_detect` / `ai_judge` / `ai_audit` the same way (`calculator.WriteHeartbeat`; `failed_videos` = videos failed in the tick, for `ai_audit` batches and sends) and deletes its row when its switch is off (`calculator.ClearHeartbeat`), so a switched-off command has no series instead of an aging one |
| `IntervalUndo` | Records interval undo events — table `{provider}_events_interval_undo` |
| `IntervalClick` | Records interval click events with `click_time` — table `{provider}_events_interval_click` |
| `TimeSavedEvent` | Records time_saved events — table `{provider}_events_time_saved` |
| `ClientFailed` | Records client-side failures with free-form `reason` and `data` JSON — table `{provider}_events_client_failed` |
| `ReviewItem` | One AI-flagged segment from an imported review sheet, or one entry of an AI row sent by `ai judge` — table `prv_review_items` (prv only). `kind` (TEXT NOT NULL DEFAULT `'sheet'`; `'ai'` for items on an AI row's entry: judge, below-threshold and adopted items) and `video_id` (INT NULL, the `prv_ai_video_calculateds` row of an ai item) are `lib/schema.js` ALTERs with defaults, so a pre-AI image keeps inserting; `hydrate` exposes both. Judge items (`ai/judge/review.go`, the same INSERTs as `insertItems` / `createBatch`, `reviews_needed` 1, priority `urgent`): sheet `ai-judge-<YYYY-MM-DD>` (UTC), codes `A<n>`, batch = the sheet's newest part nobody holds or has a verdict in with room for the video's items within 30, else a new part (`<sheet>`, `<sheet>-p2`, …), so a reviewer's batch never grows; `proposed` = the entry's category, `cues` = its transcript, `link` = player link at start − 2 s (`PROVIDER_LINK_AT`, `{t}` as `1h2m3s`), `flagged_by` = `["judge <decision> by <by>: <reason>", "signals: <non-zero counters>", "keep: <bool>"]`. md imports never produce ai items; `import-below-threshold.js` creates `B<n>` ai items on hidden entries and, with `--served`, `S<n>` ones on served entries (see Ops); the admin "send to review" link creates `M<n>` ai items in `ai-admin-<date>` (see `admin.js`); the second opinion creates `D<n>` ai items in `ai-second-<date>`, priority `important`, and the chapter check `T<n>` ai items in `ai-chapter-<date>`, priority `important` (see AI-first segments). Fields `sheet` (sheet name), `batch` (the part the item belongs to: the sheet name, or `<sheet>-pN` when the sheet was cut), `item_code` (`C7`), `position`, `native_id`, `start`/`end` (seconds, from key.tsv; an ai item's = its entry's whole seconds), `proposed` (`sponsor` or `sponsor+self_promotion`), `cues`, `link` (player link from the sheet, required by the importer), `flagged_by` (JSONB run ids, blind until decided), `created_at` (DB-side default). `sheet` is nullable without backfill: a pre-2026-10-20 image inserts items without it (`ON CONFLICT` on the `(batch, item_code)` index, which stays), so every read uses `COALESCE(sheet, batch)`; unique `(COALESCE(sheet, batch), item_code)` (expression index in `lib/schema.js`), which also makes such an image's insert of a split sheet's code fail instead of duplicating it. The importers, the split and the adopt script write items via `reviewRepository.insertItems()` (with `kind` / `video_id`) / `itemsInSheet()` / `splitBatch()` / `adoptItem()` (no review-table SQL in `scripts/`); the one exception is the Go side (`ai/review`, used by the judge, the second opinion and the chapter check), which inserts its items and batches with its own SQL (a Go binary cannot call the repository), so a change to these tables updates both (and `openPart()`, its part-placement twin in `review.js`). Its part names are the importer's for a re-import that adds a part to a sheet imported whole (`<sheet>`, then `-p2`, …; it never cuts a sheet up front, so no `-p1`) |
| `ReviewVerdict` | Append-only assessor verdicts — table `prv_review_verdicts`, FK `item_id` (cascade). `verdict` (`sponsor`\|`self_promotion`\|`not_ad`\|`unclear`), `comment`, `reviewer` (a `prv_review_reviewers` code; md imports: `--reviewer`, default `bayanovea`), `source` (`page`\|`import`), `start` / `end` (INTEGER) / `bounds_source` (`cue`\|`typed`\|`chapter`\|`import`): the segment's bounds set by the assessor, all three or none, keep verdicts only (nullable `lib/schema.js` ALTERs, so a pre-bounds image keeps inserting), `decided_at` (DB-side default `CURRENT_TIMESTAMP`, also set on existing tables by `bootstrap()`). Latest row per item (`decided_at DESC, id DESC`) is the verdict, older rows are history. All writes go through `reviewRepository.recordVerdict()` (page and importer), which throws `ReviewInputError` (→ 400) on bad input |
| `ReviewReviewer` | Reviewer codes — table `prv_review_reviewers` (`code` PK, `created_at`). Seeded with `REVIEWERS` (`bayanovea`, `gkshi`) in `lib/schema.js`; assessors add themselves on the picker (`reviewRepository.createReviewer()`, unique in any letter case). Verdicts, flags and locks carry these codes |
| `AiVideo` | AI detection queue and state, one row per native_id — table `prv_ai_videos` (prv only, like every `prv_ai_*` table; all new tables, created by `sync()`). `native_id` PK, `views_max`, `views_text` (the latest counter string a client sent, a `lib/schema.js` ALTER), `requests`, `first_seen_at`, `last_seen_at` (read path), `status` (default `seen`, only the detector and withdraw / restore move it), `attempts`, `next_attempt_at`, `batch_id`, `last_error`, `judged_at`, `judge_counters` (JSONB, the counters at the last judgement; only its `duration_recut` is read back, as the re-cut watermark), `queued_by` (TEXT NULL, a `lib/schema.js` ALTER: `views` | `requests` | `both` | `manual`, which criterion let the row into the detector, set once on the first claim, NULL for rows claimed before 2026-10-28), `updated_at` |
| `AiRun` | One row per detector call — table `prv_ai_runs`: `native_id`, `video_id`, `prompt_sha`, `prompt_version`, `model`, `transcript` (JSONB meta + cues `{start, end, text, words?: [{t, text}]}`, words from prv's per-word tags since 2026-10-24 (eval `vtt` 7fd1a9a), read by the judge (text only, never the words) and by the review page's transcript window), `track_overrun_s`, `yt_duration_s`, `chapters` (JSONB `[{start, end, title}]` from yt-dlp's info, `[]` = none, NULL = unknown; a `lib/schema.js` ALTER), `raw_output`, `usage`, `cost_usd` (null until the answer comes), `created_at`. The detect budget counts these rows |
| `AiVideoCalculated` | The AI's final segments per `videos` row — table `prv_ai_video_calculateds`: `video_id` PK (FK `videos`), `native_id`, `run_id` (FK `prv_ai_runs`), `data` (JSONB entries `{category_id, start, end, confidence, source: "ai" | "chapter" | "review", rating?}`, `chapter` when the chapter check served it at a chapter's bounds, `review` once an assessor's verdict set its bounds, `rating` sparse as in `video_calculateds`), `hidden` (JSONB, default `[]`, a `lib/schema.js` ALTER: every other detected segment, same shape plus `reason` `confidence` \| `short` \| `review` (`not_ad` / `unclear` verdict) \| `unconfirmed` (the second model did not find it), no ratings), `published_at`, `withdrawn_at` / `withdrawn_by` (`judge` \| `review` \| `admin`) / `withdrawn_reason`, `updated_at`. Withdrawn rows keep `data`; serving checks `withdrawn_at IS NULL` and non-empty `data`. Written by `ai detect` (publish), `ai regate`, the vote handlers and `calculate --recompute-ratings` (`rating`), `aiRepository.withdraw()` / `applyVerdict()` and `ai judge` |
| `AiJudgement` | Append-only judgements — table `prv_ai_judgements`: `video_id`, `decision` (`ok` \| `withdraw` \| `review`), `by` (`rules` \| `llm`), `reason`, `signals` (JSONB), `model` / `cost_usd` (LLM only), `created_at` |
| `AiConfirmation` | One row per second-model call on a detector run — table `prv_ai_confirmations` (`ai/pipeline/confirm.go`): `run_id` (unique, FK `prv_ai_runs`), `video_id`, `native_id`, `model`, `prompt_sha` (the prompt the second call got), `raw_output`, `usage`, `cost_usd`, `error` (the failure text; then `confirmed` / `unconfirmed` / `extra` are NULL), `confirmed` (entries served), `unconfirmed` (entries hidden as `unconfirmed`), `extra` (second-model segments matching no first-model one), `created_at`. Written in the publish transaction; read by `/metrics` (`ai_cost_usd{kind="confirm"}`) and the dashboard |
| `AiTimeline` | Phase 3 (audio drift), no writer yet — table `prv_ai_timelines`: `id`, `native_id` (indexed), `video_id`, `yt_duration_s`, `steps` (JSONB `[{at_s, shift_s}]`, shift = subtitle time − audio time), `windows` (JSONB measurements), `method`, `measured_at` |
| `ReviewBatch` | One row per review batch — table `prv_review_batches` (`batch` PK = the items' batch name). `reviews_needed` (INT, default 1: how many reviewers must finish it), `excluded` (TEXT[], default `{}`: codes that may never take it), `priority` (`urgent` \| `important` \| `optional`, default `important`; sort order of the list, `PRIORITIES` in `prv/repository/review.js`; the judge's batches are `urgent`, the importer's `--priority`), `locked_by` / `locked_at` (current holder, null = free), `created_at`; the table also keeps a legacy `assignee` column the model leaves out (always NULL after boot, see Schema bootstrap). Written by the importer (`createBatch()`) and the lock calls; "who worked on / finished it" is derived from verdicts, not stored |
| `ReviewAudit` | One row per audit of a finished review batch by `ai audit` (see Ops → Audit) — table `prv_review_audits` (prv only, created by `sync()`): `batch` (indexed), `watermark` (the batch's newest verdict id when audited), `items`, `metrics` (JSONB: verdicts, proposed × verdict, sources, comments, bounds, pace per reviewer, `model_findings_dropped`), `findings` (JSONB `[{kind, severity, items, text, evidence, action, new}]`), `summary`, `model`, `prompt_sha`, `raw_output` (TEXT), `usage`, `cost_usd`, `llm_error`, `created_at` (indexed), `notified_at` (the Telegram message went out), `hidden_at` / `hidden_by` (the owner's hide). Written by the Go side only; only `notified_at` and `hidden_*` are ever updated; never deleted |

**Soft Deletes:** All queries must filter `deleted_at IS NULL`. This is handled in `repository/` — always check there when writing new queries.

**Dual User ID System:** Users have both a `generated_user_id` (UUID) and an optional `prv_user_id`. The codebase is transitioning to internal DB `id` references.

**Schema bootstrap:** project has no migrations folder. New tables come from `sequelize.sync()` (run on every boot in `db.js`); new columns on existing tables are added with idempotent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statements run right after `sync()`. Example: `banned_at` on `users`. Column defaults go the same way (`ALTER TABLE … ALTER COLUMN … SET DEFAULT …`, e.g. the review tables' `created_at` / `decided_at`). The sync, the ALTERs and category seeding live in `lib/schema.js` `syncSchema()`, shared by `bootstrap()` and `scripts/sync-db.js`, so both leave the DB in the same shape — add new ALTERs there. One-offs live there too, guarded so a second boot is a no-op: `migrateBatchAssignees()` (2026-10-20) touches only rows with `prv_review_batches.assignee IS NOT NULL` and, in one transaction, sets `excluded = {bayanovea}` on `gkshi` batches (blind copies of her sheets), locks every free batch whose assignee has not finished it on that assignee (`gkshi` only once started, so untouched overlap batches go to anyone else), then sets `assignee = NULL`. The column is kept (nullable, added `IF NOT EXISTS` on a fresh DB, not in the model) because a pre-2026-10-20 image inserts it on boot, so a rollback still starts; a roll-forward re-migrates only the rows that image assigned. Dropping it: `docs/backlog/drop-review-batch-assignee.md`. `renameLegacyObjects()` (2026-10-29) runs **before** `sync()` (which would otherwise create empty `prv_*` tables next to the old ones) and only with `LEGACY_PRV` set: in one transaction, in schema `public`, constraints whose name carries the `LEGACY_PRV` prefix first (`pg_constraint`, `ALTER TABLE … RENAME CONSTRAINT`; a PK / unique constraint's index follows it), then the remaining tables, indexes and sequences (`pg_class` relkind `r` / `i` / `S`, names `<legacy>_…` or containing `_<legacy>_user_id`, e.g. `users_generated_user_id_<legacy>_user_id`), then the columns `<legacy>_user_id` / `deleted_by_<legacy>_user_id` of every table (`information_schema.columns`), then `calculator_heartbeats.provider` `<legacy>` → `prv` (when the table exists); the leading `<legacy>_` or the inner `_<legacy>_user_id` becomes the `prv` form, identifiers quoted; a table's row type follows the table. Logs `Legacy rename: N objects`, nothing when a boot finds none (idempotent); `test/legacy-rename.test.js`. `renameToLegacy()` is the same rename (`renamePrefix()`) from `prv` back to `<legacy>`, logging `Rename to legacy: N objects`, run only by `scripts/rename-to-legacy.js` for a rollback (see Deployment); both refuse a prefix other than lowercase letters and digits, or `prv`. A 2026-11-03 one-off sets `prv_ai_video_calculateds.data` to `[]` where it is JSON null (the chapter check published an empty served list so before `ai/pipeline/chapters.go` was fixed; `jsonb_array_length` in the judge's due query and `.map` on the review page failed on such rows).
